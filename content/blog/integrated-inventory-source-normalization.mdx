동기화 버튼을 누르면 네 원천 테이블을 `UNION`해 한 테이블로 복사하는 것으로 끝날 것 같았다. 실제 문제는 그다음이었다. 오프라인 매장, 이커머스, 식단 서비스인 그리팅, 물류센터는 같은 상품 재고도 서로 다른 컬럼명과 상태값으로 기록했고, 가격을 책임지는 원천과 물리 LOT·소비기한을 책임지는 원천도 달랐다.

이 차이를 화면과 업무 기능마다 직접 해석하게 두면 새로운 원천이 추가될 때마다 조회, 위험 판정, 대시보드, 배치 로직을 모두 고쳐야 한다. 더 큰 문제는 같은 상품을 가리키는 값이 충돌할 때다. 어느 원천을 믿어야 하는지 설명할 기준이 없어진다.

네 원천은 출처를 추적할 수 있도록 그대로 보존했다. 동기화 서버는 우리 서비스가 이해하는 **공통 재고 의미**로 번역하고, `MAPPED` 상태의 연결과 같은 실행에 들어온 변경 후보 사이의 값 충돌을 검증한 뒤 정식 업무 데이터에 반영했다. 재고가 달라진 범위는 같은 트랜잭션에서 수요예측·안전재고·LOT 규칙으로 다시 판정해 목록이 보여 줄 위험 등급과 이유까지 함께 저장했다.

이 글에서 말하는 **원천 정규화**는 관계형 데이터베이스의 제1·제2정규형처럼 테이블 중복을 분해하는 이론을 뜻하지 않는다. 서로 다른 외부 표현을 하나의 업무 언어로 맞추는 **표준화와 통합 과정**을 뜻한다.

원천 표준화·검증 로직과 초기 데이터 생성기는 제가 맡은 [Backend 원천 동기화 PR #65](https://github.com/kosa11-final-project/BackEnd/pull/65)와 [원천 테스트 데이터 PR #4](https://github.com/kosa11-final-project/dummy-data/pull/4)에서 구현했다. 동시 실행을 막는 방법은 두 번째 글로 넘기고, 이 글은 **버튼을 누른 뒤 원천 한 행이 정식 재고와 위험 상태가 되기까지**의 순서와 판단 기준에 집중한다.

## 먼저 결론: 한 번의 동기화가 만드는 결과

네 원천 테이블은 물리적으로 병합하지 않는다. 이 글에서 말하는 “합친다”는 출처별 원본을 보존하면서 검증을 통과한 업무 사실만 정식 상품·SKU·LOT·재고 관계에 반영한다는 뜻이다.

| 버튼 이후 순서 | 이 단계에서 결정하는 것 |
| --- | --- |
| `접수` → `연결 사전 검사` | 실행 기록을 만들고 모든 활성 원천 행에 `MAPPED` 연결이 있는지, SKU·창고·재고 잔액 식별자가 채워졌는지 확인한다. |
| `변경 후보 읽기` → `공통 형식화` | 마지막 성공 지문과 달라진 행을 최대 500행씩 읽어 같은 자료형과 업무 용어로 바꾼다. |
| `의미 검증` → `정식 값 비교` | 음수·필수값 누락·파싱할 수 없는 날짜·변경 후보 간 충돌을 막고, 실제 정식 값이 달라진 대상만 남긴다. |
| `정식 재고 반영` → `위험 상태 산출` | 상품·SKU·가격·정책·LOT·재고를 갱신하고, 수요예측·안전재고·LOT 규칙으로 위험 등급과 이유를 만든다. |
| `하나의 핵심 커밋` → `후속 스냅샷` | 정식 재고·처리 지문·위험 판정을 함께 확정한 뒤 대시보드·통계 작업은 별도로 이어 간다. |

핵심 트랜잭션은 정식 재고와 위험 판정을 같은 결과로 확정한다. 재고만 새 값이고 위험 이유는 이전 값인 상태를 만들지 않는다. 정규화가 끝난 뒤의 조회 성능과 동시 실행 제어는 [두 번째 글](/blog/integrated-inventory-sync-end-to-end-architecture)에서 이어서 설명한다.

![오프라인·이커머스·그리팅·물류센터 원천이 공통 형식과 검증을 거쳐 통합재고가 되는 흐름](/images/blog/integrated-inventory-source-to-canonical-ai.png)

*생성 이미지 · “원천 보존 → 공통 형식 → 검증·매핑 → 통합재고”라는 큰 경계를 먼저 보여 준다. 실제 컬럼 매핑과 실패 조건은 아래 표와 코드가 기준이다.*

### 문제 상황에서 기술 선택까지 이어진 이유

| 문제 상황 | 선택한 기술·설계 | 왜 이 경계가 필요한가 |
| --- | --- | --- |
| 원천마다 상품·수량·상태의 이름과 단위가 다름 | MyBatis SQL projection + 원천별 어댑터 + 공통 record | 이후 위험 판정과 목록이 원천별 예외를 반복하지 않게 함 |
| 이름이 비슷한 상품을 잘못 연결할 수 있음 | `MAPPED` row map과 안정적인 내부 ID | 자동 문자열 매칭보다 느리지만 잘못된 재고 덮어쓰기를 막음 |
| 같은 값이 계속 들어와도 매번 전체를 쓰면 부담이 커짐 | SHA-256 내용 지문 + 정식 값 최종 비교 | 변경 후보를 줄이되 지문만으로 변경 없음을 단정하지 않음 |
| 일부 원천만 반영되면 서비스가 서로 다른 시점을 보게 됨 | 사전 연결 검증, 의미 검증, 핵심 트랜잭션 | 오류를 조용히 건너뛰지 않고 전체 시도의 경계를 분명히 함 |
| 정식 재고만 바뀌고 위험 이유가 이전 값으로 남을 수 있음 | `RiskRuleEngine` + 같은 핵심 트랜잭션의 위험 결과 저장 | 재고 수량·위험 등급·판정 이유·규칙 버전을 한 실행 결과로 묶음 |

## 이 글에서 답하는 질문

- 왜 네 원천 테이블을 하나로 합치지 않았는가?
- 서로 다른 컬럼명과 상태값은 어느 단계에서 같은 의미로 바꾸는가?
- 원천의 한 행이 정식 상품, 판매·재고 관리 단위인 SKU, 같은 조건으로 생산·입고된 묶음인 LOT, 재고 중 무엇과 연결되는지 어떻게 아는가?
- 두 원천이 같은 값을 서로 다르게 주장하면 어느 쪽을 믿는가?
- 내용 지문인 해시만 같으면 정말 변경이 없다고 볼 수 있는가?
- 한 번에 500건씩 처리한다는 말과 전체 트랜잭션은 어떤 관계인가?
- 초기 데이터 3만여 건이 실제 업무 관계를 깨뜨리지 않았는지 어떻게 확인했는가?

## 전체 흐름부터 한눈에 보기

**원천별 현재 데이터 → 전체 연결 상태 사전 검사 → 지문이 다른 변경 후보 선별 → 후보를 공통 의미로 번역·검증 → 정식 값과 최종 비교 → 정식 업무 데이터 갱신 → 위험 판정 저장**

| 단계 | 하는 일 | 지키려는 것 |
| --- | --- | --- |
| 원천 보존 | 네 시스템의 현재 재고를 각자의 테이블에 유지한다. | 출처와 원천별 계약을 잃지 않는다. |
| 연결 사전 검사 | 모든 활성 원천 행의 `MAPPED` 연결, SKU·창고·재고 잔액 식별자, 원천 행 존재 여부를 확인한다. | 변경 여부와 무관하게 빠진 연결을 먼저 찾는다. |
| 변경 선별 | 데이터베이스가 마지막 성공 때와 지문이 다른 원천 행만 후보로 고른다. | 애플리케이션에 불필요한 전체 값을 올리지 않는다. |
| 후보 번역 | 후보의 컬럼명, 날짜, 상태, 수량을 같은 업무 의미와 자료형으로 바꾼다. | 이후 단계가 원천별 표현을 알지 않아도 된다. |
| 의미 검증 | 후보의 잘못된 수량과 필수값, 같은 실행의 변경 후보가 동일 대상을 향할 때의 값 충돌을 찾는다. | 일부만 조용히 반영되는 것을 막는다. |
| 최종 비교 | 후보와 정식 업무 데이터의 실제 값이 다른지 확인한다. | 지문은 달라도 정식 값은 같은 불필요한 쓰기를 거른다. |
| 정식 반영 | 이미 연결된 상품·SKU·가격·원가·LOT·정책·재고 중 값이 달라진 행을 갱신한다. | 서비스 전체가 같은 정식 데이터를 보게 한다. |
| 위험 판정 | 실제 변경의 영향을 받는 범위를 다시 평가하고 결과를 저장한다. | 재고 값과 위험 설명이 같은 실행 결과에 속하게 한다. |

이 구조의 핵심은 “네 테이블을 하나로 합친다”가 아니다. **원천은 원천대로 남기고, 서비스가 사용하는 의미와 책임만 한곳에서 통일한다**는 데 있다.

## 왜 네 원천 테이블을 그대로 두었나

처음 생각할 수 있는 방법은 네 원천을 하나의 넓은 테이블에 넣는 것이다. 조회는 단순해 보이지만 곧 문제가 생긴다.

- 오프라인에만 있는 매장 정보와 물류센터에만 있는 물리 LOT 정보가 한 테이블에 섞인다.
- 특정 원천에만 필요한 컬럼 때문에 빈 값이 많아진다.
- 한 원천의 계약 변경이 공용 테이블 전체의 변경으로 번진다.
- 원래 어느 시스템이 제공한 값인지 추적하기 어려워진다.
- 원천 고유의 제약과 적재 주기를 하나의 규칙으로 억지로 맞추게 된다.

반대로 기능마다 네 원천을 직접 조회하면 원천별 예외가 여러 서비스에 복제된다. 위험 판정과 대시보드가 서로 다른 번역 규칙을 쓰는 순간 같은 재고를 보고도 다른 숫자를 만들 수 있다.

현재 구조는 두 극단 사이를 택했다.

1. 원천 테이블은 각자의 구조와 출처를 보존한다.
2. 동기화할 때만 공통 재고 의미로 읽는다.
3. 검증을 통과한 결과를 기존 정식 업무 테이블에 반영한다.
4. 나머지 기능은 원천이 아니라 정식 업무 데이터를 조회한다.

이 방식은 원천 차이를 없애지 않는다. 차이를 다루는 장소를 동기화 경계로 한정한다.

## 데이터의 수명과 책임을 나누었다

통합 과정에는 서로 수명이 다른 데이터가 함께 등장한다.

| 데이터 | 역할 | 수명과 책임 |
| --- | --- | --- |
| 원천 현재 데이터 | 각 시스템이 지금 주장하는 재고 상태 | 원천별 계약을 보존하고 변경 사실을 제공한다. |
| 원천 연결표 | 원천 행과 기존 정식 식별자의 관계 | 초기 정확 매핑 또는 수동 승인으로 등록된 연결 방식과 상태를 보존한다. |
| 실행 중 공통 기록 | 네 원천을 같은 의미로 읽은 작업용 데이터 | 한 번의 동기화 동안만 메모리에 존재한다. |
| 정식 업무 데이터 | 상품·SKU·가격·원가·LOT·정책·재고 | 화면과 업무 기능이 신뢰하는 현재 상태다. |
| 실행·원천 상태 | 어느 버전을 언제 처리했는지 기록 | 변경 감지, 감사, 복구 판단에 사용한다. |
| 테스트 생성물 | 개발 환경의 재현 가능한 원천 데이터 | 운영 동기화와 분리해 테스트 기준을 만든다. |

작업용 공통 기록을 별도 영구 테이블로 만들지 않은 이유는 현재 규모에서는 변환 후 바로 검증하고 반영하는 편이 단순했기 때문이다. 대신 변경 후보 전체를 메모리에 모으므로 최대 10만 건의 상한이 있다. 더 큰 규모나 여러 단계의 재처리가 필요해지면 임시 적재 테이블을 두는 편이 낫다.

## 공통 형식은 어디에서 만들어지는가

지문이 달라 변경 후보가 된 원천 행은 데이터베이스에서 읽어 오는 순간 공통 형식으로 바꾼다. 이 변환은 데이터베이스에 보내는 조회 문장인 SQL이 맡는다. 서로 다른 컬럼을 같은 이름과 자료형으로 조회하고, 날짜 문자열과 판매 가능 여부 같은 표현도 공통 의미로 맞춘다.

그 결과 이후 단계는 원천 이름을 묻지 않고 다음과 같은 질문만 하면 된다.

- 어떤 상품과 SKU인가?
- 어느 창고 또는 판매처의 재고인가?
- 가용 수량과 예약 수량은 얼마인가?
- 가격과 원가는 어떤 통화와 단위인가?
- LOT의 입고일과 유통기한은 언제인가?
- 이 값의 출처와 원천 버전은 무엇인가?

![서로 다른 원천 컬럼을 공통 재고 의미로 번역하고 값의 의미를 확인하는 과정](/images/blog/inventory-source-projection-ai.png)

*생성 이미지 · 컬럼 이름을 그대로 합치는 대신 “같은 의미로 번역 → 값 검증 → 공통 재고 의미”의 순서를 둔 이유를 보여 준다. 이미지의 짧은 라벨보다 실제 매퍼의 자료형·필수값 검증이 우선이다.*

자바 쪽 어댑터는 원천 데이터와 공통 처리 과정 사이를 잇는 연결부다. 모든 변환을 직접 맡지 않고, 넘어온 기록이 해당 원천 유형과 맞는지 확인한 뒤 공통 작업 공간으로 전달한다. 이 책임을 명확히 해야 “어댑터 하나만 추가하면 새 원천도 끝난다”는 잘못된 기대를 피할 수 있다.

## 검증은 두 번에 나누어 한다

형식만 같다고 안전한 데이터가 되는 것은 아니다. 검증은 서로 다른 문제를 찾기 위해 두 단계로 나뉜다.

### 1. 원천과 연결 정보의 사전 검증

원천을 읽기 전에 다음을 확인한다.

- 활성 원천 행마다 `MAPPED` 상태의 연결이 있는가?
- 연결표에 SKU·창고·재고 잔액을 가리키는 필수 식별자가 있는가?
- 연결된 원천 행이 실제로 존재하는가?
- 하나의 정식 재고 잔액에 여러 원천 행이 중복 연결되어 있지 않은가?

이 검사는 잘못된 연결을 일찍 발견해 많은 데이터를 읽은 뒤 실패하는 일을 줄인다. 다만 데이터베이스에는 남아 있지만 시스템에서는 삭제된 것으로 취급하는 대상까지 사전에 모두 찾아내지는 못한다. 반영 단계는 활성 대상만 갱신하므로, 운영 검증을 강화할 때는 이런 논리 삭제 상태도 따로 확인해야 한다.

### 2. 공통 기록의 의미 검증

공통 형식으로 읽은 뒤에는 다음을 확인한다.

- 상품·SKU·LOT·분류처럼 반영에 필요한 값이 빠지지 않았는가?
- 가용 수량, 예약 수량, 안전재고가 허용 범위를 벗어나지 않았는가?
- 날짜 문자열을 정해진 형식으로 읽을 수 있고 공통 기록의 필수값이 채워졌는가?
- 같은 실행에서 읽힌 변경 후보가 같은 상품이나 SKU를 서로 다른 값으로 주장하지 않는가?

오류가 있는 행만 건너뛰지 않고 전체 동기화를 중단한다. 정식 재고는 여러 원천이 함께 만든 한 시점의 결과다. 일부만 반영하면 어느 부분까지 신뢰할 수 있는지 설명하기 어렵다.

## 원천 행과 정식 데이터는 이름이 아니라 연결표로 잇는다

서로 다른 시스템의 상품 이름이 비슷하다고 자동으로 같은 상품이라고 판단하지 않았다. 원천 행마다 기존 정식 상품·SKU·창고·LOT·재고 식별자를 명시적으로 연결하는 표를 둔다.

원천 행을 구분하는 키는 대체로 **원천 종류, 위치, 원천 SKU, LOT**처럼 그 시스템 안에서 한 행을 안정적으로 찾을 수 있는 요소를 조합한다. 이 조합의 일부가 바뀌면 같은 재고의 수정이 아니라 새로운 원천 행으로 보일 수 있다. 따라서 원천 키를 고를 때는 사람이 읽기 좋은 값보다 시간이 지나도 바뀌지 않는 식별자를 우선해야 한다.

명시적 연결은 이름이 비슷한 대상을 잘못 엮는 일을 막고, 어느 원천 행이 어떤 정식 데이터에 반영됐는지 추적하게 해준다. 연결 방식은 초기 정확 매핑인 `INITIAL_EXACT`와 수동 승인인 `APPROVED_MANUAL`, 상태는 `MAPPED`·`INVALID`·`REVIEW_REQUIRED`로 구분한다. 동기화에는 `MAPPED`만 사용하며 나머지는 사전 검사에서 실패한다.

대신 신규 상품과 원천 행을 자동으로 만들지는 않는다. 새 대상은 먼저 정식 데이터와 연결 관계를 준비해야 한다. 자동 확장성보다 통제와 추적 가능성을 선택한 결과다.

### 분류 연결에는 아직 예외가 있다

상품, SKU, 창고, LOT, 재고는 안정적인 식별자를 중심으로 연결한다. 그러나 상품 분류는 현재 원천의 분류 이름과 정식 분류 이름을 **정확히 비교**해 찾는다. 이름이 조금만 달라도 연결되지 않고, 분류 이름 자체의 유일성도 데이터베이스 제약으로 완전히 보장하지 않는다.

현재 테스트 데이터에서는 이 계약을 통제할 수 있어 동작하지만, 원천이 늘거나 운영자가 이름을 바꾸는 환경에서는 취약하다. 장기적으로는 분류도 별도 코드 또는 명시적 연결표로 바꾸는 것이 안전하다.

## 여러 원천이 같은 값을 주장할 때의 규칙

공통 형식으로 바꿨다고 값의 충돌이 사라지는 것은 아니다. 오프라인과 이커머스가 같은 SKU의 가격을 서로 다르게 보내거나, 여러 원천이 같은 상품 속성을 다르게 주장할 수 있다.

현재는 상품, SKU, 가격, 원가, 재고 정책처럼 여러 원천이 제공할 수 있는 값이 **같은 실행의 변경 후보로 함께 읽혀 같은 대상에 모이면** 서로 일치해야 한다. 값이 다르면 마지막에 읽은 값을 조용히 덮어쓰지 않고 전체 시도를 실패시킨다.

물리적인 LOT 정보는 변경 후보가 같은 실행에 함께 들어온 경우 물류센터 원천을 우선한다. 이때 실제 입고일, 소비기한, 물류 상태는 물류센터 후보가 덮는다. 읽기 순서가 아니라 사실의 책임 주체로 우선순위를 정했다.

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| 마지막 값 우선 | 구현이 단순하다. | 읽는 순서에 따라 결과가 달라지고 충돌이 숨는다. |
| 원천별 우선순위 | 자동으로 결과를 만들기 쉽다. | 속성마다 권위가 다르면 규칙이 복잡해진다. |
| 일치 요구 후 실패 | 불일치를 즉시 드러내고 잘못된 반영을 막는다. | 작은 원천 오류도 전체 동기화를 멈출 수 있다. |
| 속성별 권위 지정 | 물리 LOT처럼 책임이 분명한 사실에 적합하다. | 권위 모델을 문서와 코드에서 계속 관리해야 한다. |

이 충돌 검사는 변경 후보 메모리 버퍼 안에서만 작동한다. 한 원천만 바뀌고 같은 대상을 가리키는 다른 원천의 지문이 그대로라면, 변하지 않은 원천은 후보로 읽히지 않아 이번 비교에 참여하지 않는다. 따라서 “모든 현재 원천의 주장을 항상 대조한다”거나 “물류센터 값이 어떤 경우에도 우선한다”고 보장할 수는 없다. 공유 대상의 모든 현재 주장이나 권위 원천을 추가로 읽어 검증하는 보강이 남아 있다.

## 내용 지문과 원천 버전은 서로 다른 문제를 푼다

많은 원천 행을 매번 정식 데이터와 전부 비교하면 비용이 커진다. 그래서 각 원천 행에는 중요한 값을 정해진 순서로 요약한 **내용 지문**, 즉 해시가 있다. 현재 지문과 마지막 성공 때 처리한 지문이 다를 때만 변경 후보로 읽는다.

여기서 줄어드는 것은 애플리케이션이 모든 원천의 실제 값을 메모리에 올리고 정식 값과 대조하는 비용이다. 데이터베이스가 지문 조건을 평가하고 후보를 찾는 조회 비용까지 없어지는 것은 아니다. 실제 실행 계획과 인덱스 효과는 운영 데이터로 따로 측정해야 한다.

하지만 해시만으로 정식 데이터를 덮어쓰지는 않는다.

1. 해시는 바뀐 가능성이 있는 원천 행을 빠르게 고른다.
2. 공통 작업 공간에서 같은 대상을 향한 값의 충돌을 검사한다.
3. 정식 데이터와 실제 값을 비교해 달라진 행만 갱신한다.
4. 전체 반영이 성공한 뒤에만 이번 지문을 처리 완료로 기록한다.

해시는 바뀌었을 가능성이 있는 행을 추리는 1차 기준일 뿐이다. 지문이 다른 후보는 실제 정식 값까지 비교한다. 원천의 부가 정보만 달라지고 정식 재고 값은 같다면 불필요한 쓰기를 피한다.

반대로 현재 지문과 마지막 성공 지문이 같다고 판단된 행은 후보로 읽지 않는다. 이 때문에 해시 충돌이 일어나거나 지문 생성 규칙에서 중요한 필드를 빠뜨리면 실제 변경도 놓칠 수 있다. 마지막 값 비교는 이미 후보로 들어온 행에만 적용되므로 이 경우까지 막아 주지는 못한다.

SHA-256이라는 알고리즘만 고른다고 끝나지 않는다. 어떤 필드를 어떤 순서와 형식으로 묶는지, 빈 값과 숫자·날짜를 어떻게 정규화하는지까지 하나의 계약으로 관리해야 한다. 생성기와 서버에 대표 입력의 예상 지문을 고정해 두고 전체 데이터의 검증값도 함께 비교한다.

![같은 원천 값은 건너뛰고 바뀐 값만 변경 후보로 보내는 해시 비교](/images/blog/inventory-hash-noop-ai.png)

*생성 이미지 · 해시는 “변경 후보를 고르는 빠른 표지”이지 최종 반영 여부를 결정하는 업무 판정이 아니다. 후보가 된 뒤에는 공통 형식 검증과 정식 값 비교를 다시 거친다.*

원천 버전은 다른 문제를 푼다. 동기화를 시작할 때 네 원천의 버전을 기억하고, 반영 직전에 잠깐 잠근 뒤 다시 비교한다. 읽는 동안 원천이 바뀌었다면 앞부분과 뒷부분이 서로 다른 시점인 결과를 만들지 않고 전체 시도를 중단한다.

이 선택은 긴 읽기 동안 원천을 잠그지 않아 다른 업무를 덜 막는 대신, 원천 변경이 잦을 때 이번 작업을 버리고 처음부터 다시 읽어야 한다는 비용을 가진다.

## 500건씩 처리하지만 500건마다 확정하지 않는다

원천은 오프라인, 이커머스, 그리팅, 물류센터 순서로 한 번에 최대 500건씩 읽는다. 이 순서는 진행 상황을 예측하기 위한 처리 순서일 뿐, 뒤에서 읽은 원천이 앞의 값을 무조건 덮어쓴다는 뜻은 아니다. 값의 충돌은 앞에서 설명한 일치 조건과 물리 LOT의 권위 규칙으로 판단한다.

마지막으로 읽은 안정적인 원천 키 다음부터 이어 읽기 때문에 데이터가 많아도 한 번의 조회가 지나치게 커지지 않는다. 정식 데이터 쓰기와 위험 판정용 조회도 최대 500건 규모의 묶음으로 나눈다.

여기서 500은 데이터베이스와 한 번에 주고받는 양이다. Spring Batch가 500건마다 독립된 작업 조각을 만들거나 저장을 확정한다는 뜻이 아니다. 현재 Spring Batch 단계는 하나의 업무 작업자를 호출하고, 페이지 읽기와 묶음 쓰기는 업무 코드가 직접 관리한다.

변경 후보 전체는 중복과 충돌을 검사하기 위해 한 번의 실행 메모리에 모인다. 최대 10만 건을 넘으면 무리하게 진행하지 않고 실패시킨다. 정식 재고, 처리 완료 지문, 원천 상태, 위험 판정은 하나의 핵심 트랜잭션에서 함께 확정되므로 마지막에 오류가 나면 모두 되돌아간다.

이 구조는 전체가 성공하거나 전체가 되돌아가는 원자성을 지키며, 결과가 만들어진 과정도 설명하기 쉽다. 다만 변경량이 커지면 메모리 사용량, 데이터베이스가 되돌리려고 보관하는 정보, 트랜잭션 시간이 함께 늘어난다. 규모가 더 커지면 임시 적재 → 집합 검증 → 짧은 최종 교체처럼 단계를 나누는 설계를 검토해야 한다.

## 재고가 바뀌면 위험 상태를 어떻게 다시 계산했나

정식 재고만 반영하면 화면은 “왜 위험한가”를 설명하지 못한다. 재고가 적다는 사실만 보면 판매 속도가 빠른 상품과 거의 팔리지 않는 상품을 같은 위험으로 오해할 수 있고, 수량이 충분해도 소비기한이 임박한 LOT는 놓칠 수 있다. 실제로 값이 달라진 `SKU × 판매처` 범위만 다시 읽어 서버 규칙 `v1.3.0`을 적용했다. 판매처에 귀속되지 않은 센터 재고는 특정 판매처의 예측을 억지로 붙이지 않고 `UNASSIGNED` 범위로 남겼다. 위험 판정과 일괄 원천 조정, 스냅샷 중복 생성 오류 수정은 [Backend 후속 PR #97](https://github.com/kosa11-final-project/BackEnd/pull/97)에 반영했다.

판정 입력은 네 가지다.

| 입력 | 서버가 사용하는 값 | 맡은 역할 |
| --- | --- | --- |
| 정식 재고 | 가용 수량 `on_hand_qty` | 현재 판매에 사용할 수 있는 시작 수량 |
| 수요예측 | D+7·D+30 누적 예측량 | 7일 뒤 안전재고 미달과 30일 내 부족 예상 계산 |
| 재고 정책 | 안전재고 수량 | 운영자가 허용한 최소 완충선 |
| LOT | 소비기한·판매중지일·입고일·LOT 수량 | 소비기한·판매중지 위험 판정과 최대 보유일수 설명값 계산 |

예약 수량은 목록과 상세에 따로 표시한다. 위험 계산에서는 가용 수량에서 다시 빼지 않았다. 현재 데이터 계약의 `on_hand_qty`가 이미 예약을 제외한 가용 수량이어서 같은 값을 두 번 차감하면 위험도를 과장한다.

```text
D+7 예상잔고 = max(가용재고 - D+7 누적 예측량, 0)
D+30 부족량 = max(D+30 누적 예측량 - 가용재고, 0)
재고일수     = 가용재고 × 30 / D+30 누적 예측량
```

### 위험 등급은 가장 높은 사유 하나가 우선한다

서버 내부 등급은 `CRITICAL > WARNING > NORMAL > GOOD` 순서이고, API와 화면에서는 각각 `DANGER > CAUTION > NORMAL > SAFE`로 바꿔 제공한다.

| 화면 등급 | 대표 판정 조건 | 이 조건을 둔 이유 |
| --- | --- | --- |
| `DANGER` | 판매중지일 도래, 소비기한 만료·30일 이하, 가용재고 0, D+7 예상잔고가 안전재고 미만 | 지금 판매할 수 없거나 곧 운영 기준 아래로 내려가는 상황을 가장 먼저 알림 |
| `CAUTION` | D+30 재고일수가 14일 미만인 부족 예상, 현재 가용재고가 안전재고 미만, 소비기한 31~90일 | 즉시 중단 수준은 아니지만 발주·이동·소진 판단이 필요한 상황 |
| `NORMAL` | D+30 재고일수가 14일 이상 30일 미만인 보충 검토, 소비기한 91~180일, 수요예측 누락·무효 상태의 보수적 하한 | 정상 판매가 가능해도 중기 보충이나 데이터 보완이 필요한 상황 |
| `SAFE` | 유효한 D+7·D+30 예측과 필수 검증을 통과했고 위 위험 사유가 없음 | 실제 규칙을 통과한 상태이며 “데이터 없음”과 구분됨 |

예측이 없거나 D+7·D+30 값이 누락·음수·역전되어 사용할 수 없으면 예측 기반 규칙만 제외한다. 재고·안전재고·LOT로 판단 가능한 위험은 계속 계산한다. 다만 현재 `v1.3.0`은 `FORECAST_UNAVAILABLE` 또는 `FORECAST_INVALID` 사유를 `NORMAL` 하한으로 기록한다. 그래서 서버 룰상 위험이 없더라도 예측이 없는 범위는 `SAFE`로 확정하지 않고 `NORMAL`로 표시하며, 가용재고 부족이나 소비기한 임박 같은 위험이 있으면 `CAUTION`·`DANGER`로 올라간다. 14일보다 오래된 예측도 값 자체가 유효하면 사용하되, 오래된 예측을 사용했다는 사실을 판정 이유에 남긴다. 안전재고 정책이 없으면 안전재고 규칙만 제외한다. 음수 재고·음수 안전재고·음수 LOT 수량은 정상 등급으로 덮지 않고 동기화 자체를 실패시킨다.

예를 들어 D+30 예측이 30개일 때 가용재고가 24개면 재고일수는 `24 × 30 ÷ 30 = 24일`이므로 `NORMAL`이다. 가용재고가 12개라서 재고일수가 12일이 되면 `CAUTION`으로 올라간다. 반대로 예측 자체가 없으면 재고일수를 계산하지 않고, 위의 보수적 `NORMAL` 하한을 적용한다.

위험 판정기는 가용 수량이 누락되면 “안전하다고 판정할 근거가 없다”고 보고 0으로 간주해 보수적으로 `DANGER` 사유를 만든다. 데이터가 없다는 이유로 `SAFE`가 되는 오류는 막지만, 원천 품질 오류가 실제 품절처럼 보일 수 있다는 비용은 남는다. 화면이 두 경우를 구분할 수 있도록 등급과 `reason_message`, 적용 규칙 버전, 안전재고 미달 여부, 재고일수, 소비기한·보유일수도 함께 저장했다.

## 왜 정식 재고와 위험 판정을 하나의 트랜잭션으로 묶었나

정식 재고가 100개에서 10개로 바뀌었는데 위험 등급이 이전 `SAFE`로 남으면 조회 속도가 아무리 빨라도 잘못된 정보를 보여 준다. 핵심 트랜잭션은 정식 재고, 마지막 처리 지문, 원천 상태, 위험 판정을 함께 확정하며 도중에 하나라도 실패하면 모두 되돌린다.

영향 범위가 있는데 위험 판정용 스냅샷이 하나도 만들어지지 않으면 정식 재고 반영까지 되돌린다. 여러 영향 범위 중 일부만 누락된 경우를 일대일로 대조하는 더 강한 완전성 검사는 아직 남아 있다.

대시보드와 통계 스냅샷은 핵심 트랜잭션이 커밋된 뒤 별도 작업으로 생성하도록 구성했다. 스냅샷 집계 실패 때문에 이미 검증된 정식 재고까지 되돌리면 핵심 데이터의 가용성이 부가 기능에 끌려간다. V27 migration이 적용된 환경에서는 핵심 트랜잭션이 후속 task 행을 함께 기록하고 실제 집계는 커밋 뒤 실행한다. 개발 환경에서 원천 33,358건을 다시 동기화해 읽기·매핑·반영 33,358건, 오류 0건과 두 스냅샷 작업 성공을 확인했다. 실행·복구 흐름은 [두 번째 글](/blog/integrated-inventory-sync-end-to-end-architecture)에서 다룬다.

## 정식 업무 모델의 관계는 유지한다

통합 결과를 하나의 넓은 재고 테이블에 복사하지 않았다. 서비스가 이미 사용하던 관계를 유지한 채 필요한 값만 갱신한다.

- 상품은 사람이 인식하는 기본 속성과 분류를 가진다.
- SKU는 실제 판매·재고 관리 단위다.
- 가격과 원가는 SKU와 판매처 또는 적용 조건에 따라 달라질 수 있다.
- LOT는 입고일과 유통기한 같은 물리 재고의 생애를 가진다.
- 재고 정책은 안전재고 같은 운영 기준을 가진다.
- 재고 잔액은 SKU, 위치, LOT 관계 위에서 가용 수량과 예약 수량을 가진다.

원천의 편의를 위해 이 관계를 한 행에 납작하게 만들면, 같은 상품 설명과 가격이 재고 행마다 반복되고 서로 다른 시점에 갱신될 수 있다. 현재 설계는 원천을 읽을 때는 공통 기록 하나로 다루되, 저장할 때는 다시 각 업무 책임에 맞는 정식 테이블로 반영한다.

## 초기 데이터는 정식 스냅샷에서 역으로 만들었다

정규화 설계를 검증하려면 단순히 행 수만 많은 무작위 데이터로는 부족하다. 원천과 정식 데이터가 같은 업무 관계를 가리켜야 하고, 첫 동기화는 아무것도 바꾸지 않아야 한다.

그래서 개발용 초기 데이터는 다음 순서로 만든다.

1. 승인된 정식 상품·SKU·가격·LOT·정책·재고 스냅샷을 읽는다.
2. 같은 업무 사실을 네 원천의 서로 다른 표현으로 역변환한다.
3. 원천 행과 정식 식별자를 잇는 연결 정보를 함께 만든다.
4. 행 수와 내용 지문, 주요 관계와 입력 전체를 요약한 검증값을 고정된 기준과 비교한다.
5. 첫 동기화를 실행해 정식 데이터의 변경 건수가 0인지 확인한다.

2026년 8월 24일 현재 승인된 테스트 기준은 네 원천을 합쳐 **33,358행**이다. 이 숫자는 처리 성능을 자랑하기 위한 수치가 아니라, 생성 규칙이 몰래 행을 빠뜨리거나 중복시키지 않았는지 확인하고 이후 코드 변경에도 같은 결과가 나오는지 비교하는 회귀 기준이다. 정식 스냅샷을 네 형식으로 역변환한 자료이므로 실제 운영의 결측, 미승인 연결, 이상 분포와 순간 부하까지 닮았다는 뜻은 아니다.

첫 실행에서 변경이 0이라는 사실도 “동기화가 아무 일도 하지 않았다”는 뜻이 아니다. 연결, 번역, 검증, 해시 비교가 모두 통과했고, 원천이 표현한 업무 사실과 정식 스냅샷이 같았다는 뜻이다.

생성기는 운영 동기화 코드와 분리했다. 초기 데이터를 만들기 위해 운영 서비스가 켜져 있어야 하거나 실제 데이터베이스를 직접 수정하게 만들면 재현성과 안전성이 떨어지기 때문이다.

## 시연용 재고 차감은 별도 경로로 격리했다

화면에서 원천 재고가 바뀌고 다음 동기화에 반영되는 모습을 보여 주기 위해 시연용 차감 기능이 있다. 이 기능은 정식 동기화의 번역 규칙과 섞지 않았다.

차감할 때는 다음 원칙을 지킨다.

- 같은 원천 상태를 동시에 바꾸지 못하도록 짧게 잠그되 최대 5초만 기다린다.
- 수량 변경, 원천 버전 증가, 감사 이력 기록, 내용 지문 갱신을 같은 시연 작업으로 묶는다.
- 잠금 시간 초과는 일반 서버 오류로 숨기지 않고 다른 작업과 충돌했다는 응답으로 바꾼다.

시연용 차감 경로와 초기 데이터 생성기는 어떤 값을 어떤 순서로 지문에 넣는지 정한 규칙이 완전히 같지는 않다. 시연 경로가 중요한 필드의 변경을 지문에 반영하지 못하면 그 행이 변경 후보에서 빠질 수 있으므로, 실제 값 비교만으로 이 차이를 보완할 수 없다. 현재 시연 범위에서는 사용하는 필드가 통제되어 있지만, 장기적으로는 생성기·서버·시연 경로가 하나의 지문 계약을 쓰도록 맞춰야 한다.

## 설계 선택과 트레이드오프

| 선택 | 얻은 것 | 치른 비용 |
| --- | --- | --- |
| 네 원천 테이블 유지 | 출처와 원천별 계약을 보존한다. | 원천별 조회와 번역 규칙을 관리해야 한다. |
| 읽기 시점의 공통 번역 | 이후 기능에서 원천별 분기를 제거한다. | SQL 조회가 길어질 수 있고 변경 시 회귀 검증이 필요하다. |
| 명시적 연결표 | 잘못된 자동 연결을 막고 추적할 수 있다. | 신규 원천 행을 먼저 승인·연결해야 한다. |
| 충돌 시 전체 실패 | 불일치를 숨기지 않고 정식 데이터의 정합성을 지킨다. | 작은 원천 오류가 전체 동기화를 막을 수 있다. |
| 해시 기반 변경 후보 | 불필요한 비교와 쓰기를 줄인다. | 지문 계약과 마지막 성공 상태를 관리해야 한다. |
| 원천 버전 재검사 | 서로 다른 시점의 원천을 섞지 않는다. | 읽는 동안 변경되면 처음부터 다시 실행해야 한다. |
| 메모리 작업 공간 | 별도 임시 적재 테이블 없이 구조가 단순하다. | 10만 건 상한과 전체 후보 메모리 사용이 있다. |
| 핵심 반영 하나의 트랜잭션 | 정식 재고·지문·위험 결과가 함께 성공하거나 실패한다. | 대량 변경 시 트랜잭션 비용이 커진다. |

## 문제 해결 성과와 아직 측정하지 않은 것

코드와 테스트로 확인한 성과는 데이터가 잘못 반영되는 경계를 막은 것이다. 운영 응답 시간은 측정하지 않았으므로 수치로 제시하지 않는다.

| 확인한 결과 | 확인 방법 | 여기서 말할 수 없는 것 |
| --- | --- | --- |
| 네 원천 33,358행과 같은 수의 연결 정보가 반복 생성됨 | 고정된 행 수·관계·내용 검증값을 계약 테스트에서 비교 | 실제 운영의 결측·편향·순간 부하까지 재현했다는 뜻은 아님 |
| 초기 원천을 다시 통합했을 때 정식 스냅샷 변경이 0건 | 정식 데이터에서 원천을 역생성하고 첫 동기화 결과 확인 | 변경량이 큰 운영 동기화의 처리 시간을 측정한 것은 아님 |
| 같은 실행의 변경 후보 충돌·음수 수량·원천 버전 변경이 조용히 반영되지 않음 | 검증기·규칙 엔진·동기화 실패 경계 테스트 | 후보로 읽히지 않은 다른 원천의 현재 값까지 항상 대조하는 것은 아님 |
| 재고와 위험 등급·이유·규칙 버전이 같은 실행 결과로 저장됨 | 핵심 writer와 rollback 경계 테스트 | 여러 영향 범위의 부분 누락을 모두 탐지하는 완전성 검사는 남음 |
| 변경 없는 원천은 후보에서 제외되고, 후보도 정식 값과 다시 비교됨 | 내용 지문과 changed-only 반영 계약 테스트 | 실제 Oracle 실행계획과 응답 시간 개선 폭은 별도 측정이 필요함 |

## 현재 구조가 의도적으로 하지 않는 일

- 비슷한 상품명이나 분류명을 보고 자동으로 연결하지 않는다.
- 매핑이 없는 새 상품·SKU·창고를 동기화 중 자동 생성하지 않는다.
- 원천에서 사라진 행을 정식 데이터에서 자동 삭제하지 않는다.
- 과거 모든 원천 이력을 정식 데이터에 다시 적재하지 않는다. 현재 원천 상태를 기준으로 동기화한다.
- 500건마다 부분 성공을 남기지 않는다. 핵심 반영은 전체가 함께 성공하거나 실패한다.
- 10만 건을 넘는 변경 후보를 무한히 메모리에 쌓지 않는다.

이 항목들은 빠진 기능 목록이라기보다 현재 설계가 지키는 책임 경계다. 예를 들어 자동 상품 생성은 편리하지만, 잘못된 상품이 정식 카탈로그에 들어갔을 때 누가 승인했는지 설명하기 어렵다. 필요해질 때는 별도의 검토·승인 흐름으로 추가하는 편이 안전하다.

## 한 행의 흐름을 사람의 말로 따라가 보기

물류센터가 특정 SKU의 한 LOT에 대해 가용 수량과 유통기한을 보냈다고 가정하자.

1. 원천을 읽기 전에 시스템은 모든 활성 행에 `MAPPED` 연결이 있는지, SKU·창고·재고 잔액 식별자가 채워졌는지 먼저 검사한다.
2. 데이터베이스는 마지막 성공 지문과 다른 물류센터 행만 변경 후보로 고른다.
3. 후보를 기존 정식 SKU·창고·LOT·재고 식별자와 연결하고, 물류센터 컬럼을 공통 가용 수량·예약 수량·입고일·유통기한·상태로 번역한다.
4. 수량·필수값·날짜 형식이 유효한지, 이번 실행에 함께 들어온 다른 변경 후보가 같은 정식 대상을 다른 값으로 주장하는지 검사한다.
5. 반영 직전 원천 버전이 그대로인지 다시 확인한다.
6. 정식 LOT와 재고 중 실제 값이 다른 부분만 갱신한다.
7. 영향받은 SKU·판매처의 가용재고, 수요예측, 안전재고, LOT를 읽고 가장 높은 위험 사유와 규칙 버전을 저장한다.
8. 모든 과정이 성공한 뒤에만 이번 내용 지문을 처리 완료로 기록한다.

코드 이름을 몰라도 이 흐름을 이해할 수 있다면 설계의 책임 경계가 제대로 드러난 것이다.

## 기술 용어를 다시 풀어보면

| 용어 | 이 글에서의 뜻 |
| --- | --- |
| 원천 데이터 | 오프라인·이커머스·그리팅·물류센터가 각자 보관하는 현재 재고 표현 |
| 표준화 | 서로 다른 컬럼명·자료형·상태값을 같은 업무 의미로 번역하는 과정 |
| 정식 데이터(canonical) | 조회와 업무 기능이 공통으로 신뢰하는 상품·SKU·LOT·재고 관계 |
| SKU | 옵션·용량까지 구분한 실제 판매 및 재고 관리 단위 |
| LOT | 같은 조건으로 생산되거나 입고되어 소비기한·입고일을 공유하는 묶음 |
| 연결표(row map) | 원천 한 행이 어느 정식 식별자를 가리키는지 기록하고 `MAPPED`·`INVALID`·`REVIEW_REQUIRED`로 관리하는 관계 |
| 내용 지문(hash) | 중요한 필드를 같은 순서로 요약해 변경 후보를 찾는 값 |
| 수요예측 | ML 파이프라인이 저장한 D+7·D+30 등의 누적 예상 수요량 |
| 서버 규칙 | 가용재고·예측·안전재고·LOT를 입력으로 위험 사유와 등급을 정하는 버전 관리된 기준 |
| 트랜잭션 | 정식 재고와 위험 판정이 함께 성공하거나 함께 되돌아가게 묶은 확정 경계 |

## 자주 묻는 질문

### 여기서 정규화는 데이터베이스 정규형을 뜻하나?

아니다. 이 글에서는 원천마다 다른 표현을 하나의 업무 의미로 맞추는 표준화 과정을 뜻한다. 저장 단계에서는 기존 관계형 업무 모델의 역할도 그대로 유지한다.

### 목록을 조회할 때마다 네 원천 테이블을 직접 합치나?

아니다. 원천 4종은 동기화 입력과 추적 근거로 보존한다. 운영 목록·전체 건수·상단 요약은 동기화가 만든 정식 재고와 저장된 위험 판정을 조회한다. 조회 경로와 종합 위험 필터는 두 번째 글에서 자세히 설명한다.

### 새 원천은 어댑터 하나만 추가하면 되나?

아니다. 원천 유형과 읽기 순서, 데이터베이스 스키마, 연결 검증, 공통 조회 번역, 초기 데이터 생성, 지문 계약, 회귀 테스트를 함께 추가해야 한다. 어댑터는 그중 원천 유형의 경계를 확인하는 한 부분이다.

### 왜 이름이 비슷한 상품을 자동으로 연결하지 않나?

상품명은 바뀔 수 있고 서로 다른 상품이 비슷한 이름을 가질 수 있다. 잘못된 자동 연결이 조용히 재고를 오염시키는 것보다, 명시적 연결이 없을 때 실패하고 검토하게 만드는 편을 택했다.

### 같은 대상을 가리키는 모든 원천 값을 항상 비교하나?

아니다. 현재 충돌 검사는 같은 실행에서 변경 후보로 읽힌 값끼리 수행한다. 지문이 바뀌지 않은 다른 원천은 후보 버퍼에 들어오지 않으므로 이번 비교에 참여하지 않는다. 모든 현재 원천의 주장과 권위 원천을 매번 대조하려면 공유 대상별 추가 조회가 필요하다.

### 해시가 같으면 실제 값 비교를 생략하나?

그렇다. 원천 지문과 마지막 성공 지문이 같으면 그 행은 변경 후보로 읽지 않는다. 지문이 다른 후보에 대해서만 정식 데이터와 실제 값을 비교해 달라진 값만 갱신한다. 그래서 지문에 포함할 필드와 정규화 규칙을 정확히 유지하는 것이 중요하다.

### 500건씩 읽는데 왜 메모리 상한이 필요한가?

한 번의 조회는 500건이지만, 같은 대상을 향한 충돌과 전체 원자성을 검증하려고 변경 후보 전체를 실행 메모리에 모으기 때문이다. 현재 상한은 10만 건이다.

### 첫 동기화의 변경 건수가 0이면 테스트가 약한 것 아닌가?

오히려 초기 기준에서는 중요한 검증이다. 서로 다른 원천 표현을 다시 공통 의미로 번역했을 때 원래 정식 스냅샷과 같아야 하기 때문이다. 이후 테스트에서는 실제 변경, 충돌, 잘못된 수량, 원천 버전 변경도 별도로 검증한다.

## 마무리

원천 통합에서 어려운 부분은 컬럼 이름 네 개를 하나로 바꾸는 일이 아니었다. **누가 어떤 사실을 책임지는지, 한 원천 행이 어느 정식 대상을 가리키는지, 값이 충돌하면 어디서 멈출지, 어느 시점의 데이터를 한 결과로 인정할지**를 정하는 일이었다.

현재 구조는 네 원천을 보존하면서도 서비스의 나머지 기능이 하나의 정식 재고 언어로 일하게 한다. 그 대가로 명시적 연결 운영, 전체 후보 메모리 사용, 충돌 시 전체 실패라는 비용을 감수한다. 이 제약은 숨겨진 구현 세부사항이 아니라 운영자가 알아야 할 설계 계약이다.
