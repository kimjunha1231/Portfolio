통합재고 화면의 동기화 버튼은 단순한 새로고침 버튼이 아니다. 버튼을 누르면 서버는 네 종류의 원천 데이터를 읽고, 서로 다른 표현을 하나의 형식으로 맞춘 뒤, 정식 재고와 위험 판정 결과를 함께 갱신한다. 도중에 같은 요청이 다시 들어오거나 서버가 멈추더라도 이전 작업이 새 결과를 덮어써서는 안 된다.

이 글은 특정 클래스 이름이나 설정값을 나열하기보다, **어떤 문제를 어떤 기술과 설계로 해결했는지**에 초점을 맞춘다. 예를 들어 “한 번에 500건을 처리한다”는 사실만 적는 대신, 그 숫자가 전체 작업량을 뜻하는지, 데이터베이스를 한 번에 읽고 쓰는 묶음의 크기를 뜻하는지, 실패 시 어디까지 되돌아가는지를 구분해 설명한다.

핵심은 데이터베이스가 실행권을 지키고, 백그라운드 작업이 원천 데이터를 나누어 읽어 정식 재고와 위험 판정을 함께 확정하는 데 있다. 대시보드와 통계는 그 뒤 별도로 만들며, 오래된 작업은 작업 세대를 확인해 쓰기를 막는다.

이 흐름은 제가 맡은 [Backend 동기화 PR #65](https://github.com/kosa11-final-project/BackEnd/pull/65)와 [안전성 보강 PR #83](https://github.com/kosa11-final-project/BackEnd/pull/83), [Frontend 실행 화면 PR #32](https://github.com/kosa11-final-project/FrontEnd/pull/32)와 [상태·복구 화면 보강 PR #40](https://github.com/kosa11-final-project/FrontEnd/pull/40)에 걸쳐 구현했다. 이 글에서는 네 번의 변경을 하나의 실행 흐름으로 연결해 설명한다.

## 먼저 보는 두 상태: 실행 상태와 조회 상태

동기화 버튼을 누른 뒤 화면에서 보이는 상태와, 그 결과를 재고 목록에서 읽는 상태는 같은 일이 아닙니다. 아래 순서를 먼저 잡아 두면 뒤의 비관적 락·배치·캐시 설명이 한 흐름으로 연결됩니다.

| 상태 | 실제 순서 | 화면/API에서 확인하는 기준 |
| --- | --- | --- |
| 실행 상태 | `QUEUED` 접수 → `RUNNING`의 `VALIDATING`·`READING`·`NORMALIZING`·`PUBLISHING` → `SUCCEEDED` | 정식 재고와 위험 판정이 확정되면 핵심 동기화 성공. 후속 스냅샷 준비 여부는 별도 필드로 확인 |
| 조회 상태 | 정식 재고 → 유효 범위 → SKU 종합 위험 집계 → `AND`/`OR` 후보 필터 → 페이지·건수·요약 → TanStack Query 캐시 갱신 | 목록과 상단 KPI가 같은 필터 연산자와 같은 종합 위험 값을 사용 |

현재 상태 확인은 SSE 스트림이 아니라 실행 상태 API 폴링입니다. 접수 대기 중에는 3초, 실행 중에는 10초, 핵심 반영 뒤 스냅샷을 기다릴 때는 처음 1분 동안 3초 간격을 사용합니다. 이 글에서 성능의 중심은 동기화 작업 자체를 무리하게 빠르게 만드는 것이 아니라, **반영이 끝난 정식 재고를 조회할 때 매번 원천을 다시 합치지 않고 필요한 행만 보내는 것**입니다.

![동기화 버튼이 원천별 실행과 정상 반영·오류 기록으로 이어지는 운영 흐름](/images/blog/inventory-sync-control-ai.png)

*생성 이미지 · 한 번의 실행 안에서 원천별 읽기·매핑·변경·오류를 기록하고 정식 반영으로 모으는 구조를 설명합니다. 실제 재시도·lease·fencing 규칙은 아래 본문과 DB task 계약이 기준입니다.*

### 문제 상황에서 기술 선택까지 이어진 이유

| 문제 상황 | 선택한 기술·설계 | 결과와 트레이드오프 |
| --- | --- | --- |
| 버튼 재클릭·재전송·다중 서버가 같은 실행을 시작할 수 있음 | client request id 멱등성 + 짧은 Oracle 비관적 락 + 활성 실행 유일성 | 중복 실행을 막지만 잠금 대기와 충돌 응답을 사용자에게 설명해야 함 |
| 원천 네 곳을 읽는 동안 HTTP 연결이 끊길 수 있음 | Spring Batch 백그라운드 작업과 run 상태 | 접수 응답은 빨라지지만 폴링·복구 상태가 필요함 |
| 서로 다른 컬럼과 수량 의미를 바로 정식 테이블에 쓰면 잘못된 재고가 확정될 수 있음 | MyBatis projection, 공통 record, 사전 연결 검증, 핵심 트랜잭션 | 오류를 조용히 삼키지 않지만 한 건의 결정적 오류가 전체 시도를 멈출 수 있음 |
| 판매처를 먼저 필터한 뒤 SKU 위험도를 계산하면 종합 위험이 달라짐 | `valid_scope_keys → sku_risk_agg → candidate_keys` | 목록·건수·요약의 위험 의미는 맞지만 운영 실행계획은 별도 측정 대상 |
| 성공 직후 스냅샷이 없는데 대시보드 API를 반복 호출할 수 있음 | `changedCount > 0`일 때만 task 생성, run의 snapshot 준비 상태를 본 뒤 선택적 캐시 무효화 | no-op 재조회는 줄지만 스냅샷 지연 시간 동안 최종적 일관성이 남음 |

## 이 글에서 답하는 질문

- 버튼을 비활성화했는데도 데이터베이스 잠금이 필요한 이유는 무엇인가?
- 왜 서버는 동기화가 끝날 때까지 기다리지 않고 “요청을 접수했다”고 먼저 응답하는가?
- 한 번에 500건씩 읽고 쓴다는 말은 500건마다 저장을 확정한다는 뜻인가?
- 서버가 중간에 멈췄다가 다시 살아났을 때, 오래된 작업을 어떻게 구분하는가?
- 정식 재고, 위험 판정, 대시보드 중 어디까지 완료되어야 “동기화 성공”인가?

## 한 번의 동기화는 어떤 순서로 진행되는가

전체 흐름을 사람의 말로 풀면 다음과 같다.

**사용자 요청 → 실행권 확인 → 백그라운드 작업 등록 → 원천 검증·읽기 → 공통 형식으로 변환 → 정식 재고와 위험 판정 반영 → 대시보드·통계 스냅샷 생성 → 화면 갱신**

| 단계 | 무엇을 하는가 | 실패했을 때의 원칙 |
| --- | --- | --- |
| 요청 접수 | 같은 요청인지, 이미 실행 중인 작업이 있는지 확인한다. | 중복 요청은 새 작업을 만들지 않고 기존 결과와 연결한다. |
| 작업 등록 | 데이터베이스에 실행 기록을 먼저 남긴다. | 등록이 확정되지 않으면 백그라운드 작업도 시작하지 않는다. |
| 원천 검증·읽기 | 네 원천의 연결 상태를 먼저 확인한 뒤 정해진 순서와 크기로 나누어 읽는다. | 읽는 동안 원천 버전이 바뀌면 전체 시도를 중단한다. |
| 공통 형식과 의미 검증 | 서로 다른 컬럼과 상태값을 공통 의미로 바꾸고, 수량·연결 관계를 검사한다. | 일부만 건너뛰지 않고 전체 시도를 실패시킨다. |
| 핵심 반영 | 정식 재고와 위험 판정 결과를 같은 업무 트랜잭션에서 저장한다. | 하나라도 실패하면 둘 다 되돌린다. |
| 후속 집계 | 변경된 결과를 바탕으로 대시보드와 통계 스냅샷을 만든다. | 핵심 반영은 유지하고, 각 집계를 제한 재시도하며 누락은 DB 기준으로 재조정한다. |
| 화면 갱신 | 실행 상태와 집계 준비 상태를 확인해 canonical·대시보드·통계를 필요한 시점에 다시 불러온다. | 통신 오류가 나도 서버 작업 자체는 계속된다. |

![브라우저 요청이 실행권 확인과 Spring Batch를 거쳐 정식 재고·스냅샷·화면 갱신으로 이어지는 동기화 구조](/images/blog/integrated-inventory-sync-architecture-ai.png)

*생성 이미지 · 브라우저 요청, 백엔드 실행, Oracle 저장, 후속 스냅샷, 화면 준비 상태의 경계를 한 장으로 정리했습니다. 이미지의 영문 라벨보다 실제 API와 상태 계약을 우선해 읽어 주세요.*

동기화 성공의 기준은 **정식 재고와 위험 판정까지 확정되는 시점**이다. 대시보드와 통계는 이 결과를 보기 좋게 집계해 특정 시점의 값으로 저장한 후속 스냅샷이다. 핵심 반영은 성공했어도 후속 집계가 늦어지는 짧은 시간에는 상세 재고와 대시보드가 서로 다른 시점을 보여 줄 수 있다.

사용자가 누르는 수동 실행과 매일 한국 시간 0시 30분에 시작하는 예약 실행도 이 흐름을 함께 사용한다. 시작 주체만 다르고 연결 검증, 변경 감지, 정식 반영, 위험 판정, 후속 스냅샷 규칙은 같다. 예약 실행을 별도의 축약 경로로 만들지 않아 같은 원천이 실행 방식에 따라 다른 결과를 만드는 일을 피했다.

## 버튼 비활성화는 동시성 제어가 아니다

화면은 실행 중일 때 버튼을 비활성화한다. 사용자 경험에는 필요하지만 이것만으로 중복 실행을 막지는 못한다.

- 사용자가 브라우저 탭을 두 개 열 수 있다.
- 네트워크 지연 때문에 같은 요청이 다시 전송될 수 있다.
- 화면을 거치지 않고 서버의 접수 주소를 직접 호출할 수 있다.
- 서로 다른 서버 인스턴스가 같은 순간에 요청을 받을 수 있다.

그래서 서버는 세 겹으로 실행권을 지킨다.

### 1. 같은 요청을 알아보는 식별자

화면은 요청마다 고유한 식별자를 만든다. 같은 식별자로 재요청이 오면 서버는 새 작업을 추가하지 않고, 이미 만든 실행 기록을 돌려준다. 이런 성질을 **멱등성**이라고 한다. 같은 요청을 여러 번 보내도 업무 결과는 한 번 보낸 것과 같게 만드는 방식이다.

멱등성은 “같은 요청의 재전송”을 다룬다. 서로 다른 식별자로 동시에 들어온 두 요청까지 막아 주지는 않는다.

여기서 같은 요청은 같은 요청 식별자를 다시 보낸 경우다. 실행 기록이 남아 있는 동안 업무 내용이 비슷해도 새 식별자를 쓰면 멱등성으로 합쳐지지 않는다. 두 요청이 동시에 실행되려 할 때는 아래의 잠금과 활성 실행 제약이 별도로 막는다. 활성 범위는 사용자 한 명이나 원천 하나가 아니라, 네 원천이 만드는 정식 통합재고 전체다.

### 2. 데이터베이스의 짧은 행 잠금

실행권을 결정하는 짧은 구간에서는 Oracle의 **비관적 락**을 사용한다. 비관적 락은 “다른 요청도 동시에 들어올 수 있다”고 가정하고, 한 요청이 실행 상태를 확인하고 기록을 만드는 동안 같은 실행권 행을 다른 요청이 바꾸지 못하게 하는 방식이다.

잠금은 동기화가 끝날 때까지 유지하지 않는다. 실행 가능 여부를 판단하고 실행 기록을 만든 뒤 바로 놓는다. 잠금을 기다리는 최대 시간도 5초로 제한했다. 그 안에 실행권을 얻지 못하면 서버는 무작정 대기하지 않고, 이미 다른 요청이 처리 중이라는 충돌 응답을 보낸다.

이렇게 범위를 좁힌 이유는 분명하다. 긴 작업 전체에 잠금을 걸면 중복 실행은 막기 쉽지만, 장애가 났을 때 다른 요청까지 오래 붙잡고 데이터베이스 연결도 낭비한다.

### 3. 데이터베이스의 유일성 제약

애플리케이션 검사가 예상치 못한 경쟁 조건을 놓치더라도, 데이터베이스가 동시에 활성 상태인 실행 기록이 둘 생기지 않도록 마지막 방어선을 둔다. 화면 확인, 서버 잠금, 데이터베이스 제약은 같은 일을 중복하는 것이 아니라 서로 다른 실패 지점을 막는다.

| 선택지 | 장점 | 이 구조에서의 한계 |
| --- | --- | --- |
| 서버 메모리 잠금 | 구현이 단순하고 빠르다. | 서버가 여러 대면 각자 다른 잠금을 보게 된다. 재시작하면 상태도 사라진다. |
| Redis 분산 잠금 | 여러 서버가 빠르게 공유할 수 있다. | 별도 인프라와 만료·장애 정책을 운영해야 한다. |
| Oracle 행 잠금 | 실행 이력과 같은 저장소에서 트랜잭션으로 관리할 수 있다. | 잠금 범위와 대기 시간을 잘못 잡으면 데이터베이스 경합이 커진다. |
| 낙관적 락 | 충돌이 드물 때 잠금 대기가 적다. | 실행 시작처럼 충돌 자체를 먼저 막아야 하는 구간에서는 재시도 설계가 복잡해진다. |

이 프로젝트는 실행 이력을 이미 Oracle에 저장하고 있었고, 실행 시작 경쟁도 같은 트랜잭션에서 판단해야 했다. 그래서 **짧은 Oracle 행 잠금과 유일성 제약**을 선택했다.

### 4. 실행 남용을 막는 속도 제한

동시에 하나만 실행되게 했다고 해서 반복 요청 문제가 사라지지는 않는다. 한 사용자가 실행이 끝날 때마다 계속 요청하면 데이터베이스와 배치 작업은 쉬지 못한다. 같은 사용자는 요청 사이에 최소 10초를 두고 한 시간에 최대 60회까지만 실행하도록 제한했다. 제한을 넘으면 서버가 다시 시도할 시간을 함께 알려 준다.

속도 제한은 시스템 남용을 줄이는 장치이고, 잠금과 유일성 제약은 같은 순간 두 작업이 활성화되는 것을 막는 장치다. 둘은 보호하는 문제가 다르므로 어느 하나로 다른 하나를 대신할 수 없다.

## 오래 걸리는 작업은 웹 요청에서 분리한다

네 원천을 읽고 검증한 뒤 여러 테이블을 갱신하는 작업은 몇 초 이상 걸릴 수 있다. 웹 요청을 그 시간 내내 열어 두면 다음 문제가 생긴다.

- 브라우저나 중간 장비의 시간 제한에 걸릴 수 있다.
- 사용자는 응답이 없는 화면을 보며 다시 버튼을 누르기 쉽다.
- 서버의 웹 요청 처리 자원이 오래 점유된다.
- 작업은 진행 중인데 네트워크만 끊겨 실패처럼 보일 수 있다.

그래서 서버는 요청을 검증하고 실행 기록을 확정한 뒤 **HTTP 202 Accepted**, 즉 “작업을 접수했지만 아직 완료되지는 않았다”는 응답을 돌려준다. 화면은 이때 받은 실행 식별자로 진행 상태를 조회한다.

실행 기록을 먼저 확정한 다음 백그라운드 작업을 시작한다. 데이터베이스 반영이 끝나기도 전에 작업을 시작하면, 백그라운드 작업이 존재하지 않는 실행 기록을 조회하는 경쟁 조건이 생길 수 있다. 현재 구조는 요청 트랜잭션이 끝난 뒤 Spring Batch 작업을 등록해 이 틈을 막는다.

Spring Batch는 작업 실행 이력과 상태처럼 중단된 작업의 재시작 여부를 판단하는 정보를 관리한다. 현재는 읽기·변환·쓰기를 각각 독립된 청크 단계로 나누지 않았다. 하나의 작업 단계가 전체 동기화 흐름을 조정한다. Spring Batch는 실행 생명주기를 맡고, 원천별 500행 읽기와 묶음 쓰기, 전체 검증과 최종 반영은 업무 코드가 관리하는 구조다.

Spring Batch를 쓴다고 해서 모든 업무가 자동으로 복구되는 것은 아니다. 어떤 상태를 다시 실행해도 안전한지, 오래 멈춘 작업을 누가 발견할지, 업무 데이터와 실행 이력을 어디까지 함께 되돌릴지는 애플리케이션이 정해야 한다. 현재 복구 실행은 저장된 페이지 중간 상태를 이어받지 않고 첫 원천 페이지부터 다시 읽는다. 읽기 비용을 다시 치르는 대신, 메모리의 중간 결과까지 영구 저장하고 정확히 복원하는 복잡성을 피했다.

현재는 동시에 등록할 수 있는 백그라운드 작업 수를 제한해 요청이 몰릴 때 서버 스레드가 무한히 늘어나지 않도록 했다. 큐가 가득 차면 “접수는 되었는데 언젠가 실행되겠지”라고 숨기지 않고, 실행 시작 실패 상태를 명시적으로 기록한다.

데이터베이스 접수가 끝난 직후 작업 등록 전에 서버가 종료되면 대기 기록만 남을 수 있다. 5분이 지난 대기 기록에 실제 Spring Batch 실행이 없으면 운영자가 같은 기록을 새 작업 세대로 복구할 수 있다. 이를 자동으로 찾아 시작하는 감시기는 아직 없으므로, 접수 기록의 지속성과 자동 실행 보장을 같은 뜻으로 보아서는 안 된다.

## 한 번에 최대 500행씩 읽는 이유

원천 데이터가 많다고 해서 한 번의 데이터베이스 조회로 전부 가져오지는 않는다. 오프라인, 이커머스, 그리팅, 물류센터 순서로 원천별 최대 500행씩 읽고 정식 테이블에 쓸 때도 최대 500행 단위로 SQL 요청을 나눈다. 처리 순서는 진행 흐름을 일정하게 만들 뿐, 뒤에서 읽은 원천이 무조건 우선한다는 뜻은 아니다.

500은 한 번의 데이터베이스 읽기와 쓰기 요청에 포함하는 최대 행 수다. 전체 동기화 건수나 저장 확정 단위는 아니다. 500행을 넘으면 다음 묶음을 계속 처리하며, 500행마다 앞부분의 성공이 따로 남지는 않는다.

읽기는 마지막으로 확인한 안정적인 키 다음부터 이어 가는 **키셋 페이지네이션**을 사용한다. 단순히 “몇 번째 묶음인지”로 이동하는 방식보다, 앞쪽 데이터가 추가되거나 삭제될 때 중복·누락이 생길 가능성을 줄일 수 있다.

한 시도 안에서는 원천 데이터의 버전도 고정한다. 읽는 도중 원천 버전이 바뀌면 “앞부분은 이전 버전, 뒷부분은 새 버전”인 혼합 결과를 만들지 않고 전체 시도를 중단한다. 운영자는 다시 실행해 한 버전의 일관된 결과를 얻는다.

500이라는 크기는 절대적인 정답이 아니다. 너무 작으면 데이터베이스 왕복 횟수가 늘고, 너무 크면 한 번에 사용하는 메모리와 SQL 크기가 커진다. 현재 값은 33,358행의 검증 자료를 다루기 위한 구현 기준이며 최적값을 입증한 성능 수치는 아니다. 실제 운영에서는 처리 시간·메모리·데이터베이스 부하를 측정해 조정해야 한다.

한 가지 한계도 있다. 조회 자체는 500행씩 하지만, 변경 후보 전체는 검증과 반영을 위해 메모리에 모은다. 현재는 최대 10만 건으로 상한을 두고 넘으면 실패시킨다. 즉, 페이지 조회가 곧 전체 메모리 사용량의 상한을 의미하지는 않는다. 데이터가 이 범위를 넘어가면 임시 적재 테이블이나 스트리밍 기반 구조로 옮겨야 한다.

## 공통 형식화와 검증은 반영 전에 끝낸다

네 원천은 같은 재고를 서로 다른 이름과 단위, 상태값으로 표현할 수 있다. 먼저 모든 활성 행이 승인된 연결표와 이어지는지 원천별로 검사한다. 이 사전 검사는 지문이 같은 행까지 포함해 연결 누락을 찾는다.

사전 검사를 통과하면 데이터베이스가 이전 성공 지문과 다른 행만 변경 후보로 고른다. 아래의 공통 변환과 의미 검증은 이 후보를 대상으로 진행한다.

- 원천의 상품·SKU·창고·재고 식별자를 정식 데이터의 안정적인 식별자와 연결한다. SKU는 옵션과 용량까지 구분한 실제 판매·재고 관리 단위다.
- 문자열이나 숫자로 흩어진 상태값을 공통 상태로 바꾼다.
- 바로 판매에 쓸 수 있는 가용 수량, 이미 배정된 예약 수량, 운영 기준인 안전재고를 같은 의미와 단위로 맞춘다.
- 같은 조건으로 생산·입고된 재고 묶음인 LOT에서는 입고일·유통기한·판매 중지일과 상태를 맞춘다.
- 어느 원천의 어느 행에서 왔는지 추적할 수 있는 출처 정보와 버전을 함께 보관한다.

그다음 수량이 음수인지, 필수값이 빠졌는지, 같은 대상을 여러 원천이 서로 다르게 주장하는지 검사한다. 이 과정은 잘못된 행만 몰래 버리는 방식이 아니다. 정식 재고를 만들 수 없을 정도의 불일치가 하나라도 있으면 이번 시도 전체를 실패시킨다. 일부 성공을 허용하면 “어느 원천까지 반영되었는지”를 별도로 추적하고 복구해야 해 운영 복잡도가 크게 올라가기 때문이다.

변경 후보를 고르는 내용 지문을 보통 **해시**라고 부른다. 지문이 다른 후보는 변환과 검증을 마친 뒤 정식 데이터의 실제 값과 다시 비교한다. 원천의 부가 정보만 달라지고 정식 값은 같다면 쓰지 않는다.

이 방식에서 지문 계약은 정확성의 일부다. 해시 충돌이 일어나거나 중요한 필드를 지문 계산에서 빠뜨리면 실제로 바뀐 행도 후보에서 제외될 수 있고, 후보에 들어오지 않은 행은 마지막 값 비교로 구할 수 없다. 그래서 해시 알고리즘뿐 아니라 필드의 종류·순서·빈 값·날짜와 숫자 표현을 생성기와 서버가 같은 규칙으로 유지하고, 대표 입력의 예상 지문과 전체 검증값을 시험한다.

이 구조는 애플리케이션이 모든 원천 값을 메모리에 올려 정식 데이터와 비교하는 비용을 줄인다. 데이터베이스가 지문 조건을 검사하고 후보를 찾는 비용까지 없애는 구조는 아니며, 실제 조회 비용은 운영 실행 계획으로 확인해야 한다.

## 정식 재고와 위험 판정은 같은 트랜잭션에서 확정한다

검증을 통과하면 정식 재고, LOT 정보, 재고 정책 등 기존에 연결된 대상을 갱신한다. 이 동기화는 새로운 상품이나 창고를 자동으로 생성하지 않는다. 검증된 기존 식별자를 기준으로 현재 값을 갱신하는 구조다.

쓰기 요청은 데이터베이스 부담을 줄이려고 500행씩 나누지만 **500행마다 저장을 확정하지는 않는다.** 정식 재고 반영과 위험 판정 저장은 모두 성공해야 한꺼번에 확정되는 하나의 업무 묶음, 즉 트랜잭션으로 처리한다. 마지막 단계에서 오류가 나면 앞에서 갱신한 정식 재고도 함께 되돌아간다.

원천 하나를 처리할 때 화면에는 데이터 검증, 원천 읽기, 공통 형식 변환이 차례로 보인다. 이 세 단계는 네 원천마다 반복된다. 모든 원천 처리가 끝나면 통합재고 반영과 위험 판정으로 넘어간다.

내부 상태 코드를 그대로 노출하지 않고 사용자가 지금 무엇을 하는지 이해할 수 있는 말로 바꿨다. 대기, 실행 중, 완료뿐 아니라 원천 변경 감지로 중단, 중단 후 복구 대기, 실행 시작 실패도 구분한다.

## 위험 판정도 이번 동기화의 결과로 저장한다

위험 판정을 조회할 때마다 다시 계산하면, 같은 실행 결과를 보고도 조회 시점이나 참조 데이터 변화에 따라 등급이 달라질 수 있다. 현재는 동기화 시점에 위험 등급, 판정 이유, 재고 소진 예상 일수, 안전재고 미달 여부를 함께 저장한다. 상세 화면은 이 저장 결과를 기준으로 보여 준다.

위험 판정의 주요 원칙은 다음과 같다.

- 표시용 상품 코드가 아니라 내부의 안정적인 상품·창고 식별자로 영향 범위를 묶는다.
- 영향 범위가 있는데 위험 결과가 하나도 만들어지지 않으면 핵심 동기화를 실패시킨다.
- 수요 예측이 없거나 유효하지 않으면 예측이 필요한 규칙만 제외하고, 가용 수량·안전재고·LOT 정보로 판단 가능한 규칙은 계속 적용한다.
- 유효하지만 오래된 예측은 계산에 사용하되, 판정 이유에 오래된 자료라는 사실을 남긴다.
- LOT의 만료·임박 여부는 예측 기준일이 아니라 실제 위험 판정일을 기준으로 계산한다.
- 가용 수량이 없으면 0으로 보고 가장 위험한 상태로 다루며, 음수 수량은 잘못된 입력으로 판단해 동기화 자체를 실패시킨다.
- 안전재고가 없으면 해당 비교 규칙만 제외하고 그 사실을 판정 이유에 남긴다.

이 설계는 “자료 하나가 없으면 무조건 안전”이라는 잘못된 결론을 피한다. 동시에 불완전한 예측 하나 때문에 가용 수량과 LOT로 알 수 있는 위험까지 모두 숨기지 않는다.

대신 보수적인 규칙에는 오판 방향이 생긴다. 가용 수량 누락을 0으로 보면 실제 재고가 있어도 과도한 위험 경보가 날 수 있지만, 화면의 판정 사유가 실제 0과 데이터 누락을 구분한다. 예측이 없으면 예측으로만 찾을 수 있는 부족 위험을 놓칠 수 있다. 예측 기준일이 판정일보다 14일 넘게 오래된 경우에도 값이 유효하면 계산에 쓰므로, 낡은 수요가 과대·과소 경보를 만들 가능성도 남는다. 이 경우에는 오래된 예측을 사용했다는 사실을 판정 사유에 함께 저장한다.

현재 구현에는 검증 경계도 남아 있다. 위험 결과가 완전히 비는 경우는 막지만, 여러 영향 범위 각각에 결과가 정확히 하나씩 존재하는지를 별도 개수 검증으로 보장하지는 않는다. 이 부분은 데이터 범위가 더 복잡해질 때 강화할 지점이다.

## 오래된 작업자는 새 결과를 덮어쓸 수 없다

백그라운드 작업은 서버 장애나 일시적인 정지 때문에 예상보다 오래 멈출 때가 있다. 일정 시간 동안 작업의 생존 신호가 없으면 운영자가 그 실행을 중단·복구 대기 상태로 바꾸고 새 시도를 시작한다.

문제는 이전 작업이 뒤늦게 다시 움직이는 경우다. 상태만 “실행 중”인지 확인하면, 오래된 작업이 새 시도의 결과를 덮어쓸 수 있다.

이를 막기 위해 실행마다 **작업 세대 번호**를 부여한다. 작업자는 읽기, 변환, 검증, 반영, 위험 판정처럼 중요한 단계로 넘어갈 때마다 자신이 여전히 현재 세대인지 확인한다. 새 시도가 시작되어 세대가 바뀌었다면 이전 작업의 상태 변경과 결과 확정을 거부한다. 분산 시스템에서는 이런 방식을 보통 **펜싱 토큰**이라고 부른다. 문을 잠그는 것에 그치지 않고, 오래된 열쇠로 들어온 작업의 쓰기까지 차단하는 장치다.

현재 복구는 자동 감시기가 알아서 시작하는 방식이 아니라 운영자가 상태를 확인하고 수동으로 재시도하는 흐름이다. 작업 세대와 생존 신호는 안전한 재시도의 기반이지만, 자동 복구 정책 자체를 대신하지는 않는다.

복구 시에는 마지막으로 읽은 위치부터 이어 가지 않고 네 원천을 처음부터 다시 읽는다. 변경 지문과 실제 값 비교 덕분에 같은 값을 다시 쓰는 일은 줄지만, 읽기 비용은 반복된다. 현재 규모에서는 마지막 처리 위치를 영구 저장하는 복잡성보다 복구 절차의 단순함을 택했다.

## 대시보드와 통계는 왜 별도 작업인가

정식 재고와 위험 판정이 확정된 뒤에는 대시보드와 통계용 스냅샷을 만든다. 이 집계까지 핵심 트랜잭션에 넣으면 다음 문제가 생긴다.

- 집계가 느릴수록 정식 재고 확정도 함께 늦어진다.
- 통계 한 건의 실패 때문에 올바르게 만든 정식 재고와 위험 판정까지 되돌아간다.
- 긴 트랜잭션이 데이터베이스 잠금과 로그 사용량을 키운다.

그래서 현재는 핵심 트랜잭션이 끝난 뒤 대시보드와 통계를 동시에 실행할 개수를 제한한 별도의 작업 대기열에서 생성한다. 하나가 실패해도 다른 하나와 핵심 동기화 결과는 유지된다.

실행을 빠르게 넘기는 executor 큐 자체는 서버 메모리에 있지만, 작업의 권위는 V27 task 행이다. canonical 반영 transaction이 대시보드와 재고통계 task를 함께 만들고, worker가 due task를 원자적으로 claim해 10분 lease와 시도 횟수를 기록한다. 연결 단절·일시적 DB 자원 장애만 최대 세 번 실행하고, 같은 입력으로 해결되지 않는 직렬화·검증·무결성 오류는 첫 시도에서 `FAILED`로 끝낸다. 서버가 재시작해 큐를 잃어도 60초 복구기가 due task와 만료 lease만 다시 예약한다. 기존 스냅샷과 task의 실행별 유일성 제약 덕분에 요청이 겹쳐도 같은 결과를 중복 저장하지 않는다.

이 방식은 새 메시지 브로커 없이 Oracle 상태만으로 재시작 누락과 최대 시도를 설명할 수 있다는 장점이 있다. 반면 task table과 scanner를 운영해야 하고, core 원천 동기화 자체의 자동 복구까지 담당하지는 않는다. V27 migration은 코드와 정적 계약 검증까지 끝냈지만 실제 Oracle 적용과 장애 주입 smoke test는 별도로 남아 있다.

## 브라우저는 완료 상태를 어떻게 확인하는가

화면은 작업 중일 때만 실행 상태를 주기적으로 확인한다.

- 실행 대기 중에는 비교적 짧은 3초 간격으로 확인한다.
- 실제 실행이 시작되면 10초 간격으로 확인해 불필요한 요청을 줄인다.
- 핵심 반영 성공 뒤 스냅샷 생성 중에는 완료 후 1분까지 3초, 1~5분은 10초 간격으로 확인한다.
- task가 실패하거나 두 스냅샷이 모두 준비되거나 화면이 백그라운드로 가면 반복 확인을 멈춘다. task 상태를 알 수 없는 경우에도 5분 뒤에는 잠금을 해제한다.

이 **폴링**은 진행 상황을 보여 주는 방법이지, 중복 실행을 막는 장치가 아니다. 중복 실행 방지는 앞에서 설명한 서버의 멱등성, 데이터베이스 잠금, 유일성 제약이 담당한다.

변경이 있는 성공을 확인하면 화면은 먼저 재고 목록, 요약, 상세, LOT, 위험 현황을 다시 조회한다. 대시보드와 통계는 아직 만드는 중일 수 있으므로 run API의 준비 상태가 각각 true가 된 뒤 해당 조회만 다시 요청한다. TanStack Query에서는 이를 캐시 무효화라고 한다. 데이터가 오래되었다고 판단하는 기준과 화면에서 더는 쓰지 않는 데이터를 메모리에서 지우는 기준은 서로 다르다. 둘을 같은 캐시 시간으로 이해하면 새로 고침 정책을 잘못 설계하기 쉽다.

### 목록과 상단 요약은 같은 필터 계약을 사용한다

재조회 시점만 같아도 목록과 요약이 서로 다른 질문을 보내면 화면은 일관되지 않는다. 실제 회귀 테스트에서 목록 요청에는 `OR`가 전달되지만 요약 API 파라미터와 캐시 키에서는 `filterOperator`가 빠진 문제를 찾았다. 이 상태에서는 목록이 여러 활성 필터 그룹 중 하나만 만족하는 재고를 보여 주는 동안 상단 KPI는 기본 `AND`로 모든 그룹을 만족하는 재고만 셀 수 있다. 요약 조회의 허용 파라미터와 조회 키에 연산자를 함께 포함해 두 응답의 조건을 맞췄다.

서버는 `AND`와 `OR`만 허용하며, 같은 그룹의 여러 선택값은 항상 `OR`로 묶는다. MyBatis도 사용자 입력을 SQL에 그대로 치환하지 않고 `<choose>`로 고정된 논리 연산자만 렌더링한다. 종합 위험은 판매처별 행을 필터한 뒤 다시 계산하지 않는다. 유효한 모든 판매처·미할당 범위에서 SKU 종합 위험을 먼저 확정하고, 목록·전체 건수·상단 요약이 같은 값을 사용한다.

이 변경은 필터 결과의 정확성을 맞춘 작업이다. 실제 Oracle에서 CTE와 조건 조합의 응답 시간이 개선됐다고 주장할 측정값은 아직 없으며, 혼합 위험 SKU smoke test와 대표 실행계획 수집은 별도로 남아 있다.

여러 브라우저가 완료를 같은 순간 확인해 조회 요청이 몰리지 않도록, 성공 뒤 다시 불러오는 시점에는 0~3초의 작은 무작위 지연을 둔다. 반면 수요예측은 이번 동기화가 직접 다시 계산하는 결과가 아니므로 자동 갱신 대상에서 제외했다.

요청 전송 도중 연결이 끊겨 접수 성공 여부를 모를 때는 같은 요청 식별자를 다시 사용한다. 서버에서 성공 또는 실패가 확인된 뒤 사용자가 새 실행을 선택할 때만 새 식별자를 만든다. 이미 다른 세션이나 예약 실행이 진행 중이면 그 실행 번호를 이어서 추적한다. 속도 제한, 상태 확인 실패, 복구 대기 역시 하나의 일반 오류로 뭉개지 않고 각각 다른 안내와 재시도 동작을 제공한다.

상태 변화는 색만으로 구분하지 않고 보조기술이 읽을 수 있는 알림으로 전달한다. 키보드만으로 실행과 수동 재시도를 할 수 있고, 상태 조회가 잠시 실패하더라도 마지막으로 확인한 정상 상태를 지우지 않는다.

변경 건수가 0이면 스냅샷을 새로 만들거나 관련 조회를 자동 재호출하지 않는다. 실제 canonical 변화가 없는 no-op 실행까지 무거운 집계와 API 요청을 반복하지 않기 위한 경계다. 변경이 있으면 화면은 `집계 최신화 중`을 표시하고 두 스냅샷이 DB에 저장됐다는 응답을 받은 뒤에만 새 집계를 요청한다.

## 조회 성능은 동기화와 분리해서 개선했다

동기화 작업을 백그라운드로 옮겼다고 목록 조회가 저절로 빨라지는 것은 아니다. 그래서 읽기 경로는 다음 순서로 좁혔다.

1. **원천 테이블을 목록 요청에서 제외한다.** 동기화가 검증해 저장한 `inventory_balance`, 상품·SKU·판매처 관계, 위험 결과를 목록의 기준으로 삼는다.
2. **SKU 한 행을 먼저 만든다.** 판매처·LOT를 그대로 조인해 행을 복제하지 않고, 판매처별 사실은 응답의 배열로 묶는다. LOT와 수요예측은 상세 요청에서만 읽는다.
3. **종합 위험을 먼저 집계한다.** 활성·유효 범위인 `valid_scope_keys`를 만든 뒤 모든 판매처/미할당 범위의 `sku_risk_agg`를 계산하고, 그 다음 `candidate_keys`에 판매처·위험·검색 필터를 적용한다. 그래서 “SAFE 판매처만 선택했더니 SKU 전체가 SAFE로 바뀌는” 오류를 피한다.
4. **목록·전체 건수·상단 요약을 같은 계약으로 계산한다.** 세 SQL은 각각 필요한 결과를 만들지만 `AND`/`OR`, 위험 등급, 유효 범위의 순서를 공유한다. 현재 목록 페이지는 Oracle `OFFSET … FETCH NEXT` 기반의 서버 페이지이며, 동기화 원천 읽기에서 쓰는 키셋 페이지와 혼동하지 않았다.
5. **프론트는 조건이 바뀐 결과만 다시 읽는다.** URL 조건 전체를 TanStack Query key에 넣고, 요약 key에도 `filterOperator`를 포함한다. 동기화가 변경을 만들었을 때만 목록·요약·상세를 무효화하고, no-op이면 무거운 재조회와 스냅샷 API 호출을 생략한다.

이 순서는 “몇 퍼센트 빨라졌다”는 벤치마크가 아니다. 현재 확인한 성과는 브라우저가 전체 원천 데이터를 받지 않고, 상세에 필요한 LOT·예측을 목록과 분리하며, 목록과 KPI가 서로 다른 필터를 보내지 않는다는 **데이터량·정확성 경계**다. 실제 Oracle 성능을 주장하려면 대표 조건별 실행계획, 응답 시간, 잠금 대기, 동시 사용자 수를 운영과 가까운 데이터로 수집해야 한다.

### 쓸모없는 호출을 줄인 지점과 아직 하지 않은 것

| 구분 | 현재 동작 | 해석 |
| --- | --- | --- |
| 변경 없는 동기화 | `changedCount = 0`이면 후속 snapshot task와 자동 목록·대시보드 재조회 생략 | no-op 실행이 캐시와 DB를 흔들지 않음 |

## 현재 보장하는 것과 아직 보장하지 않는 것

| 현재 보장하는 것 | 아직 남은 과제 |
| --- | --- |
| 같은 요청은 하나의 실행 결과로 묶이고, 후속 집계의 시도·lease·최종 실패도 task별로 남는다. | V27의 실제 Oracle 적용·장애 복구 smoke 검증은 남아 있다. |
| 네 원천이 만드는 정식 통합재고 전체에는 하나의 활성 동기화만 시작된다. | 오래 멈춘 실행을 자동으로 찾고 복구하는 감시기는 없다. |
| 한 시도는 같은 원천 버전만 사용한다. | 새 상품·창고·원천 삭제를 자동으로 정식 데이터에 전파하지 않는다. |
| 정식 재고와 위험 판정은 함께 확정되거나 함께 되돌아간다. | 전체 변경 후보를 메모리에 모으므로 매우 큰 규모에는 임시 적재 구조가 필요하다. |
| 목록·전체 건수·상단 KPI는 같은 필터 연산자와 SKU 종합 위험을 사용한다. | 실제 Oracle의 혼합 위험 데이터 smoke test와 대표 조건 실행계획 수집은 남아 있다. |
| 오래된 작업 세대는 새 결과를 덮어쓸 수 없다. | 폴링보다 정밀한 실시간 알림과 스냅샷 세대 표시는 추후 개선 대상이다. |
| 화면에는 내부 상태 코드 대신 이해할 수 있는 한국어 상태를 표시한다. | 처리량, 잠금 대기, 후속 집계 지연을 운영 지표로 더 세분화할 필요가 있다. |

“정확히 한 번만 실행된다”는 표현은 의도적으로 쓰지 않았다. 네트워크와 장애가 있는 시스템에서 그 말은 지나치게 넓은 보장을 암시한다. 현재 구조가 실제로 보장하는 것은 **같은 요청 식별자를 하나로 묶고, 정식 통합재고 전체의 활성 작업을 하나로 제한하며, 오래된 작업의 쓰기를 거부하고, 핵심 결과를 모두 함께 확정하거나 함께 되돌리는 것**이다.

## 핵심 트레이드오프 정리

| 설계 선택 | 얻은 것 | 치른 비용 |
| --- | --- | --- |
| 짧은 비관적 락과 유일성 제약 | 여러 서버에서도 실행 시작 경쟁을 막는다. | 잠금 대기 시간과 충돌 응답을 운영해야 한다. |
| 접수 응답과 Spring Batch 분리 | 긴 작업이 웹 요청을 붙잡지 않는다. | 화면 상태 조회와 작업 복구 정책이 필요하다. |
| 500행 단위 읽기·쓰기 | 한 번의 SQL과 메모리 급증을 줄인다. | 데이터베이스 왕복 횟수가 늘며, 크기를 튜닝해야 한다. |
| 원천 버전 고정과 해시 비교 | 혼합 스냅샷을 막고 변경 후보를 빨리 찾는다. | 원천이 자주 바뀌면 시도가 실패할 수 있고 지문 규칙을 관리해야 한다. |
| 핵심 업무 하나의 트랜잭션 | 정식 재고와 위험 판정의 불일치를 막는다. | 변경량이 커질수록 트랜잭션 시간과 메모리 부담이 커진다. |
| 제한된 후속 스냅샷 + V27 task 복구 | 핵심 반영을 빠르게 끝내고 일시 실패·재시작 누락을 복구한다. | task table, lease, scanner 운영이 추가된다. |
| 위험 판정 결과 저장 | 같은 실행의 등급과 이유를 일관되게 설명한다. | 규칙 변경 뒤 과거 결과를 다시 계산하려면 별도 재평가가 필요하다. |

## 자주 묻는 질문

### 데이터베이스 잠금은 동기화가 끝날 때까지 유지하나?

아니다. 실행 가능 여부를 확인하고 실행 기록을 만드는 짧은 구간에만 사용한다. 실제 원천 읽기와 반영은 작업 세대, 원천 버전, 업무 트랜잭션으로 보호한다.

### 한 번에 500행이면 전체 데이터가 500행을 넘을 수 없나?

아니다. 500은 한 번의 읽기 또는 쓰기 요청 크기다. 다음 묶음을 계속 처리한다. 다만 변경 후보 전체를 메모리에 모으므로 현재는 별도의 10만 건 상한이 있다.

### Spring Batch를 쓰면 실패한 작업이 자동으로 복구되나?

아니다. Spring Batch는 실행 상태와 재시작 기반을 제공한다. 어떤 작업을 언제 다시 실행할지, 재실행이 업무상 안전한지는 별도 정책과 구현이 필요하다. 현재는 수동 복구 흐름이다.

### 수요 예측이 없으면 위험하지 않다고 판단하나?

아니다. 예측이 필요한 규칙만 제외하고 가용 수량, 안전재고, LOT로 판단할 수 있는 위험은 계속 평가한다. 가용 수량 자체가 없으면 0으로 보아 가장 보수적으로 다룬다.

### `OR` 필터를 선택하면 목록과 상단 KPI가 다른 조건을 쓰나?

아니다. 주소의 `filterOperator=OR`가 목록과 요약 API 파라미터 및 각각의 캐시 키에 함께 들어간다. 서버의 목록·전체 건수·요약 SQL도 같은 그룹 결합 방식과 미리 확정한 SKU 종합 위험을 사용한다.

### 동기화 성공인데 대시보드가 잠시 이전 값일 수 있나?

서버의 핵심 성공은 정식 재고와 위험 판정의 확정을 뜻하므로 스냅샷 생성 중에는 짧은 지연이 있다. 화면은 이때 `집계 최신화 중`을 표시하고, 각 스냅샷이 DB에 저장됐다는 준비 상태를 받은 뒤 해당 API를 다시 요청한다.
