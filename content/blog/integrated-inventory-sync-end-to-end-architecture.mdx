통합재고 화면에서 해결해야 할 성능 문제는 두 종류였다. 첫째, 목록을 열거나 필터를 바꿀 때 브라우저가 원천·판매처·LOT·예측 데이터를 한꺼번에 받지 않아야 했다. 둘째, 동기화 버튼을 눌렀을 때는 오래 걸리는 작업이 HTTP 요청과 데이터베이스 잠금을 붙잡지 않아야 했다. 같은 요청의 재전송이나 여러 서버의 동시 실행도 막아야 했다.

읽기 경로와 실행 경로는 분리해서 다뤘다. 읽기 경로는 **정식 재고 → SKU 종합 위험 → 후보 필터 → 서버 페이지 → TanStack Query** 순서로 필요한 데이터만 보낸다. 실행 경로는 **멱등성 → 짧은 비관적 락 → HTTP 202 → Spring Batch → 트랜잭션 → 선택적 캐시 갱신** 순서로 작업을 보호한다.

운영 응답 시간의 개선율은 아직 말할 수 없다. 실제 Oracle 실행계획과 운영 부하 측정이 남아 있다. 이 글에서 “조회 성능을 개선했다”는 말은 현재 코드가 목록의 데이터 범위를 SKU 단위로 제한하고, LOT·예측을 상세로 분리하며, 정식 재고 DML 건수가 0인 실행 뒤 후속 스냅샷과 자동 재조회를 생략한다는 뜻이다. 다만 위험 판정만 다시 저장된 실행까지 `changedCount`가 포착하지는 못하므로, 이 경우 캐시 최신성은 남은 과제로 구분한다.

읽기·실행 경로는 제가 맡은 [Backend 동기화 PR #65](https://github.com/kosa11-final-project/BackEnd/pull/65)와 [안전성 보강 PR #83](https://github.com/kosa11-final-project/BackEnd/pull/83), [Frontend 실행 화면 PR #32](https://github.com/kosa11-final-project/FrontEnd/pull/32)와 [상태·복구 화면 보강 PR #40](https://github.com/kosa11-final-project/FrontEnd/pull/40)에 걸쳐 구현했다. 이후 필터 조건과 권역 선택은 [Frontend 후속 PR #52](https://github.com/kosa11-final-project/FrontEnd/pull/52), 위험 판정·일괄 원천 조정·스냅샷 중복 처리는 [Backend 후속 PR #97](https://github.com/kosa11-final-project/BackEnd/pull/97)에서 보강했다. 네 원천을 정식 재고와 위험 상태로 만드는 내부 과정은 [첫 번째 글](/blog/integrated-inventory-source-normalization)에서 분리해 설명한다.

## 먼저 결론: 읽기와 실행을 다른 경로로 최적화했다

동기화 버튼을 누른 뒤 화면에서 보이는 실행 상태와, 그 결과를 재고 목록에서 읽는 조회 상태는 같은 일이 아니다. 아래 순서를 먼저 잡아 두면 뒤의 비관적 락·배치·캐시 설명이 한 흐름으로 연결된다.

| 경로 | 실제 순서 | 이 경로가 해결한 문제 |
| --- | --- | --- |
| 조회 경로 | 정식 재고 → 유효 범위 → SKU 종합 위험 → `AND`/`OR` 후보 → 페이지·건수·요약 → TanStack Query | 원천·LOT·예측 전체 전송과 필터별 불일치를 줄임 |
| 실행 경로 | `QUEUED` 접수 → `RUNNING`의 `VALIDATING`·`READING`·`NORMALIZING`·`PUBLISHING`·`ASSESSING_RISK` → `SUCCEEDED` → 후속 스냅샷 | 중복·동시 실행, 긴 HTTP 요청, 오래된 작업의 덮어쓰기를 막음 |

현재 상태 확인은 SSE 스트림이 아니라 실행 상태 API 폴링이다. 접수 대기 중에는 3초, 실행 중에는 10초, 핵심 반영 뒤 스냅샷을 기다릴 때는 처음 1분 동안 3초 간격을 사용한다. 이 글에서 성능의 중심은 동기화 작업 자체를 무리하게 빠르게 만드는 것이 아니라, **반영이 끝난 정식 재고를 조회할 때 매번 원천을 다시 합치지 않고 필요한 행만 보내는 것**이다.

![동기화 버튼이 원천별 실행과 정상 반영·오류 기록으로 이어지는 운영 흐름](/images/blog/inventory-sync-control-ai.png)

*생성 이미지 · 한 번의 실행 안에서 원천별 읽기·매핑·변경·오류를 기록하고 정식 반영으로 모으는 구조를 설명한다. 실제 재시도·lease·fencing 규칙은 아래 본문과 DB task 계약이 기준이다.*

### 문제 상황에서 기술 선택까지 이어진 이유

| 문제 상황 | 선택한 기술·설계 | 결과와 트레이드오프 |
| --- | --- | --- |
| 버튼 재클릭·재전송·다중 서버가 같은 실행을 시작할 수 있음 | client request id 멱등성 + 짧은 Oracle 비관적 락 + 활성 실행 유일성 | 중복 실행을 막지만 잠금 대기와 충돌 응답을 사용자에게 설명해야 함 |
| 원천 네 곳을 읽는 동안 HTTP 연결이 끊길 수 있음 | Spring Batch 백그라운드 작업과 run 상태 | 접수 응답은 빨라지지만 폴링·복구 상태가 필요함 |
| 서로 다른 컬럼과 수량 의미를 바로 정식 테이블에 쓰면 잘못된 재고가 확정될 수 있음 | MyBatis projection, 공통 record, 사전 연결 검증, 핵심 트랜잭션 | 오류를 조용히 삼키지 않지만 한 건의 결정적 오류가 전체 시도를 멈출 수 있음 |
| 판매처를 먼저 필터한 뒤 SKU 위험도를 계산하면 종합 위험이 달라짐 | `valid_scope_keys → sku_risk_agg → candidate_keys` | 목록·건수·요약의 위험 의미는 맞지만 운영 실행계획은 별도 측정 대상 |
| 성공 직후 스냅샷이 없는데 대시보드 API를 반복 호출할 수 있음 | 정식 재고 `changedCount > 0`일 때만 task 생성, run의 snapshot 준비 상태를 본 뒤 선택적 캐시 무효화 | 정식 재고 무변경 실행의 호출은 줄지만 스냅샷 지연과 위험 판정만 바뀐 실행의 캐시 최신성은 남음 |

## 이 글에서 답하는 질문

- 왜 목록은 원천 테이블이 아니라 정식 재고를 읽고, LOT·수요예측은 상세 요청으로 분리했는가?
- 종합 위험 필터와 `AND`/`OR` 조건이 목록·건수·상단 KPI에서 어떻게 같은 결과를 만드는가?
- 어떤 API와 캐시만 다시 요청하고, 왜 SSE 대신 폴링을 사용했는가?
- 버튼을 비활성화했는데도 데이터베이스 잠금이 필요한 이유는 무엇인가?
- 왜 서버는 동기화가 끝날 때까지 기다리지 않고 “요청을 접수했다”고 먼저 응답하는가?
- 한 번에 500건씩 읽고 쓴다는 말은 500건마다 저장을 확정한다는 뜻인가?
- 서버가 중간에 멈췄다가 다시 살아났을 때, 오래된 작업을 어떻게 구분하는가?
- 정식 재고, 위험 판정, 대시보드 중 어디까지 완료되어야 “동기화 성공”인가?

## 목록 조회가 범위를 줄이는 순서

판매처와 LOT를 그대로 조인해 한 SKU가 여러 행으로 늘어나면 페이지 수, 전체 건수, 상단 KPI가 모두 흔들린다. 동기화 작업을 백그라운드로 옮겨도 목록 SQL과 응답이 그대로면 사용자가 체감하는 조회는 달라지지 않는다. 따라서 목록 한 행의 기준을 SKU로 고정했다.

![정식 재고에서 위험 집계와 조건 필터를 거쳐 SKU 목록·상세·TanStack Query로 이어지는 조회 흐름](/images/blog/integrated-inventory-query-flow-ai.png)

*생성 이미지 · 정식 재고에서 위험을 먼저 집계하고 조건 필터를 거쳐 SKU 목록과 상세를 나눈 뒤 브라우저 캐시로 이어지는 순서를 보여 준다. 실제 목록 쿼리 순서는 아래 단계와 MyBatis 매퍼가 기준이다.*

### 1. 원천 4종을 목록 요청에서 제외했다

오프라인·이커머스·그리팅·물류센터 테이블을 요청마다 `UNION`하면 원천별 예외 처리가 모든 읽기 기능에 반복된다. 목록 API는 동기화가 이미 표준화하고 검증한 정식 상품·SKU·판매처·재고와 저장된 위험 판정을 읽어 같은 동기화 결과를 보는 화면에 같은 수량 의미를 제공한다.

목록 API가 정식 재고를 읽으려면 해당 재고가 최신이어야 한다. 화면은 최신성 상태를 알 수 있도록 동기화 실행 상태와 후속 스냅샷 준비 상태를 따로 보여 준다.

### 2. 목록과 상세의 데이터 무게를 나눴다

목록은 SKU 한 행과 판매처별 요약 배열만 반환한다. 물리 LOT와 수요예측은 사용자가 SKU와 판매처를 선택했을 때 상세 API로 읽는다. 목록·상세 분리는 세 가지 문제를 막았다.

- 판매처·LOT의 1:N 조인 때문에 목록 행이 복제되는 문제
- 목록 첫 화면에서 사용하지 않는 LOT·예측 데이터까지 전송하는 문제
- 상세 데이터 변경 때문에 전체 목록 캐시까지 자주 무효화하는 문제

사용자가 상세를 열 때는 API 요청이 한 번 추가된다. 목록 탐색 빈도가 더 높다는 판단으로 LOT·예측을 상세 API에 분리했다.

### 3. 위험을 먼저 집계하고 그다음 필터했다

위험 판정 단위는 `SKU × 판매처`이고 목록 한 행은 SKU다. 같은 SKU에 `DANGER` 판매처와 `SAFE` 판매처가 함께 있을 때 판매처 조건부터 적용하고 남은 행으로 위험을 다시 계산하면 SKU 전체의 위험이 `SAFE`로 바뀔 수 있다.

MyBatis CTE의 순서는 다음처럼 고정했다.

```text
valid_scope_keys
  → sku_risk_agg
  → candidate_keys
  → 목록 / 전체 건수 / 상단 요약
```

1. `valid_scope_keys`가 활성 판매처와 미할당 재고 범위를 확정한다.
2. `sku_risk_agg`가 범위 전체에서 `DANGER → CAUTION → NORMAL → SAFE` 우선순위로 SKU 종합 위험을 하나 만든다.
3. `candidate_keys`가 검색어·채널·판매처·물류센터·카테고리·보관유형·종합 위험 조건을 적용한다.
4. 목록, 전체 건수, 상단 요약이 같은 후보 기준을 사용한다.

여기서 미할당 물류센터 범위도 종합 위험 집계에 포함된다. 판매처가 없는 범위에는 판매처별 ML 예측을 붙이지 않으므로 현재 `v1.3.0` 규칙은 그 범위를 `FORECAST_UNAVAILABLE` 사유와 함께 `NORMAL` 하한으로 둔다. 따라서 한 SKU의 판매처 범위가 `SAFE`여도 미할당 범위가 있으면 SKU 목록의 종합 위험은 `NORMAL`이 될 수 있다. 이는 `양호` 필터가 고장 난 것이 아니라, 판매처별 위험과 SKU 전체 위험을 보수적으로 분리한 결과다.

CTE 집계 순서는 **필터가 업무 의미를 바꾸지 않게 하는 정확성 설계**다. SQL 성능은 별도 문제이며, 실제 Oracle 실행계획에서 어느 CTE가 병목인지와 인덱스 효과는 대표 데이터로 따로 측정해야 한다.

### 4. `AND`와 `OR`를 API·SQL·캐시 키까지 같은 계약으로 보냈다

사용자는 활성 필터 그룹 사이에서 `AND` 또는 `OR`를 선택할 수 있다. 예를 들어 “냉동이면서 위험”과 “냉동이거나 위험”은 전혀 다른 질문이다. 같은 그룹 안에서 여러 채널을 선택한 값들은 항상 `OR`이고, 그룹과 그룹을 묶는 방식만 사용자가 바꾼다.

초기 회귀 테스트에서는 목록 요청에 `filterOperator=OR`가 들어가도 요약 API 파라미터와 TanStack Query key에서는 빠지는 문제를 찾았다. 그러면 목록은 `OR`, 상단 KPI는 기본 `AND`로 계산되어 한 화면에서 서로 다른 수를 보여 준다. 요약 허용 파라미터와 캐시 키에 연산자를 포함해 두 응답의 질문을 맞췄다.

서버는 `AND`와 `OR`만 허용한다. MyBatis도 사용자 문자열을 `${filterOperator}`로 직접 삽입하지 않고 `<choose>`에서 두 고정 연산자만 렌더링한다. 고정 연산자 렌더링은 기능 정확성을 맞추고 동적 SQL 삽입 위험도 줄인다.

상세 필터에는 판매처 권역도 같은 조건 그룹으로 포함했고, 실제 목록 API가 저장·반환하는 판정상태인 `ASSESSED`와 `UNASSESSED`만 선택지로 노출했다. 화면에만 존재하던 `STALE`, `FAILED`, `REASSESSING` 같은 중간 상태를 조회 조건처럼 보내지 않도록 프론트와 백엔드 허용값을 맞췄다.

### 5. 서버 페이지와 화면 캐시의 책임을 분리했다

목록 API의 기본 크기는 20개, 최대 크기는 100개다. 현재 목록은 Oracle의 `OFFSET … FETCH NEXT`로 페이지를 자르고, 전체 건수는 별도 count SQL로 구한다. 원천 동기화 읽기에는 키셋 페이지네이션을 사용한다.

| 방식 | 장점 | 현재 목록에서의 판단 |
| --- | --- | --- |
| `OFFSET` 페이지 | 페이지 번호 이동과 전체 페이지 UI가 단순함 | 현재 목록에 사용. 뒤 페이지가 깊어질수록 스캔 비용이 커질 수 있음 |
| 키셋 페이지 | 깊은 페이지와 데이터 변화에 상대적으로 안정적 | 원천 동기화 읽기에 사용. 임의 페이지 이동과 전체 페이지 UI는 별도 설계 필요 |

프론트는 검색·필터·정렬·페이지를 URL에 보존하고, 같은 조건 전체를 TanStack Query key에 넣는다. 검색·필터·정렬 조건이 바뀌면 페이지를 1로 되돌려 이전 조건의 깊은 페이지에서 빈 결과가 보이는 문제를 피한다. 페이지가 바뀌는 동안에는 `keepPreviousData`로 기존 행을 유지해 화면 깜빡임을 줄이고, 필터 기준정보는 5분 동안 신선한 값으로 본다. 브라우저 캐시는 서버 페이지네이션을 대신하지 않는다. 서버가 먼저 데이터량을 제한하고, 브라우저 캐시는 같은 질문의 재사용과 전환 경험을 담당한다.

### 조회 쪽에서 확인한 성과와 미측정 항목

| 코드와 테스트로 확인한 결과 | 아직 확인하지 않은 항목 |
| --- | --- |
| 브라우저가 원천 4종과 전체 LOT·예측을 한 번에 받지 않음 | 운영과 가까운 데이터의 p50·p95 응답 시간 |
| 목록 한 행을 SKU로 고정하고 LOT·예측을 상세로 분리 | 대표 필터 조합별 Oracle 실행계획과 버퍼 읽기 |
| 목록·건수·상단 요약이 같은 `AND`/`OR`와 SKU 종합 위험을 사용 | 동시 사용자 증가에 따른 DB CPU·대기 시간 |
| 페이지 크기를 최대 100개로 제한하고 이전 페이지를 화면에 유지 | 깊은 `OFFSET` 페이지가 실제로 병목이 되는 시점 |

코드로 확인된 성능 개선 범위는 **불필요한 데이터 전송과 호출 감소**다. 운영 벤치마크를 하지 않아 특정 응답 시간이나 개선율은 성과로 쓰지 않았다.

## 동기화 실행을 보호하는 순서

전체 흐름을 사람의 말로 풀면 다음과 같다.

**사용자 요청 → 실행권 확인 → 백그라운드 작업 등록 → 원천 검증·읽기 → 공통 형식으로 변환 → 정식 재고와 위험 판정 반영 → 대시보드·통계 스냅샷 생성 → 화면 갱신**

| 단계 | 무엇을 하는가 | 실패했을 때의 원칙 |
| --- | --- | --- |
| 요청 접수 | 같은 요청인지, 이미 실행 중인 작업이 있는지 확인한다. | 중복 요청은 새 작업을 만들지 않고 기존 결과와 연결한다. |
| 작업 등록 | 데이터베이스에 실행 기록을 먼저 남긴다. | 등록이 확정되지 않으면 백그라운드 작업도 시작하지 않는다. |
| 원천 검증·읽기 | 네 원천의 연결 상태를 먼저 확인한 뒤 정해진 순서와 크기로 나누어 읽는다. | 읽는 동안 원천 버전이 바뀌면 전체 시도를 중단한다. |
| 공통 형식과 의미 검증 | 서로 다른 컬럼과 상태값을 공통 의미로 바꾸고, 수량·연결 관계를 검사한다. | 일부만 건너뛰지 않고 전체 시도를 실패시킨다. |
| 핵심 반영 | 정식 재고와 위험 판정 결과를 같은 업무 트랜잭션에서 저장한다. | 하나라도 실패하면 둘 다 되돌린다. |
| 후속 집계 | 변경된 결과를 바탕으로 대시보드와 통계 스냅샷을 만든다. | 핵심 반영은 유지하고, 각 집계를 제한 재시도하며 누락은 DB 기준으로 재조정한다. |
| 화면 갱신 | 실행 상태와 집계 준비 상태를 확인해 canonical·대시보드·통계를 필요한 시점에 다시 불러온다. | 통신 오류가 나도 서버 작업 자체는 계속된다. |

![브라우저 요청이 실행권 확인과 Spring Batch를 거쳐 정식 재고·스냅샷·화면 갱신으로 이어지는 동기화 구조](/images/blog/integrated-inventory-sync-architecture-ai.png)

*생성 이미지 · 브라우저 요청, 백엔드 실행, Oracle 저장, 후속 스냅샷, 화면 준비 상태의 경계를 한 장으로 정리했다. 이미지의 영문 라벨보다 실제 API와 상태 계약을 우선해 읽어야 한다.*

동기화 성공의 기준은 **정식 재고와 위험 판정까지 확정되는 시점**이다. 대시보드와 통계는 이 결과를 보기 좋게 집계해 특정 시점의 값으로 저장한 후속 스냅샷이다. 핵심 반영은 성공했어도 후속 집계가 늦어지는 짧은 시간에는 상세 재고와 대시보드가 서로 다른 시점을 보여 줄 수 있다.

사용자가 누르는 수동 실행과 매일 한국 시간 0시 30분에 시작하는 예약 실행도 이 흐름을 함께 사용한다. 시작 주체만 다르고 연결 검증, 변경 감지, 정식 반영, 위험 판정, 후속 스냅샷 규칙은 같다. 예약 실행을 별도의 축약 경로로 만들지 않아 같은 원천이 실행 방식에 따라 다른 결과를 만드는 일을 피했다.

## 버튼 비활성화는 동시성 제어가 아니다

화면은 실행 중일 때 버튼을 비활성화한다. 사용자 경험에는 필요하지만 이것만으로 중복 실행을 막지는 못한다.

- 사용자가 브라우저 탭을 두 개 열 수 있다.
- 네트워크 지연 때문에 같은 요청이 다시 전송될 수 있다.
- 화면을 거치지 않고 서버의 접수 주소를 직접 호출할 수 있다.
- 서로 다른 서버 인스턴스가 같은 순간에 요청을 받을 수 있다.

그래서 서버는 세 겹으로 실행권을 지킨다.

### 1. 같은 요청을 알아보는 식별자

화면은 요청마다 고유한 식별자를 만든다. 같은 식별자로 재요청이 오면 서버는 새 작업을 추가하지 않고, 이미 만든 실행 기록을 돌려준다. 이런 성질을 **멱등성**이라고 한다. 같은 요청을 여러 번 보내도 업무 결과는 한 번 보낸 것과 같게 만드는 방식이다.

멱등성은 “같은 요청의 재전송”을 다룬다. 서로 다른 식별자로 동시에 들어온 두 요청까지 막아 주지는 않는다.

여기서 같은 요청은 같은 요청 식별자를 다시 보낸 경우다. 실행 기록이 남아 있는 동안 업무 내용이 비슷해도 새 식별자를 쓰면 멱등성으로 합쳐지지 않는다. 두 요청이 동시에 실행되려 할 때는 아래의 잠금과 활성 실행 제약이 별도로 막는다. 활성 범위는 사용자 한 명이나 원천 하나가 아니라, 네 원천이 만드는 정식 통합재고 전체다.

### 2. 데이터베이스의 짧은 행 잠금

실행권을 결정하는 짧은 구간에서는 Oracle의 **비관적 락**을 사용한다. 비관적 락은 “다른 요청도 동시에 들어올 수 있다”고 가정하고, 한 요청이 실행 상태를 확인하고 기록을 만드는 동안 같은 실행권 행을 다른 요청이 바꾸지 못하게 하는 방식이다.

잠금은 동기화가 끝날 때까지 유지하지 않는다. 실행 가능 여부를 판단하고 실행 기록을 만든 뒤 바로 놓는다. 잠금을 기다리는 최대 시간도 5초로 제한했다. 그 안에 실행권을 얻지 못하면 서버는 무작정 대기하지 않고, 이미 다른 요청이 처리 중이라는 충돌 응답을 보낸다.

이렇게 범위를 좁힌 이유는 분명하다. 긴 작업 전체에 잠금을 걸면 중복 실행은 막기 쉽지만, 장애가 났을 때 다른 요청까지 오래 붙잡고 데이터베이스 연결도 낭비한다.

### 3. 데이터베이스의 유일성 제약

애플리케이션 검사가 예상치 못한 경쟁 조건을 놓치더라도, 데이터베이스가 동시에 활성 상태인 실행 기록이 둘 생기지 않도록 마지막 방어선을 둔다. 화면 확인, 서버 잠금, 데이터베이스 제약은 같은 일을 중복하는 것이 아니라 서로 다른 실패 지점을 막는다.

| 선택지 | 장점 | 이 구조에서의 한계 |
| --- | --- | --- |
| 서버 메모리 잠금 | 구현이 단순하고 빠르다. | 서버가 여러 대면 각자 다른 잠금을 보게 된다. 재시작하면 상태도 사라진다. |
| Redis 분산 잠금 | 여러 서버가 빠르게 공유할 수 있다. | 별도 인프라와 만료·장애 정책을 운영해야 한다. |
| Oracle 행 잠금 | 실행 이력과 같은 저장소에서 트랜잭션으로 관리할 수 있다. | 잠금 범위와 대기 시간을 잘못 잡으면 데이터베이스 경합이 커진다. |
| 낙관적 락 | 충돌이 드물 때 잠금 대기가 적다. | 실행 시작처럼 충돌 자체를 먼저 막아야 하는 구간에서는 재시도 설계가 복잡해진다. |

이 프로젝트는 실행 이력을 이미 Oracle에 저장하고 있었고, 실행 시작 경쟁도 같은 트랜잭션에서 판단해야 했다. 그래서 **짧은 Oracle 행 잠금과 유일성 제약**을 선택했다.

### 4. 실행 남용을 막는 속도 제한

동시에 하나만 실행되게 했다고 해서 반복 요청 문제가 사라지지는 않는다. 한 사용자가 실행이 끝날 때마다 계속 요청하면 데이터베이스와 배치 작업은 쉬지 못한다. 같은 사용자는 요청 사이에 최소 10초를 두고 한 시간에 최대 60회까지만 실행하도록 제한했다. 제한을 넘으면 서버가 다시 시도할 시간을 함께 알려 준다.

속도 제한은 시스템 남용을 줄이는 장치이고, 잠금과 유일성 제약은 같은 순간 두 작업이 활성화되는 것을 막는 장치다. 둘은 보호하는 문제가 다르므로 어느 하나로 다른 하나를 대신할 수 없다.

## 오래 걸리는 작업은 웹 요청에서 분리한다

네 원천을 읽고 검증한 뒤 여러 테이블을 갱신하는 작업은 몇 초 이상 걸릴 수 있다. 웹 요청을 그 시간 내내 열어 두면 다음 문제가 생긴다.

- 브라우저나 중간 장비의 시간 제한에 걸릴 수 있다.
- 사용자는 응답이 없는 화면을 보며 다시 버튼을 누르기 쉽다.
- 서버의 웹 요청 처리 자원이 오래 점유된다.
- 작업은 진행 중인데 네트워크만 끊겨 실패처럼 보일 수 있다.

그래서 서버는 요청을 검증하고 실행 기록을 확정한 뒤 **HTTP 202 Accepted**, 즉 “작업을 접수했지만 아직 완료되지는 않았다”는 응답을 돌려준다. 화면은 이때 받은 실행 식별자로 진행 상태를 조회한다.

실행 기록을 먼저 확정한 다음 백그라운드 작업을 시작한다. 데이터베이스 반영이 끝나기도 전에 작업을 시작하면, 백그라운드 작업이 존재하지 않는 실행 기록을 조회하는 경쟁 조건이 생길 수 있다. 현재 구조는 요청 트랜잭션이 끝난 뒤 Spring Batch 작업을 등록해 이 틈을 막는다.

Spring Batch는 작업 실행 이력과 상태처럼 중단된 작업의 재시작 여부를 판단하는 정보를 관리한다. 현재는 읽기·변환·쓰기를 각각 독립된 청크 단계로 나누지 않았다. 하나의 작업 단계가 전체 동기화 흐름을 조정한다. Spring Batch는 실행 생명주기를 맡고, 원천별 500행 읽기와 묶음 쓰기, 전체 검증과 최종 반영은 업무 코드가 관리하는 구조다.

Spring Batch를 쓴다고 해서 모든 업무가 자동으로 복구되는 것은 아니다. 어떤 상태를 다시 실행해도 안전한지, 오래 멈춘 작업을 누가 발견할지, 업무 데이터와 실행 이력을 어디까지 함께 되돌릴지는 애플리케이션이 정해야 한다. 현재 복구 실행은 저장된 페이지 중간 상태를 이어받지 않고 첫 원천 페이지부터 다시 읽는다. 읽기 비용을 다시 치르는 대신, 메모리의 중간 결과까지 영구 저장하고 정확히 복원하는 복잡성을 피했다.

현재는 동시에 등록할 수 있는 백그라운드 작업 수를 제한해 요청이 몰릴 때 서버 스레드가 무한히 늘어나지 않도록 했다. 큐가 가득 차면 “접수는 되었는데 언젠가 실행되겠지”라고 숨기지 않고, 실행 시작 실패 상태를 명시적으로 기록한다.

데이터베이스 접수가 끝난 직후 작업 등록 전에 서버가 종료되면 대기 기록만 남을 수 있다. 5분이 지난 대기 기록을 새 작업 세대로 바꾸는 복구 서비스와 명령 객체는 구현되어 있다. 그러나 이 명령을 호출할 운영용 API나 CLI 어댑터, 대기 기록을 자동 탐색하는 감시기는 아직 연결되지 않았다. 따라서 현재 코드는 복구의 핵심 규칙을 갖췄지만, 운영자가 실제로 호출할 수 있는 완성된 복구 경로까지 제공한다고 볼 수는 없다.

## 한 번에 최대 500행씩 읽는 이유

원천 데이터가 많다고 해서 한 번의 데이터베이스 조회로 전부 가져오지는 않는다. 오프라인, 이커머스, 그리팅, 물류센터 순서로 원천별 최대 500행씩 읽고 정식 테이블에 쓸 때도 최대 500행 단위로 SQL 요청을 나눈다. 처리 순서는 진행 흐름을 일정하게 만들 뿐, 뒤에서 읽은 원천이 무조건 우선한다는 뜻은 아니다.

500은 한 번의 데이터베이스 읽기와 쓰기 요청에 포함하는 최대 행 수다. 전체 동기화 건수나 저장 확정 단위는 아니다. 500행을 넘으면 다음 묶음을 계속 처리하며, 500행마다 앞부분의 성공이 따로 남지는 않는다.

읽기는 마지막으로 확인한 안정적인 키 다음부터 이어 가는 **키셋 페이지네이션**을 사용한다. 단순히 “몇 번째 묶음인지”로 이동하는 방식보다, 앞쪽 데이터가 추가되거나 삭제될 때 중복·누락이 생길 가능성을 줄일 수 있다.

한 시도 안에서는 원천 데이터의 버전도 고정한다. 읽는 도중 원천 버전이 바뀌면 “앞부분은 이전 버전, 뒷부분은 새 버전”인 혼합 결과를 만들지 않고 전체 시도를 중단한다. 운영자는 다시 실행해 한 버전의 일관된 결과를 얻는다.

500이라는 크기는 절대적인 정답이 아니다. 너무 작으면 데이터베이스 왕복 횟수가 늘고, 너무 크면 한 번에 사용하는 메모리와 SQL 크기가 커진다. 현재 값은 33,358행의 검증 자료를 다루기 위한 구현 기준이며 최적값을 입증한 성능 수치는 아니다. 실제 운영에서는 처리 시간·메모리·데이터베이스 부하를 측정해 조정해야 한다.

한 가지 한계도 있다. 조회 자체는 500행씩 하지만, 변경 후보 전체는 검증과 반영을 위해 메모리에 모은다. 현재는 최대 10만 건으로 상한을 두고 넘으면 실패시킨다. 즉, 페이지 조회가 곧 전체 메모리 사용량의 상한을 의미하지는 않는다. 데이터가 이 범위를 넘어가면 임시 적재 테이블이나 스트리밍 기반 구조로 옮겨야 한다.

## 공통 형식화와 검증은 반영 전에 끝낸다

실행 안전장치만으로는 잘못된 원천 값의 반영을 막지 못한다. 활성 원천의 연결표가 `MAPPED` 상태인지와 필수 정식 식별자·원천 행이 존재하는지 먼저 검사하고, 마지막 성공 지문과 달라진 후보만 공통 형식으로 읽은 뒤 수량·필수 값·같은 실행 후보 사이의 충돌을 검증한다. 후보가 된 값도 정식 데이터와 다시 비교해 실제 차이가 없으면 쓰지 않는다. 변경되지 않은 원천 행까지 매 실행마다 다시 비교하는 구조는 아니며, 이 범위는 [첫 번째 글](/blog/integrated-inventory-source-normalization)에 한계로 명시했다.

이 글은 `MAPPED` 연결 검사부터 정식 값 비교까지를 실행 경계로만 다룬다. 원천 4종의 컬럼을 어떤 의미로 맞췄는지, 연결표와 해시가 각각 어떤 문제를 해결하는지, 수요예측·안전재고·LOT로 위험 등급을 어떻게 산출하는지는 [첫 번째 글](/blog/integrated-inventory-source-normalization)에 정리했다.

## 정식 재고와 위험 판정은 같은 트랜잭션에서 확정한다

검증을 통과하면 정식 재고, LOT 정보, 재고 정책 등 기존에 연결된 대상을 갱신한다. 이 동기화는 새로운 상품이나 창고를 자동으로 생성하지 않는다. 검증된 기존 식별자를 기준으로 현재 값을 갱신하는 구조다.

쓰기 요청은 데이터베이스 부담을 줄이려고 500행씩 나누지만 **500행마다 저장을 확정하지는 않는다.** 정식 재고 반영과 위험 판정 저장은 모두 성공해야 한꺼번에 확정되는 하나의 업무 묶음, 즉 트랜잭션으로 처리한다. 마지막 단계에서 오류가 나면 앞에서 갱신한 정식 재고도 함께 되돌아간다.

원천 하나를 처리할 때 화면에는 데이터 검증, 원천 읽기, 공통 형식 변환이 차례로 보인다. 이 세 단계는 네 원천마다 반복된다. 모든 원천 처리가 끝나면 통합재고 반영과 위험 판정으로 넘어간다.

내부 상태 코드를 그대로 노출하지 않고 사용자가 지금 무엇을 하는지 이해할 수 있는 말로 바꿨다. 대기, 실행 중, 완료뿐 아니라 원천 변경 감지로 중단, 중단 후 복구 대기, 실행 시작 실패도 구분한다.

## 위험 판정도 이번 동기화의 결과로 저장한다

위험 판정을 조회할 때마다 다시 계산하면 같은 동기화 결과도 조회 시점의 참조 데이터에 따라 다르게 보일 수 있다. 동기화 트랜잭션은 영향받은 범위의 등급·이유·규칙 버전·재고일수를 저장하고, 목록과 상세는 저장된 결과를 읽는다.

저장된 위험 결과를 읽으면 목록 요청마다 수요예측과 모든 LOT를 다시 조회해 규칙 엔진을 실행하지 않아도 된다. 현재 위험 규칙 버전은 `v1.3.0`이며, 수요예측이 없거나 유효하지 않은 범위는 예측 규칙을 제외하되 `NORMAL` 하한과 사유를 저장한다. 규칙이 바뀌면 기존 결과의 재평가 시점을 정하는 정책이 필요하다. 현재는 다음 재고 동기화가 영향을 받은 범위를 갱신하며, 과거 전체를 즉시 다시 계산하는 별도 재평가 작업은 두지 않았다.

## 오래된 작업자는 새 결과를 덮어쓸 수 없다

백그라운드 작업은 서버 장애나 일시적인 정지 때문에 예상보다 오래 멈출 때가 있다. 복구 서비스는 생존 신호가 오래된 실행을 중단·복구 대기 상태로 바꾸고 새 작업 세대를 만들 수 있다.

문제는 이전 작업이 뒤늦게 다시 움직이는 경우다. 상태만 “실행 중”인지 확인하면, 오래된 작업이 새 시도의 결과를 덮어쓸 수 있다.

이를 막기 위해 실행마다 **작업 세대 번호**를 부여한다. 작업자는 읽기, 변환, 검증, 반영, 위험 판정처럼 중요한 단계로 넘어갈 때마다 자신이 여전히 현재 세대인지 확인한다. 새 시도가 시작되어 세대가 바뀌었다면 이전 작업의 상태 변경과 결과 확정을 거부한다. 분산 시스템에서는 이런 방식을 보통 **펜싱 토큰**이라고 부른다. 문을 잠그는 것에 그치지 않고, 오래된 열쇠로 들어온 작업의 쓰기까지 차단하는 장치다.

현재 구현에는 작업 세대와 생존 신호를 검사하는 복구 핵심 로직과 명령 경계가 있다. 반면 이를 외부에서 실행할 운영용 API·CLI 어댑터와 자동 감시기는 없다. 따라서 안전한 재시도의 기반은 마련됐지만, “운영자가 지금 수동 복구할 수 있다”거나 “자동 복구된다”고 설명해서는 안 된다.

복구 시에는 마지막으로 읽은 위치부터 이어 가지 않고 네 원천을 처음부터 다시 읽는다. 변경 지문과 실제 값 비교 덕분에 같은 값을 다시 쓰는 일은 줄지만, 읽기 비용은 반복된다. 현재 규모에서는 마지막 처리 위치를 영구 저장하는 복잡성보다 복구 절차의 단순함을 택했다.

## 대시보드와 통계는 왜 별도 작업인가

정식 재고와 위험 판정이 확정된 뒤에는 대시보드와 통계용 스냅샷을 만든다. 이 집계까지 핵심 트랜잭션에 넣으면 다음 문제가 생긴다.

- 집계가 느릴수록 정식 재고 확정도 함께 늦어진다.
- 통계 한 건의 실패 때문에 올바르게 만든 정식 재고와 위험 판정까지 되돌아간다.
- 긴 트랜잭션이 데이터베이스 잠금과 로그 사용량을 키운다.

그래서 핵심 트랜잭션이 끝난 뒤 대시보드와 통계를 별도 작업으로 생성하고, 동시에 실행할 개수를 제한하도록 코드를 구성했다. 하나가 실패해도 다른 하나와 핵심 동기화 결과는 유지하는 것이 목표다.

V27 migration이 적용된 환경에서는 실행을 빠르게 넘기는 executor 큐가 서버 메모리에 있더라도, 작업의 권위는 DB task 행에 남도록 설계했다. canonical 반영 트랜잭션이 대시보드와 재고통계 task를 함께 만들고, worker가 실행할 task를 원자적으로 선점해 10분 lease와 시도 횟수를 기록한다. 연결 단절·일시적 DB 자원 장애만 최대 세 번 실행하고, 같은 입력으로 해결되지 않는 직렬화·검증·무결성 오류는 첫 시도에서 `FAILED`로 끝낸다. 60초 복구기는 실행 시점이 된 task와 만료된 lease를 다시 예약하며, 스냅샷과 task의 실행별 유일성 제약은 같은 결과의 중복 저장을 막는다. 초기 `INSERT ALL` 방식은 두 task를 한 번에 만들 때 Oracle PK 충돌(`ORA-00001`)을 일으킬 수 있었고, 현재는 `(run_id, task_type)` 기준 `MERGE`로 바꿔 재시도와 중복 호출을 멱등하게 처리한다.

이 방식은 새 메시지 브로커 없이 Oracle 상태만으로 재시작 누락과 최대 시도를 설명할 수 있다는 장점이 있다. 반면 task table과 scanner를 운영해야 하고, core 원천 동기화 자체의 자동 복구까지 담당하지는 않는다. 개발 환경에서 V27 migration과 수정된 task mapper를 적용한 뒤 원천 33,358건 동기화를 실행했고, 읽기·매핑·반영 33,358건과 오류 0건, 대시보드·통계 task 성공을 확인했다. 운영 환경의 장애 주입과 부하 측정은 별도 검증 대상이다.

## 브라우저는 완료 상태를 어떻게 확인하는가

화면은 작업 중일 때만 실행 상태를 주기적으로 확인한다.

- 실행 대기 중에는 비교적 짧은 3초 간격으로 확인한다.
- 실제 실행이 시작되면 10초 간격으로 확인해 불필요한 요청을 줄인다.
- 핵심 반영 성공 뒤 스냅샷 생성 중에는 완료 후 1분까지 3초, 1~5분은 10초 간격으로 확인한다.
- task가 실패하거나 두 스냅샷이 모두 준비되거나 화면이 백그라운드로 가면 반복 확인을 멈춘다. task 상태를 알 수 없는 경우에도 5분 뒤에는 자동 조회와 대기 표시를 끝낸다.

### 왜 SSE 대신 상태 API 폴링을 선택했나

`QUEUED → RUNNING → SUCCEEDED/FAILED` 상태는 비교적 적게 바뀐다. 이미 접수 응답과 실행 번호, 상태 조회 API가 있어 현재 범위에서는 간격을 조절한 폴링을 택했다. SSE는 서버가 상태 변화를 바로 밀어 불필요한 빈 응답과 화면 지연을 줄일 여지가 있다.

폴링은 상태가 바뀐 직후 다음 주기까지 화면 반영이 늦을 수 있고, 여러 사용자가 동시에 보고 있으면 같은 상태 API를 반복 호출한다. 실행 단계별 간격을 다르게 두고, 백그라운드 탭·완료·실패·5분 상한에서 자동 조회를 멈췄으며, 완료 직후에는 0~3초의 작은 무작위 지연으로 재조회 시점을 흩었다.

SSE로 바꾸려면 연결 수뿐 아니라 인증 만료, 프록시 타임아웃, 재연결 시 마지막 이벤트 복구, 여러 탭의 중복 연결을 함께 설계해야 한다. 상태 API 호출량과 완료 감지 지연이 실제 문제가 되는지 측정하기 전에는 기술을 추가하지 않았다.

이 **폴링**은 진행 상황을 보여 주는 방법이지, 중복 실행을 막는 장치가 아니다. 중복 실행 방지는 앞에서 설명한 서버의 멱등성, 데이터베이스 잠금, 유일성 제약이 담당한다.

변경이 있는 성공을 확인하면 화면은 먼저 재고 목록, 요약, 상세, LOT, 위험 현황을 다시 조회한다. 대시보드와 통계는 아직 만드는 중일 수 있으므로 run API의 준비 상태가 각각 true가 된 뒤 해당 조회만 다시 요청한다. TanStack Query에서는 이를 캐시 무효화라고 한다. 데이터가 오래되었다고 판단하는 기준과 화면에서 더는 쓰지 않는 데이터를 메모리에서 지우는 기준은 서로 다르다. 둘을 같은 캐시 시간으로 이해하면 새로 고침 정책을 잘못 설계하기 쉽다.

### 목록과 상단 요약은 같은 필터 계약을 사용한다

재조회 시점만 같아도 목록과 요약이 서로 다른 질문을 보내면 화면은 일관되지 않는다. 실제 회귀 테스트에서 목록 요청에는 `OR`가 전달되지만 요약 API 파라미터와 캐시 키에서는 `filterOperator`가 빠진 문제를 찾았다. 이 상태에서는 목록이 여러 활성 필터 그룹 중 하나만 만족하는 재고를 보여 주는 동안 상단 KPI는 기본 `AND`로 모든 그룹을 만족하는 재고만 셀 수 있다. 요약 조회의 허용 파라미터와 조회 키에 연산자를 함께 포함해 두 응답의 조건을 맞췄다.

서버는 `AND`와 `OR`만 허용하며, 같은 그룹의 여러 선택값은 항상 `OR`로 묶는다. MyBatis도 사용자 입력을 SQL에 그대로 치환하지 않고 `<choose>`로 고정된 논리 연산자만 렌더링한다. 종합 위험은 판매처별 행을 필터한 뒤 다시 계산하지 않는다. 유효한 모든 판매처·미할당 범위에서 SKU 종합 위험을 먼저 확정하고, 목록·전체 건수·상단 요약이 같은 값을 사용한다.

이 변경은 필터 결과의 정확성을 맞춘 작업이다. 실제 Oracle에서 CTE와 조건 조합의 응답 시간이 개선됐다고 주장할 측정값은 아직 없으며, 혼합 위험 SKU smoke test와 대표 실행계획 수집은 별도로 남아 있다.

여러 브라우저가 완료를 같은 순간 확인해 조회 요청이 몰리지 않도록, 성공 뒤 다시 불러오는 시점에는 0~3초의 작은 무작위 지연을 둔다. 반면 수요예측은 이번 동기화가 직접 다시 계산하는 결과가 아니므로 자동 갱신 대상에서 제외했다.

요청 전송 도중 연결이 끊겨 접수 성공 여부를 모를 때는 같은 요청 식별자를 다시 사용한다. 서버에서 성공 또는 실패가 확인된 뒤 사용자가 새 실행을 선택할 때만 새 식별자를 만든다. 이미 다른 세션이나 예약 실행이 진행 중이면 그 실행 번호를 이어서 추적한다. 속도 제한, 상태 확인 실패, 복구 대기 역시 하나의 일반 오류로 뭉개지 않고 각각 다른 안내와 재시도 동작을 제공한다.

상태 변화는 색만으로 구분하지 않고 보조기술이 읽을 수 있는 알림으로 전달한다. 키보드만으로 실행과 수동 재시도를 할 수 있고, 상태 조회가 잠시 실패하더라도 마지막으로 확인한 정상 상태를 지우지 않는다.

`changedCount`는 정식 재고에 실행한 DML 건수다. 이 값이 0이면 서버는 후속 스냅샷 task를 만들지 않고, 화면도 목록·상세·LOT·위험·대시보드·통계를 자동 재호출하지 않는다. 정식 재고가 그대로인 실행의 무거운 집계와 API 요청을 줄이기 위한 경계다. 변경이 있으면 화면은 `집계 최신화 중`을 표시하고 두 스냅샷이 DB에 저장됐다는 응답을 받은 뒤에만 새 집계를 요청한다.

여기에는 분명한 빈틈이 있다. 정식 재고 DML은 0이어도 영향 범위의 위험 판정은 다시 평가·저장될 수 있다. 현재 `changedCount`만으로는 이 **위험 판정만 변경된 실행**을 구분하지 못하므로, 화면의 위험 캐시가 자동 갱신되지 않을 수 있다. 따라서 `changedCount = 0`을 “아무 처리도 없었다”는 뜻으로 쓰지 않고, 후속 조건을 정식 재고 변경 건수와 위험 변경 건수로 나누는 작업을 남은 과제로 둔다.

### 쓸모없는 호출을 줄인 지점과 아직 하지 않은 것

| 구분 | 현재 동작 | 해석 |
| --- | --- | --- |
| 정식 재고 DML 0건 | `changedCount = 0`이면 후속 snapshot task와 자동 재조회 생략 | 불필요한 호출은 줄지만 위험 판정만 바뀐 실행을 놓칠 수 있음 |
| 변경 있는 동기화 | canonical·위험 반영 후 목록/요약/상세를 먼저 무효화하고, snapshot 준비 완료 후 대시보드·통계만 선택적으로 재조회 | 핵심 데이터와 부가 집계의 시점을 분리함 |
| 실행 상태 확인 | `QUEUED` 3초, `RUNNING` 10초, snapshot 대기 초반 3초 후 10초, 최대 5분 | 상태 API를 무한 호출하지 않음 |
| 실시간 전송 | SSE/WebSocket 미사용, 폴링 사용 | 현재는 구현·운영 복잡도보다 API 계약 검증을 우선함. 연결 수와 지연을 측정한 뒤 다음 선택을 할 수 있음 |
| DB 인덱스·파티션·실행계획 | 이번 글의 구현 범위에서 새 인덱스를 추가했다고 주장하지 않음 | 실제 Oracle 통계와 계획 없이 “인덱스로 빨라졌다”고 쓰지 않음 |

## 코드로 확인한 성과와 실제 환경에서 남은 검증

| 코드·테스트로 확인한 것 | 아직 남은 과제 |
| --- | --- |
| 같은 요청은 하나의 core 실행 결과로 묶인다. V27 task의 시도·lease·최종 실패 상태는 코드와 정적 계약에 구현되어 있다. | V27의 실제 Oracle 적용과 장애 주입 smoke 검증이 남아 있다. |
| 네 원천이 만드는 정식 통합재고 전체에는 하나의 활성 동기화만 시작된다. 복구 핵심 로직은 작업 세대를 갱신한다. | 복구 명령을 호출할 운영용 API·CLI 어댑터와 자동 감시기가 없다. |
| 한 시도는 같은 원천 버전만 사용한다. | 새 상품·창고·원천 삭제를 자동으로 정식 데이터에 전파하지 않는다. |
| 정식 재고와 위험 판정은 함께 확정되거나 함께 되돌아간다. | 전체 변경 후보를 메모리에 모으므로 매우 큰 규모에는 임시 적재 구조가 필요하다. |
| 목록·전체 건수·상단 KPI는 같은 필터 연산자와 SKU 종합 위험을 사용한다. | 실제 Oracle의 혼합 위험 데이터 smoke test와 대표 조건 실행계획 수집은 남아 있다. |
| 오래된 core 작업 세대의 상태 변경과 결과 확정은 거부된다. | 폴링보다 정밀한 실시간 알림과 스냅샷 세대 표시는 추후 개선 대상이다. |
| 정식 재고 `changedCount`가 0이면 후속 task와 자동 재조회를 생략한다. | 위험 판정만 다시 저장된 실행을 별도 변경 건수로 감지해야 한다. |
| 화면에는 내부 상태 코드 대신 이해할 수 있는 한국어 상태를 표시한다. | 처리량, 잠금 대기, 후속 집계 지연을 운영 지표로 더 세분화할 필요가 있다. |

“정확히 한 번만 실행된다”는 표현은 의도적으로 쓰지 않았다. 네트워크와 장애가 있는 시스템에서 그 말은 지나치게 넓은 보장을 암시한다. 현재 구조가 실제로 보장하는 것은 **같은 요청 식별자를 하나로 묶고, 정식 통합재고 전체의 활성 작업을 하나로 제한하며, 오래된 작업의 쓰기를 거부하고, 핵심 결과를 모두 함께 확정하거나 함께 되돌리는 것**이다.

## 핵심 트레이드오프 정리

| 설계 선택 | 얻은 것 | 치른 비용 |
| --- | --- | --- |
| 짧은 비관적 락과 유일성 제약 | 여러 서버에서도 실행 시작 경쟁을 막는다. | 잠금 대기 시간과 충돌 응답을 운영해야 한다. |
| 접수 응답과 Spring Batch 분리 | 긴 작업이 웹 요청을 붙잡지 않는다. | 화면 상태 조회와 작업 복구 정책이 필요하다. |
| 500행 단위 읽기·쓰기 | 한 번의 SQL과 메모리 급증을 줄인다. | 데이터베이스 왕복 횟수가 늘며, 크기를 튜닝해야 한다. |
| 원천 버전 고정과 해시 비교 | 혼합 스냅샷을 막고 변경 후보를 빨리 찾는다. | 원천이 자주 바뀌면 시도가 실패할 수 있고 지문 규칙을 관리해야 한다. |
| 핵심 업무 하나의 트랜잭션 | 정식 재고와 위험 판정의 불일치를 막는다. | 변경량이 커질수록 트랜잭션 시간과 메모리 부담이 커진다. |
| 제한된 후속 스냅샷 + V27 task 설계 | 핵심 반영과 부가 집계를 분리하고, DB task로 일시 실패·재시작 누락을 복구할 수 있다. | 실제 Oracle 적용·장애 검증 뒤에만 운영 보장할 수 있고 task table, lease, scanner 운영이 추가된다. |
| 위험 판정 결과 저장 | 같은 실행의 등급과 이유를 일관되게 설명한다. | 규칙 변경 뒤 과거 결과를 다시 계산하려면 별도 재평가가 필요하다. |

## 기술 용어를 다시 풀어보면

| 용어 | 이 기능에서 맡은 일 | 이것만으로 해결되지 않는 문제 |
| --- | --- | --- |
| 서버 페이지네이션 | 목록을 기본 20개·최대 100개씩 잘라 전송 | 깊은 `OFFSET` 페이지의 DB 비용 |
| TanStack Query | 조건별 서버 응답을 캐시하고 필요한 조회만 다시 요청 | 서버 SQL 자체의 병목 |
| 멱등성 | 같은 요청 식별자의 재전송을 기존 실행과 연결 | 서로 다른 식별자의 동시 요청 |
| 비관적 락 | 실행 시작 판단을 짧게 한 요청씩 처리 | 긴 작업 전체의 생명주기와 복구 |
| 유일성 제약 | 활성 실행 두 개가 저장되는 것을 DB에서 최종 차단 | 어떤 실행이 최신인지 판단하는 세대 관리 |
| 트랜잭션 | 정식 재고와 위험 판정을 함께 확정하거나 되돌림 | 커밋 뒤 실행되는 대시보드·통계 집계 |
| 펜싱 토큰 | 복구 뒤 살아난 오래된 작업의 쓰기를 거부 | 고아 작업을 자동으로 발견해 재시작하는 정책 |
| 폴링 | 작업 상태 API를 필요한 간격으로 다시 조회 | 서버가 즉시 밀어주는 실시간 알림 |
| SSE | 서버가 한 HTTP 연결로 상태 변화를 계속 보내는 대안 | 재연결·프록시·다중 탭·연결 수 운영이 추가로 필요 |
| 캐시 무효화 | 바뀐 데이터와 연결된 조회만 오래된 것으로 표시 | 현재의 `changedCount`만으로는 위험 판정만 바뀐 실행을 판별하지 못함 |

한 기술이 전체 문제를 해결하지는 않는다. 멱등성은 재전송을, 락은 시작 경쟁을, 유일성 제약은 마지막 저장 경쟁을, 펜싱은 오래된 작업의 늦은 쓰기를 맡는다. 역할을 섞으면 “멱등 키가 있으니 동시성도 해결됐다”거나 “비관적 락을 작업 끝까지 잡아야 안전하다”는 잘못된 결론으로 이어진다.

## 자주 묻는 질문

### 데이터베이스 잠금은 동기화가 끝날 때까지 유지하나?

아니다. 실행 가능 여부를 확인하고 실행 기록을 만드는 짧은 구간에만 사용한다. 실제 원천 읽기와 반영은 작업 세대, 원천 버전, 업무 트랜잭션으로 보호한다.

### 한 번에 500행이면 전체 데이터가 500행을 넘을 수 없나?

아니다. 500은 한 번의 읽기 또는 쓰기 요청 크기다. 다음 묶음을 계속 처리한다. 다만 변경 후보 전체를 메모리에 모으므로 현재는 별도의 10만 건 상한이 있다.

### Spring Batch를 쓰면 실패한 작업이 자동으로 복구되나?

아니다. Spring Batch는 실행 상태와 재시작 기반을 제공한다. 어떤 작업을 언제 다시 실행할지, 재실행이 업무상 안전한지는 별도 정책과 구현이 필요하다. 현재는 작업 세대와 생존 신호를 검사하는 복구 서비스·명령 객체까지만 있고, 운영자가 호출할 API·CLI 어댑터와 자동 감시기는 없다.

### 수요 예측이 없으면 위험하지 않다고 판단하나?

아니다. 예측이 필요한 규칙만 제외하고 가용 수량, 안전재고, LOT로 판단할 수 있는 위험은 계속 평가한다. 현재 `v1.3.0`은 예측 누락·무효 사유를 `NORMAL` 하한으로 저장하므로, 서버 룰상 다른 위험이 없어도 `SAFE`로 확정하지 않는다. 가용 수량 자체가 없으면 0으로 보아 가장 보수적으로 `DANGER` 처리한다.

### `OR` 필터를 선택하면 목록과 상단 KPI가 다른 조건을 쓰나?

아니다. 주소의 `filterOperator=OR`가 목록과 요약 API 파라미터 및 각각의 캐시 키에 함께 들어간다. 서버의 목록·전체 건수·요약 SQL도 같은 그룹 결합 방식과 미리 확정한 SKU 종합 위험을 사용한다.

### 동기화 성공인데 대시보드가 잠시 이전 값일 수 있나?

서버의 핵심 성공은 정식 재고와 위험 판정의 확정을 뜻하므로 스냅샷 생성 중에는 짧은 지연이 있다. 화면은 이때 `집계 최신화 중`을 표시하고, 각 스냅샷이 DB에 저장됐다는 준비 상태를 받은 뒤 해당 API를 다시 요청한다.
