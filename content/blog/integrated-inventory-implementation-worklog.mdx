재고관리 서비스에는 오프라인 매장, 이커머스, 식단 서비스인 그리팅, 물류센터처럼 성격이 다른 원천이 함께 들어옵니다. 문제는 이 데이터가 모두 ‘재고’라는 이름을 쓰면서도 상품을 식별하는 방법, 수량의 뜻, 갱신 시점이 서로 다르다는 점이었습니다.

제가 맡은 범위는 이 데이터를 단순히 한 화면에 모으는 데서 끝나지 않았습니다. 통합재고 목록과 상세 조회를 만들고, 수요예측과 안전재고를 이용해 위험을 판정하고, 네 원천의 변경분을 정식 재고에 반영하는 실행 흐름까지 연결했습니다.

이 글은 세밀한 코드 문법보다 다음 질문에 답하는 데 초점을 맞춥니다.

- 어떤 서비스 문제 때문에 이 기능이 필요했는가
- 문제가 커질 것을 예상해 어떤 경계를 두었는가
- Oracle, Spring Boot, MyBatis, Spring Batch, React, TanStack Query를 어디에 사용했는가
- 더 단순한 방법을 두고 현재 방식을 선택한 이유와 비용은 무엇인가
- 실제 구현은 어떤 순서로 확장되었는가

글에서 자주 나오는 SKU는 용량·옵션까지 구분한 실제 판매·재고 관리 단위입니다. LOT는 같은 조건으로 생산되거나 입고되어 유통기한과 상태를 함께 관리하는 재고 묶음을 뜻합니다.

## 먼저 보는 두 흐름: 동기화 상태와 조회 상태

이 글의 세부 내용을 읽기 전에 버튼을 눌렀을 때의 **동기화 상태**와, 반영된 재고를 읽을 때의 **조회 상태**를 분리해 보면 전체 구조가 훨씬 단순해집니다.

| 구분 | 기능이 움직이는 순서 | 이 단계가 끝났다는 뜻 |
| --- | --- | --- |
| 동기화 상태 | `QUEUED 접수` → `RUNNING 검증·읽기·정규화·반영` → `SUCCEEDED 핵심 반영` → `스냅샷 준비` → `화면 갱신` | 정식 재고와 위험 판정이 같은 핵심 트랜잭션으로 확정됨. 대시보드·통계는 뒤에서 별도 생성될 수 있음 |
| 조회 상태 | `URL 필터 복원` → `정식 재고 범위 확정` → `SKU 종합 위험 집계` → `후보 필터링` → `목록·건수·요약 반환` → `TanStack Query 캐시 갱신` | 원천 테이블을 매번 다시 합치지 않고, 같은 조건으로 목록과 상단 숫자를 보여 줌 |

즉, **동기화가 데이터를 바꾸는 쓰기 흐름**이라면 **조회는 이미 확정된 정식 재고를 빠르게 읽는 흐름**입니다. 현재 화면의 진행 상태 확인은 SSE가 아니라 `QUEUED`일 때 3초, `RUNNING`일 때 10초 간격의 폴링으로 구현했습니다. SSE를 넣지 않은 것은 실시간 알림 자체를 목표로 하기보다 현재 규모에서 작업 상태 API와 화면 갱신 계약을 먼저 안정화했기 때문이며, 운영 지표로 연결 지연과 동시 접속을 측정한 뒤 검토할 확장 지점으로 남겼습니다.

![승인된 기준선에서 원천 데이터를 만들고 연결 지도와 실행 메타데이터를 거쳐 동기화하는 구조](/images/blog/inventory-source-lifecycle-ai.png)

*생성 이미지 · 원천 데이터를 바로 정식 테이블에 덮어쓰지 않고, 승인 snapshot·연결 지도·실행 metadata를 통과시키는 이유를 한 장으로 표현했습니다. 실제 상태명과 보장 범위는 본문 표와 코드 계약을 기준으로 읽어야 합니다.*

### 문제 상황과 선택한 기술을 한 번에 연결하면

| 실제로 걱정한 문제 | 선택한 기술·설계 | 얻은 효과와 남은 비용 |
| --- | --- | --- |
| 네 원천의 컬럼명·수량 의미가 달라 잘못된 상품에 반영될 수 있음 | 원천별 MyBatis projection, 승인 연결표, 공통 형식 검증 | 변환 규칙이 한 경계에 모이지만 새 원천을 추가할 때 매핑 계약을 함께 관리해야 함 |
| 버튼을 두 번 누르거나 다른 탭에서 동시에 요청할 수 있음 | client request id 멱등성, 짧은 Oracle 비관적 락, 활성 실행 유일성 제약 | 같은 요청과 동시 실행을 구분해 막지만 잠금 경합·충돌 응답을 운영해야 함 |
| 수만 행을 읽는 동안 HTTP 요청이 끊길 수 있음 | Spring Batch 백그라운드 실행, 단계별 run 상태와 fencing token | 웹 요청은 빨리 끝나지만 상태 조회와 복구 판단이 필요함 |
| 목록마다 원천·LOT를 전부 조인하면 중복과 전송량이 커짐 | SKU grain 서버 페이지, 목록/상세 분리, 정식 재고 read model | 첫 응답의 데이터량을 줄이지만 실제 Oracle 응답 시간은 별도 측정이 필요함 |
| 판매처 필터 뒤에 종합 위험을 계산하면 결과가 달라짐 | `valid_scope_keys → sku_risk_agg → candidate_keys` CTE 순서 | 목록·건수·요약이 같은 위험 값을 보지만 CTE 실행계획은 운영 데이터로 확인해야 함 |
| 새로고침·뒤로 가기에서 필터와 완료 상태가 사라짐 | URL search params, TanStack Query query key와 조건부 invalidation | 링크 공유와 선택적 재조회가 가능하지만 URL·캐시 계약을 함께 유지해야 함 |

## 문제 1. 같은 ‘수량’이라도 뜻이 달랐다

재고 화면에서 가장 위험한 오해는 숫자가 보인다는 이유만으로 그 숫자를 곧바로 판매 가능 수량이라고 생각하는 것입니다.

예를 들어 총재고가 100개이고 이미 주문에 배정된 수량이 30개라면 새 주문에 사용할 수 있는 재고는 70개입니다. 그래서 화면과 API에서 다음 의미를 분리했습니다.

- 가용 수량: 지금 새 주문에 배정할 수 있는 수량
- 예약 수량: 이미 주문 등에 배정된 수량
- 총재고: 가용 수량과 예약 수량을 합한 수량
- 안전재고: 수요 변동과 공급 지연을 견디기 위해 남겨 둘 기준 수량

이 프로젝트의 저장 규칙에서는 이름이 ‘현재 보유 수량’처럼 보이는 값이 이미 가용 수량입니다. 예약 수량을 여기서 다시 빼지 않고, 총재고를 보여 줄 때만 두 수량을 더합니다. 예약분을 다시 빼면 같은 수량을 두 번 차감하는 오류가 생깁니다. 이 규칙을 서버의 공통 업무 모델에 두고 화면과 위험 판정이 같은 뜻을 쓰도록 했습니다.

모든 기능이 같은 기준을 쓴다는 게 가장 큰 장점입니다. 대신 원천마다 별도의 수량 의미가 추가될 때는 공통 모델과 변환 규칙도 함께 고쳐야 합니다. 편의를 좇아 의미를 뭉개기보다 변경 비용을 감수하고 경계를 명확히 한 선택입니다.

## 문제 2. 많은 재고를 한 번에 가져오면 조회가 느려진다

통합재고 목록은 상품, SKU, 판매처별 수량과 종합 위험 등급을 함께 보여 줍니다. 수요예측은 목록에 섞지 않고 판매처를 고른 상세 화면에서 별도로 조회합니다. 관계를 잘못 묶으면 한 SKU가 LOT·판매처 수만큼 중복되고, 전체 데이터를 브라우저에 내려 보낸 뒤 필터링하면 데이터가 늘수록 첫 화면이 느려집니다.

그래서 목록 조회는 서버가 다음 책임을 갖도록 설계했습니다.

1. 검색어, 채널, 판매처, 권역, 카테고리, 보관유형, 물류센터, 종합 위험 등급과 판정 상태를 조건으로 적용합니다.
2. 활성 필터 그룹을 모두 만족하는 `AND`와 하나 이상 만족하는 `OR`를 선택할 수 있게 합니다. 같은 그룹에서 여러 값을 고르면 그 값들은 `OR`로 묶습니다.
3. 정렬 기준과 페이지를 서버에서 계산하고, 전체 건수와 현재 페이지를 각각 구합니다.
4. 목록과 상단 요약 KPI가 같은 필터와 결합 연산자를 사용하게 합니다.
5. 목록에 필요한 정보만 SKU 한 행과 판매처 배열로 묶어 반환하고, LOT와 수요예측은 상세에서 별도로 조회합니다.

Oracle은 저장과 검색을 담당하고, MyBatis는 목록 목적에 맞춘 SQL을 명시적으로 제어하는 데 사용했습니다. 객체 관계를 자동으로 따라가는 방식보다 SQL이 길어질 수 있지만 어떤 조인과 조건이 실행되는지 확인하기 쉽고, 목록용 읽기 모델도 세밀하게 조정할 수 있었습니다.

여기서 읽기 모델은 데이터베이스 구조를 그대로 노출하는 객체가 아닙니다. ‘재고 목록을 보여 주는 데 필요한 값’을 한 응답으로 구성한 화면 목적의 데이터입니다. 쓰기 구조와 읽기 구조를 완전히 분리하는 대규모 아키텍처까지 도입하지는 않았지만, 적어도 화면마다 데이터베이스 관계를 임의로 조립하지 않도록 조회 경계를 만들었습니다.

이 선택으로 운영 응답 시간이 몇 퍼센트 줄었다고 말할 측정값은 아직 없습니다. 현재 확인한 결과는 서버 페이지 처리와 목록·상세 조회 계약이 테스트를 통과했다는 것입니다. 성능 향상을 입증했다기보다 데이터가 늘 때 브라우저가 전체 재고를 떠안는 구조를 피했다고 보는 편이 정확합니다.

### 종합 위험도는 판매처 필터보다 먼저 확정해야 했다

목록의 행은 SKU지만 저장된 위험 판정은 SKU와 판매처 범위에 가깝습니다. 이 차이를 놓치면 필터가 표시 결과 자체를 바꿀 수 있습니다.

기존 SQL은 판매처별 위험을 먼저 필터한 뒤 남은 판매처 행으로 SKU 종합 위험도를 다시 계산했습니다. 예를 들어 같은 SKU에 `DANGER` 판매처와 `SAFE` 판매처가 함께 있을 때 `SAFE`를 고르면, `DANGER` 행이 먼저 빠지고 남은 행만으로 SKU가 `SAFE`처럼 보일 수 있었습니다. 화면에 표시된 종합 위험도를 거른 것이 아니라, 필터를 통과한 일부 행으로 종합 위험도를 새로 만든 셈입니다.

이를 다음 순서로 바꿨습니다.

1. 삭제·비활성 데이터와 사용할 수 없는 물류센터를 제외한 유효 재고 범위를 먼저 고릅니다.
2. 유효한 모든 판매처·미할당 범위에서 SKU 종합 위험도를 계산합니다.
3. `DANGER → CAUTION → NORMAL → SAFE` 우선순위와 미판정 여부를 확정합니다.
4. 확정된 SKU 종합 위험도를 검색 후보에 적용합니다.
5. 목록 표시, 전체 건수, 상단 요약 KPI가 같은 종합 위험도를 사용합니다.

MyBatis의 목록·건수·요약 SQL은 각각 실행되지만 모두 `valid_scope_keys → sku_risk_agg → candidate_keys` 순서를 따릅니다. 이 변경은 응답 속도를 개선했다고 주장하기 위한 최적화가 아니라, “화면에 보이는 종합 위험도”와 “필터가 비교하는 위험도”를 같은 값으로 맞춘 정확성 수정입니다. CTE가 실제 Oracle에서 어떤 실행계획을 만드는지는 별도로 측정해야 합니다.

## 문제 3. 검색·필터·상세 상태가 화면 안에서만 사라졌다

재고 담당자는 검색하고, 위험 재고만 걸러 보고, 특정 상품의 상세를 연 뒤 그 주소를 다른 사람에게 공유할 수 있어야 합니다. 그런데 검색 조건을 React 컴포넌트 내부 상태에만 두면 새로고침이나 뒤로 가기에서 맥락이 사라집니다.

그래서 검색어, 필터, 정렬, 페이지, 열려 있는 상세 항목을 주소의 조회 문자열에 담았습니다. 주소가 화면 상태의 기준이 되기 때문에 다음 효과를 얻었습니다.

- 새로고침해도 같은 조건이 유지됩니다.
- 뒤로 가기와 앞으로 가기가 사용자의 탐색 흐름대로 동작합니다.
- 현재 보고 있는 재고 상태를 링크로 공유할 수 있습니다.
- 중복된 상태 저장소가 줄어듭니다.

필터 결합 방식도 주소 상태에 포함했습니다. 기본 `AND`는 주소에서 생략하고, `OR`를 고르면 `filterOperator=OR`로 남깁니다. 새로고침하거나 링크를 공유해도 결합 방식이 유지됩니다.

서버에서 받은 데이터는 TanStack Query로 관리했습니다. 검색 조건을 구조화한 조회 키를 사용해 서로 다른 조건의 결과가 섞이지 않게 했고, 다음 페이지를 가져오는 동안 직전 결과를 유지해 화면이 불필요하게 비지 않도록 했습니다.

이 과정의 회귀 테스트에서 목록 요청에는 `OR`가 전달되지만 요약 전용 조회 키를 만드는 목록에서 `filterOperator`가 빠진 문제도 찾았습니다. 그대로 두면 재고 목록은 `OR`, 상단 KPI는 기본 `AND`로 서로 다른 질문에 답할 수 있었습니다. 요약 API 파라미터와 캐시 키에 연산자를 함께 넣어 두 조회의 조건을 맞췄습니다.

서버는 `AND`와 `OR`만 허용하고 다른 값은 잘못된 요청으로 거부합니다. MyBatis에서도 요청 문자열을 SQL에 그대로 치환하지 않고 `<choose>`가 고정된 `AND` 또는 `OR` 토큰만 렌더링하도록 했습니다. 화면 상태 복원뿐 아니라 쿼리 안전성까지 같은 계약으로 묶었습니다.

주소 상태는 공유와 복원에 강하지만 모든 임시 상태를 담으면 주소가 복잡해집니다. 업무 맥락을 바꾸는 조건만 주소에 두고, 애니메이션이나 마우스 상태처럼 금방 사라지는 표현은 컴포넌트 안에 남겼습니다.

상세 패널은 단순히 오른쪽에 보이는 상자가 아니라 대화상자처럼 동작하도록 설계했습니다. 키보드로 닫을 수 있고 패널이 열린 동안 초점이 바깥으로 빠져나가지 않으며, 닫은 뒤에는 원래 조작하던 위치로 돌아갑니다. 접근성을 별도의 마감 작업이 아닌 기본 상호작용 규칙으로 다뤘습니다.

## 문제 4. 재고가 적다는 사실만으로 위험을 설명할 수 없었다

재고 20개가 충분한지는 판매 속도와 안전재고 기준에 따라 달라집니다. 그래서 단순한 임계값 하나 대신 다음 정보를 함께 보는 위험 판정을 만들었습니다.

- 현재 가용 수량
- 최근 판매를 바탕으로 계산한 수요예측
- 품목별 안전재고 기준
- LOT의 잔여 수량과 유통기한
- 판매 중지처럼 즉시 대응이 필요한 상태

결과는 정상, 주의, 위험처럼 운영자가 바로 판단할 수 있는 등급과 함께 저장합니다. 등급만 남기지 않고 ‘재고가 0임’, ‘예측 정보가 없어 해당 규칙을 제외함’, ‘유통기한이 가까움’ 같은 사유와 판정 규칙의 버전도 같이 기록했습니다.

### 일부 정보가 없을 때 전체 판정을 포기하지 않았다

초기 설계에서는 예측이나 정책이 없으면 판정 자체를 하지 않는 방식을 고려했습니다. 그러나 운영자는 일부 정보가 부족하더라도 현재 재고가 0이거나 LOT가 곧 만료된 사실은 알아야 합니다.

현재 규칙은 사용할 수 있는 정보로 계속 판정합니다.

- 가용 수량이 없으면 0으로 보아 가장 높은 위험과 결측 사유를 남깁니다.
- 예측이 없거나 올바르지 않으면 예측 기반 규칙만 제외합니다.
- 안전재고 기준이 없으면 그 규칙만 제외하고 이유를 남깁니다.
- 오래되었지만 형식상 유효한 예측은 사용하되, 오래된 자료라는 사실을 표시합니다.
- 음수 수량처럼 업무적으로 성립할 수 없는 값은 조용히 보정하지 않고 동기화를 실패시킵니다.

이 방식은 ‘모든 입력이 완벽해야만 결과가 나오는 시스템’보다 운영에 유용합니다. 대신 일부 정보로 내린 결과와 완전한 정보로 내린 결과를 구별할 수 있도록 사유와 입력 상태를 함께 보여 줘야 합니다.

보수적인 판단에는 오판 비용도 따릅니다. 재고 누락을 0으로 취급하면 안전하다고 잘못 말하는 일을 피하는 대신, 실제 재고가 남아 있어도 과도한 경보가 날 수 있습니다. 화면은 ‘실제 0’과 ‘값이 없어 0으로 간주함’을 판정 사유로 구분합니다. 예측이 없으면 예측 기반 부족 신호를 놓칠 수 있고, 기준일이 14일보다 오래된 예측을 계속 쓰면 낡은 수요 때문에 과대·과소 경보가 생길 수 있습니다. 그래서 결측과 노후 여부를 결과에 남겨 운영자가 등급의 근거를 함께 보게 했습니다.

판정 기준일과 예측 기준일도 분리했습니다. 예측이 언제 만들어졌는지와 오늘 LOT가 얼마나 남았는지는 다른 시간축입니다. 둘을 섞으면 과거 예측일을 기준으로 유통기한을 계산하는 오류가 생깁니다.

## 문제 5. 네 원천을 곧바로 정식 재고에 덮어쓸 수 없었다

오프라인, 이커머스, 그리팅, 물류센터는 서로 다른 열과 식별자를 사용합니다. 그래서 원천 테이블을 하나로 합쳐 버리는 대신, 원천의 모습을 보존한 채 공통 형식으로 번역하는 계층을 두었습니다.

전체 흐름은 다음과 같습니다.

1. 각 원천의 활성 행이 모두 승인된 연결표와 이어지는지 먼저 검사합니다.
2. 데이터베이스가 마지막 성공 지문과 다른 행만 변경 후보로 골라 최대 500행씩 읽습니다.
3. 후보의 서로 다른 열을 상품, SKU, 판매지점, 수량 같은 공통 의미로 바꿉니다.
4. 필수값·수량·날짜를 검증하고, 여러 원천이 같은 값을 주장하면 충돌 규칙을 적용합니다.
5. 정식 재고와 실제 값을 비교해 정말 달라진 대상만 남깁니다.
6. 정식 재고와 위험 판정을 한 번의 핵심 반영으로 확정합니다.

연결표를 둔 이유는 이름이 같다는 이유만으로 데이터를 합치지 않기 위해서입니다. 상품명과 매장명은 바뀌거나 중복될 수 있지만 내부 식별자는 안정적입니다. 연결 작업은 추가로 필요하지만 잘못된 상품의 재고를 조용히 덮어쓰는 위험은 줄어듭니다.

현재 동기화는 기존 정식 재고를 갱신하는 범위에 집중합니다. 원천에 처음 등장한 상품을 자동 등록하거나, 원천에서 사라진 행을 곧바로 삭제하는 기능까지 포함하지 않았습니다. 자동 생성과 삭제는 상품 승인, 참조 관계, 이력 보존 정책이 함께 필요하기 때문입니다.

## 재현 가능한 대규모 기준 데이터를 준비한 방법

동기화 기능은 몇 행의 예제만으로는 페이지 이동, 중복 연결, 변경 감지를 충분히 확인하기 어렵습니다. 그래서 정식 재고 스냅샷을 기준으로 네 원천 형식의 고정 테스트 데이터를 생성했습니다. 이 데이터는 관계와 변환 규칙을 반복 검증하려는 기준이며, 실제 운영의 결측·편향·순간 부하까지 재현한다고 보지는 않았습니다.

| 원천 | 행 수 |
| --- | ---: |
| 오프라인 | 23,392 |
| 이커머스 | 325 |
| 그리팅 | 1,416 |
| 물류센터 | 8,225 |
| 합계 | 33,358 |

무작위로 매번 다른 파일을 만드는 대신 같은 입력이면 같은 결과가 나오는 생성기를 사용했습니다. 생성된 행 수, 연결표 행 수, 내용 검증값을 함께 확인해 ‘대략 비슷한 데이터’가 아니라 반복 검증할 수 있는 시험 기준으로 만들었습니다.

이 데이터는 운영 중 계속 실행되는 동기화 기능과 역할이 다릅니다. 초기 데이터 생성은 개발·검증 환경을 준비하는 도구이고, 운영 동기화는 원천의 변경을 감지해 정식 재고에 반영하는 기능입니다. 두 경로를 구분해야 테스트 편의를 위해 만든 규칙이 운영 로직으로 섞이지 않습니다.

## 문제 6. 동기화 버튼을 두 번 누르면 작업이 겹칠 수 있었다

브라우저에서 버튼을 비활성화해도 다른 탭, 다른 사용자, 예약 실행, 직접 API 요청까지 막지는 못합니다. 동시 실행 제어의 최종 책임을 서버와 데이터베이스에 둔 이유입니다.

사용자가 동기화를 요청하면 서버는 오래 기다리게 하지 않고 요청이 접수되었다는 응답과 실행 번호를 돌려줍니다. 실제 작업은 별도로 이어집니다.

1. 짧은 접수 구간에서 요청 식별자와 실행 가능 여부를 확인합니다.
2. Oracle의 비관적 잠금으로 동시에 들어온 접수 판단을 한 줄씩 처리합니다.
3. 활성 실행을 하나만 허용하는 고유 제약으로 마지막 안전망을 둡니다.
4. 접수 기록을 먼저 확정한 뒤 Spring Batch 작업을 시작합니다.
5. 브라우저는 실행 번호로 상태를 확인합니다.

### 용어를 사람의 말로 풀면

| 개념 | 이 기능에서 하는 일 |
| --- | --- |
| 멱등성 | 같은 요청을 다시 보내도 새 작업을 중복 생성하지 않습니다. 통신이 끊겨 성공 여부를 모를 때 특히 필요합니다. |
| 비관적 잠금 | 동시에 들어온 요청들이 실행 가능 여부를 차례로 판단하게 합니다. 잠금 대기는 최대 5초로 제한했습니다. |
| 고유 제약 | 애플리케이션 판단에 틈이 생겨도 데이터베이스가 활성 작업 두 개를 허용하지 않습니다. |
| 속도 제한 | 한 사용자가 지나치게 자주 실행하지 못하도록 최소 10초 간격과 시간당 60회 상한을 둡니다. |
| 펜싱 토큰 | 복구된 새 작업이 시작된 뒤 예전 작업이 늦게 돌아와 결과를 덮어쓰지 못하게 세대 번호를 검사합니다. |

여기서 ‘같은 요청’은 같은 요청 식별자를 다시 보낸 경우입니다. 실행 기록이 남아 있는 동안 내용이 비슷해도 새 식별자를 사용하면 별도 요청으로 취급됩니다. 다만 이미 작업이 진행 중이라면 네 원천이 만드는 통합재고 전체에 하나만 열어 둔 활성 실행 제약이 두 번째 시작을 막습니다. 사용자별 또는 원천별로 따로 실행되는 구조는 아닙니다.

비관적 잠금은 구현이 명확하고 Oracle이 최종 판단을 맡는 장점이 있습니다. 반면 요청이 몰리면 기다림이 생깁니다. 그래서 잠금 구간에는 긴 데이터 처리를 넣지 않고, 접수 여부를 결정하는 짧은 작업만 수행했습니다.

속도 제한과 동시 실행 제한도 역할이 다릅니다. 속도 제한은 반복 요청으로부터 시스템을 보호하고, 동시 실행 제한은 정식 재고가 서로 다른 두 작업에 의해 동시에 갱신되는 것을 막습니다. 하나가 다른 하나를 대신할 수 없습니다.

수동 버튼과 매일 한국 시간 0시 30분의 예약 실행은 같은 파이프라인을 사용합니다. 실행을 시작한 주체만 다를 뿐 검증, 변경 감지, 반영, 위험 판정, 후속 작업은 같은 규칙을 거칩니다. 별도의 ‘간단한 예약 전용 경로’를 만들지 않아 두 실행 방식의 결과가 달라지는 문제를 피했습니다.

## Spring Batch를 사용하되 확정 단위와 혼동하지 않았다

Spring Batch는 작업의 시작·성공·실패 같은 실행 생명주기를 관리하는 데 사용했습니다. 일반적인 청크 작업은 일정 건수마다 읽기·가공·저장을 반복하며 중간 진행 위치를 남깁니다. 현재 구조는 이런 청크 작업이 아니라 하나의 작업 단계가 전체 동기화 흐름을 조정하는 방식입니다.

각 원천은 안정적인 원천 행 식별자를 기준으로 한 번에 최대 500행씩 이어 읽습니다. 페이지 번호 방식은 앞쪽 데이터가 추가되거나 삭제될 때 중복이나 누락이 생길 수 있지만 마지막 식별자 다음부터 읽는 방식은 이런 변화에 더 안정적입니다.

여기서 500행은 데이터베이스와 주고받는 묶음의 크기이지, 500행마다 변경을 최종 확정한다는 뜻이 아닙니다. 바뀐 후보는 메모리에 모아 검증하고, 정식 반영은 마지막 핵심 트랜잭션에서 한 번에 처리합니다. 트랜잭션은 여러 데이터 변경이 모두 성공하거나 모두 되돌아가게 묶는 경계입니다. 현재 메모리 버퍼는 최대 10만 건으로 제한했습니다.

이 선택은 ‘모두 반영되거나 아무것도 반영되지 않는’ 원자성을 이해하기 쉽게 보장합니다. 대신 변경량이 커질수록 메모리 사용과 마지막 트랜잭션 시간이 증가합니다. 처리 규모가 더 커지면 중간 적재 테이블, 마지막 처리 위치의 영구 저장, 여러 번의 부분 확정을 고려해야 합니다. 현재 규모에서는 복구 단순성과 일관성을 우선했습니다.

## 변경 감지용 지문은 빠른 후보 선별 장치다

원천 행마다 업무에 영향을 주는 값을 일정한 순서로 묶어 SHA-256 지문을 만듭니다. 데이터베이스는 현재 지문과 마지막 동기화 지문이 다른 행만 반환합니다. 덕분에 애플리케이션이 3만 건이 넘는 원천의 실제 값을 모두 메모리에 올려 정식 재고와 비교하지 않아도 됩니다. 데이터베이스가 후보를 찾으면서 지문 조건을 검사하는 비용 자체가 사라지는 것은 아닙니다.

지문이 다른 후보는 공통 형식으로 바꾼 뒤 실제 정식 재고 값과 다시 비교합니다. 원천의 부가 정보만 달라져 정식 값은 같다면 여기서 불필요한 쓰기를 걸러 냅니다.

다만 지문이 같다고 판단된 행은 후보로 읽지 않습니다. 해시 충돌이 일어나거나, 지문 규칙에서 중요한 필드를 빠뜨리면 실제 변경도 놓칠 수 있습니다. 마지막 값 비교가 이 경우까지 구해 주지는 못합니다. 그래서 생성기와 서버가 같은 필드·정규화·순서를 사용하도록 계약을 고정하고, 대표 입력의 예상 지문과 전체 데이터 검증값을 시험 기준으로 관리해야 합니다.

시연용 재고 차감 경로는 현재 더 작은 범위의 지문 규칙을 사용합니다. 지금의 시연 범위에는 충분하지만 같은 원천 계약을 확장하기 전에는 하나의 지문 규칙으로 통합해야 합니다.

## 핵심 반영은 한 번에, 대시보드와 통계는 그다음에

검증이 끝나면 정식 재고, 원천과 정식 데이터의 참조, 마지막 동기화 상태, 위험 판정 결과, 실행 완료 상태를 하나의 핵심 트랜잭션에서 확정합니다.

트랜잭션은 여러 변경을 하나의 약속으로 묶는 기능입니다. 도중에 하나라도 실패하면 앞선 변경도 되돌려, 재고는 갱신됐지만 위험 판정은 이전 값인 상태를 막습니다.

원천을 오래 읽는 동안 데이터베이스 잠금을 계속 잡지는 않습니다. 대신 마지막 반영 직전에 원천 버전과 실행 세대를 다시 확인합니다. 읽는 동안 원천이 바뀌었다면 이번 반영을 중단하고 다시 실행하게 합니다. 긴 잠금으로 전체 시스템을 느리게 만들지 않으면서 오래된 결과의 반영을 막기 위한 절충입니다.

대시보드와 통계 스냅샷은 핵심 반영이 성공한 뒤 각각 별도 작업으로 만듭니다. 두 작업은 서로 독립적이므로 통계 생성 실패가 대시보드 생성까지 막지 않고, 후속 작업 실패가 이미 확정된 정식 재고를 되돌리지도 않습니다.

재고 동기화의 성공 여부가 부가 집계에 끌려가지 않는다는 게 장점입니다. canonical 반영 transaction에는 대시보드와 재고통계 작업 행만 함께 기록하고, 실제 집계는 commit 뒤 실행합니다. 각 작업은 대기·실행·재시도 대기·성공·실패 상태, 최대 세 번의 시도와 10분 lease를 DB에 남깁니다. 연결 단절이나 일시적 DB 자원 장애만 다시 시도하고, 직렬화·검증·무결성처럼 같은 입력으로 반복해도 나아지지 않는 오류는 첫 시도에서 실패로 끝냅니다. 서버가 재시작해 메모리 큐가 비어도 정기 복구기가 due task와 만료 lease만 다시 요청하며, snapshot이 이미 저장됐으면 성공 상태를 복원합니다.

## 브라우저는 완료를 기다리지 않고 상태를 추적한다

접수 응답을 받은 화면은 실행 상태를 주기적으로 확인합니다.

- 대기 중에는 3초 간격으로 확인합니다.
- 실행 중에는 10초 간격으로 확인합니다.
- 성공 뒤 스냅샷을 만드는 동안에는 완료 후 1분까지 3초, 1~5분은 10초 간격으로 확인합니다.
- task가 실패하거나 두 스냅샷이 모두 준비되면 자동 확인을 멈춥니다. task 상태를 알 수 없는 경우도 5분을 상한으로 둡니다.
- 브라우저가 백그라운드에 있을 때는 불필요한 확인을 쉬고, 다시 돌아오거나 연결이 회복되면 최신 상태를 확인합니다.

통신이 끊겨 접수 성공 여부를 모르면 같은 요청 식별자로 다시 확인합니다. 사용자가 완료된 작업 뒤 새로 시도할 때만 새로운 식별자를 만듭니다. 서버의 멱등성 규칙과 화면의 재시도 규칙이 함께 맞아야 중복 실행을 막을 수 있습니다.

다른 사용자나 예약 실행이 이미 작업 중이면 서버가 알려 준 기존 실행을 따라갑니다. 속도 제한에 걸리면 다시 시도할 수 있는 시간을 안내합니다. 상태 확인이 실패해도 마지막으로 확인한 정상 상태를 즉시 지우지 않고, 오류와 수동 재시도 방법을 함께 보여 줍니다.

변경이 있는 성공 뒤에는 재고 목록·요약·상세·LOT·위험 정보를 먼저 다시 불러옵니다. 대시보드와 통계는 run API가 각 스냅샷의 DB 저장 완료를 알려 준 뒤 해당 조회만 다시 요청합니다. 여러 사용자가 동시에 완료 화면을 열어 서버에 같은 순간 요청을 몰아넣지 않도록 0~3초의 작은 무작위 지연도 둡니다. 변경 건수가 0이면 스냅샷 생성과 자동 재조회를 모두 생략하고, 수요예측은 이번 동기화가 직접 다시 계산하는 대상이 아니므로 자동 갱신 범위에서 제외했습니다.

상태 메시지는 화면에만 색으로 표현하지 않고 보조기술이 변화를 읽을 수 있게 알립니다. 키보드 사용자가 실행과 재시도를 할 수 있고, 실패·복구 대기·다른 세션의 실행도 문장으로 구분합니다.

## 복구는 자동 재시작보다 안전한 수동 판단을 택했다

작업 중 서버가 멈추면 실행 기록과 마지막 심장박동이 남습니다. 운영자는 중단된 작업을 확인한 뒤 복구 실행을 시작할 수 있습니다. 새 실행에는 더 높은 세대 번호가 부여되고, 예전 작업은 반영 직전에 자신이 최신 세대인지 확인합니다.

현재 복구는 마지막 500행 다음부터 이어 가지 않고 첫 페이지부터 다시 읽습니다. 변경 감지 덕분에 이미 같은 상태인 행의 쓰기는 줄어들지만 읽기 비용은 다시 듭니다. 반면 메모리 중간 상태를 영속화하고 정확히 복원하는 복잡성이 없습니다.

실행 기록이 확정된 직후, 백그라운드 작업을 등록하기 전에 서버가 꺼지는 틈도 있습니다. 이런 실행은 대기 상태로 남으며, 5분이 지나도 실제 배치 실행이 없으면 운영자가 같은 기록을 새 세대로 복구할 수 있습니다. 현재는 이를 자동으로 찾아 주는 감시기가 없으므로 접수 기록이 남았다는 사실만으로 실행 시작까지 자동 보장되지는 않습니다.

자동으로 고아 작업을 찾아 재시작하는 감시기는 아직 두지 않았습니다. 자동 복구는 운영 부담을 줄이지만, 장애 원인을 확인하지 않은 채 잘못된 입력을 반복 실행할 수 있습니다. 프로젝트 범위에서는 실행 기록, 심장박동, 수동 복구, 펜싱으로 안전한 복구 기반을 먼저 마련했습니다.

## 검증은 기능별 성공이 아니라 경계까지 확인했다

2026년 8월 24일 최신 로컬 코드로 다시 확인한 결과, Backend 전체 테스트 472개 중 실제 DB 연결 조건이 필요한 16개를 제외한 456개가 실패 없이 끝났습니다. Frontend는 Node 24.18.0과 pnpm 11.18.0에서 코드 검사·형식 검사·프로덕션 빌드와 293개 테스트를 모두 통과했습니다. 이번 조회 변경만 좁힌 Frontend 회귀 테스트 38개도 통과했고, Backend는 HTTP 연산자 검증과 MyBatis `BoundSql` 렌더링 테스트로 목록·건수·요약에 `OR`와 SKU 종합 위험 조건이 함께 들어가는지 확인했습니다. 원천 데이터 저장소도 계약 테스트 12개를 통과했고, 33,358개 원천 행과 같은 수의 연결표 및 전체 내용 검증값이 다시 일치했습니다. 동기화 화면의 다른 세션 감지·모바일 위험 사유를 포함한 브라우저 시나리오 3개도 모두 성공했습니다. 이는 기능 계약과 정확성에 관한 결과이며 운영 환경의 응답 시간·메모리·잠금 대기 성능을 입증하는 수치는 아닙니다.

특히 다음 경계를 시험 대상으로 보았습니다.

- 같은 요청을 다시 보내도 실행이 하나인지
- 다른 요청이 동시에 들어오면 활성 실행을 따라가는지
- 원천 버전이 바뀌면 오래된 결과를 반영하지 않는지
- 잘못된 음수 수량이 조용히 저장되지 않는지
- 핵심 반영 실패 시 정식 재고와 위험 결과가 함께 되돌아가는지
- 새 실행이 시작된 뒤 오래된 작업자가 결과를 덮어쓰지 못하는지
- 화면이 성공·실패·속도 제한·상태 확인 오류를 서로 다르게 안내하는지

테스트 수 자체보다 ‘어떤 실패를 막기 위한 테스트인가’를 연결하는 것이 중요했습니다.

## 현재 구조의 한계와 다음 단계

현재 구현이 의도적으로 남겨 둔 한계도 분명합니다.

- 원천의 신규 상품을 정식 상품으로 자동 등록하지 않습니다.
- 원천에서 사라진 행을 자동 삭제로 해석하지 않습니다.
- 일부 분류 연결은 이름 일치에 의존하므로 안정적인 식별자 매핑으로 확장할 여지가 있습니다.
- 변경 후보를 메모리에 모으므로 매우 큰 변경에는 중간 적재 구조가 필요합니다.
- 복구 시 첫 페이지부터 다시 읽으며 자동 복구 감시기는 없습니다.
- V27 task migration은 코드와 계약 테스트까지 확인했지만 실제 Oracle 적용과 장애 주입 smoke test는 남아 있습니다.
- `AND`/`OR`와 종합 위험도 쿼리는 MyBatis 렌더링까지 확인했지만, 실제 Oracle 데이터에서 혼합 위험 SKU를 조회하는 smoke test와 대표 조건의 실행계획 수집은 남아 있습니다.
- 위험 판정 결과의 개수와 영향 범위가 정확히 일치하는지 더 강한 완전성 검사가 필요합니다.
- 지문 규칙이 생성기, 서버, 시연 경로에서 하나의 계약으로 유지되는지 계속 검증해야 합니다.

이 항목들은 단순히 ‘못 만든 기능’이 아니라 현재 규모에서 복잡성을 어디까지 받아들였는지 보여 주는 설계 경계입니다. 처리량과 운영 중요도가 커진다면 core run 자동 복구 감시, 중간 적재 테이블, 더 강한 매핑 계약을 순서대로 검토할 수 있습니다.

## 마무리

통합재고의 핵심은 네 시스템의 숫자를 한 테이블에 넣는 일이 아니었습니다. 서로 다른 의미를 공통 언어로 바꾸고, 누가 어떤 값을 결정하는지 정하고, 긴 작업의 중복과 실패를 통제하고, 정식 재고와 위험 판단이 같은 시점을 가리키게 만드는 일이었습니다.

구현 순서도 이 문제의 구조를 따라갔습니다. 먼저 조회 경계를 만들고, 화면 상태를 공유 가능하게 만들고, 판단 근거가 있는 위험 판정을 추가했습니다. 그다음 원천 데이터를 공통 형식으로 연결하고, 동시 실행·멱등성·트랜잭션·복구를 갖춘 동기화로 확장했습니다.

특정 기술을 많이 넣는 것보다 중요한 것은 각 기술의 책임을 분리하는 것이었습니다. Oracle은 최종 동시성과 데이터 일관성을, Spring Batch는 실행 생명주기를, MyBatis는 목적이 분명한 조회와 일괄 반영을, React와 TanStack Query는 공유 가능한 탐색과 서버 상태 추적을 맡았습니다.
