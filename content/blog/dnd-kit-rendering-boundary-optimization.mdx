JobSecretary의 칸반 보드에서 카드를 드래그하다가, 움직이지 않은 카드의 회사명과 직무 정보까지 다시 그려지는 현상을 발견했습니다. 처음에는 `React.memo`를 붙이면 충분히 해결할 수 있다고 생각했지만, Profiler에서 확인한 리렌더링 횟수는 거의 줄지 않았습니다.

이 글은 그 문제를 해결하기 위해 실제로 따라간 순서를 기록한 회고입니다. 먼저 현상을 측정하고, 메모이제이션이 왜 듣지 않았는지 확인한 다음, `dnd-kit`의 `useSortable`과 `Context` 구조를 살펴봤습니다. 그 뒤 드래그 상태를 처리하는 부분과 카드 내용을 그리는 부분을 나누고, 현재 프로젝트에서 사용한 `Render Props`, `React.memo`, `React Portal`이 각각 어떤 이유로 필요했는지 정리했습니다.

## 문제 상황: 움직이지 않은 카드도 다시 실행되었습니다

칸반 보드를 만든 뒤 같은 목록에서 카드를 한 장 드래그해 다른 칸으로 옮기는 시나리오를 정했습니다. React Developer Tools Profiler로 드래그 시작부터 종료까지를 기록하고, 전체 커밋 수와 실제로 움직이지 않은 카드 컴포넌트의 실행 횟수를 비교했습니다.

측정 결과는 다음과 같았습니다.

| 항목 | 측정 결과 |
| --- | ---: |
| 한 번의 드래그에서 발생한 전체 커밋 | 271회 |
| 실제로 이동하지 않은 카드의 렌더링 | 268회 |

여기서 렌더링은 React가 컴포넌트 함수를 다시 실행해 새로운 React element tree를 계산하는 `render` 단계에 가깝습니다. 이 단계가 끝났다고 브라우저의 DOM이 바로 바뀌는 것은 아닙니다. React는 이전 결과와 비교한 뒤 실제로 달라진 부분만 `commit` 단계에서 DOM에 반영합니다. 따라서 비활성 카드가 268회 렌더링됐다는 것은 해당 카드가 268번 다시 계산 대상이 되었다는 뜻이지, 카드의 DOM 전체가 268번 교체됐다는 뜻은 아닙니다. 다만 카드 하나의 위치를 계산하기 위해 회사명·직무·마감일을 그리는 코드까지 함께 실행되고 있었고, 카드 수가 늘어나면 이 비용도 커질 수 있는 구조였습니다.

개선 전후 동작 영상은 [JobSecretary 프로젝트 상세](/projects/jobsecretary)의 칸반 보드 섹션에 첨부했습니다. 이 글에서는 영상보다 그 현상이 생긴 이유와 코드 구조를 중심으로 살펴보겠습니다.

## 첫 번째 시도: React.memo만으로 해결하려 했습니다

처음 떠올린 해결책은 `React.memo`였습니다. 카드 데이터가 바뀌지 않았다면 카드 컴포넌트도 다시 실행할 필요가 없다고 생각했기 때문입니다.

초기 구현을 설명하기 위해 구조를 단순화하면 다음과 같습니다. 이 코드는 당시 프로젝트의 전체 원문이 아니라, 문제가 생긴 책임 배치를 보여주기 위한 축약 예시입니다.

```tsx
const SortableCard = memo(function SortableCard({ application }: Props) {
  const {
    attributes,
    listeners,
    setNodeRef,
    transform,
    transition,
  } = useSortable({ id: application.id });

  return (
    <article
      ref={setNodeRef}
      style={{ transform: CSS.Transform.toString(transform), transition }}
      {...attributes}
      {...listeners}
    >
      <h3>{application.company}</h3>
      <p>{application.role}</p>
      <span>{application.deadline}</span>
    </article>
  );
});
```

`application`이 같은 객체라면 `memo`가 부모의 일반적인 리렌더링을 건너뛸 수 있습니다. 그런데 이 컴포넌트 안에서 `useSortable`을 호출하고 있다는 점이 문제였습니다. 카드가 받은 Props만 보는 것이 아니라, 상위 `SortableContext`의 값을 직접 읽고 있었기 때문입니다.

`React.memo`를 적용한 뒤에도 Profiler의 숫자가 크게 달라지지 않은 이유를 확인하려면, 카드가 어떤 값을 어디에서 읽는지 먼저 봐야 했습니다.

## 원인 확인: dnd-kit의 Context 구조를 따라갔습니다

`dnd-kit`에서 드래그 기능은 크게 두 Context를 중심으로 동작합니다.

- `DndContext`: 센서 이벤트, 현재 드래그 중인 아이템, 충돌 대상처럼 전체 드래그에 필요한 상태를 관리합니다.
- `SortableContext`: 정렬 가능한 아이템 목록과 정렬 전략을 관리하고, 각 아이템이 위치를 계산하는 데 필요한 값을 제공합니다.

각 카드가 `SortableContext`를 직접 사용하는 것이 아니라, `useSortable`이 그 Context를 읽습니다. 공식 `useSortable.ts`의 핵심 부분은 다음과 같은 형태입니다.

```tsx
// dnd-kit 공식 useSortable.ts에서 Context를 읽는 부분
const {
  items,
  activeIndex,
  overIndex,
  sortedRects,
  strategy: globalStrategy,
} = useContext(Context);
```

위 코드는 공식 소스에서 Context 구독과 관련된 부분만 발췌한 것입니다. 전체 파일은 [dnd-kit `useSortable.ts` 원문](https://github.com/clauderic/dnd-kit/blob/master/packages/sortable/src/hooks/useSortable.ts)에서 확인할 수 있습니다.

`useSortable`은 Context에서 값을 읽은 뒤 `useDraggable`과 `useDroppable`을 조합하고, 현재 카드의 `index`와 다른 카드의 위치를 바탕으로 `transform`, `transition`, `setNodeRef`, 이벤트 핸들러를 계산해 반환합니다. 따라서 `useSortable`을 호출한 카드는 카드 정보만 받는 컴포넌트가 아니라, 정렬 상태를 구독하는 컴포넌트가 됩니다.

`SortableContext` 쪽에서는 `DndContext`의 값을 읽어 정렬에 필요한 값을 만들고 Context Provider로 전달합니다. 공식 소스의 흐름을 읽기 쉽게 줄이면 다음과 같습니다.

```tsx
// dnd-kit SortableContext.tsx의 흐름을 읽기 쉽게 줄인 예시
const { active, over, droppableRects } = useDndContext();

const activeIndex = active ? items.indexOf(active.id) : -1;
const overIndex = over ? items.indexOf(over.id) : -1;

const contextValue = useMemo(
  () => ({
    activeIndex,
    overIndex,
    items,
    sortedRects: getSortedRects(items, droppableRects),
    strategy,
  }),
  [activeIndex, overIndex, items, droppableRects, strategy],
);
```

이 코드 역시 원문 전체가 아니라 값이 만들어지는 순서를 보여주기 위한 축약본입니다. 실제 구현은 [dnd-kit `SortableContext.tsx` 원문](https://github.com/clauderic/dnd-kit/blob/master/packages/sortable/src/components/SortableContext.tsx)에서 확인할 수 있습니다.

구조를 그림으로 표현하면 다음과 같습니다.

```text
DndContext
  └─ SortableContext
       ├─ 카드 A ─ useSortable() ─ 회사명·직무·마감일
       ├─ 카드 B ─ useSortable() ─ 회사명·직무·마감일
       └─ 카드 C ─ useSortable() ─ 회사명·직무·마감일
```

카드 A를 드래그하면 센서가 포인터 위치를 전달하고, `DndContext`가 활성 아이템과 충돌 대상을 갱신합니다. `SortableContext`는 그 결과를 `activeIndex`, `overIndex`, 측정된 사각형 목록 같은 정렬 값으로 바꿔 Context에 넣습니다. 이 Context를 읽고 있는 카드들은 새 값을 받아 자신의 위치를 다시 계산합니다.

중요한 점은 “정렬에 참여하는 모든 카드가 위치 계산을 해야 한다”는 사실과 “카드의 모든 콘텐츠를 매번 다시 계산해야 한다”는 사실이 같지 않다는 것입니다. 초기 코드에서는 이 두 책임이 하나의 컴포넌트에 함께 있었습니다.

## 원인: useSortable이 Context를 직접 읽고 있었습니다

`React.memo`는 부모가 전달한 Props를 비교합니다. Props가 같으면 부모가 다시 실행되어도 자식 컴포넌트의 실행을 건너뛸 수 있습니다.

하지만 `memo`로 감싼 컴포넌트가 Context를 직접 읽고 있으면 비교 기준이 달라집니다.

```tsx
const SortableCard = memo(function SortableCard({ application }: Props) {
  // application Props가 같아도 useSortable 내부의 useContext가 변경을 읽습니다.
  const sortable = useSortable({ id: application.id });

  return <CardView application={application} sortable={sortable} />;
});
```

이 컴포넌트의 `application`이 바뀌지 않았더라도 `useSortable`이 읽은 Context 값이 바뀌면 컴포넌트는 업데이트 대상이 됩니다. `memo`가 Context 변경을 차단해 주는 것은 아니기 때문입니다.

포인터가 움직일 때의 흐름을 단계별로 적으면 다음과 같습니다.

```text
포인터 이동
  ↓
DndContext가 active·over·측정값 갱신
  ↓
SortableContext가 activeIndex·overIndex·sortedRects 계산
  ↓
Context value 변경
  ↓
useSortable을 사용하는 카드가 transform·transition 재계산
  ↓
같은 함수 안에 있던 카드 콘텐츠도 함께 실행
```

여기서 `useContext`를 사용한다는 말은 하위 컴포넌트가 단순히 부모의 Props를 전달받는다는 뜻이 아닙니다. `useSortable`을 호출한 컴포넌트가 Context 소비자가 되어, Context Provider의 값이 바뀔 때 직접 업데이트를 받는다는 뜻입니다.

그래서 문제의 원인을 “카드에 Props를 많이 전달했다”라고만 설명할 수는 없었습니다. 핵심은 카드 컴포넌트가 `useSortable`을 통해 빠르게 바뀌는 Context를 읽고 있었고, 그 안에서 변하지 않은 회사명·직무·마감일 UI까지 함께 그리고 있었다는 점입니다.

## 해결 과정 1: 라이브러리 교체와 구조 분리를 따로 판단했습니다

원인을 확인한 뒤에는 두 가지 선택지를 비교했습니다.

첫 번째는 `dnd-kit`을 유지하면서 `useSortable`을 호출하는 부분과 카드 콘텐츠를 분리하는 방법입니다. 이 방법이라면 라이브러리를 바꾸지 않고도 Context를 읽는 범위를 줄일 수 있습니다.

두 번째는 현재 프로젝트에서 사용하던 드래그 구현을 `@hello-pangea/dnd`의 `Draggable`로 옮기는 방법입니다. `Draggable`은 Render Props로 `provided`와 `snapshot`을 전달하기 때문에, 드래그 연결 정보와 카드 데이터를 나누는 경계를 코드에서 더 분명하게 표현할 수 있었습니다.

여기서 구분해야 할 점이 있습니다. `@hello-pangea/dnd`로 바꾼 것 자체가 리렌더링을 줄여준 것은 아닙니다. 라이브러리를 바꿔도 드래그 상태와 카드 콘텐츠를 한 컴포넌트에 계속 넣으면 같은 문제가 다시 생길 수 있습니다. 이번 변경에서 중요한 것은 라이브러리 교체가 아니라, 교체 과정에서 렌더링 책임을 다시 나눈 일이었습니다.

## 해결 과정 2: Render Props로 드래그 영역을 분리했습니다

Render Props는 컴포넌트가 계산한 값을 자식 함수의 인자로 전달하는 패턴입니다. `@hello-pangea/dnd`의 `Draggable`은 다음과 같은 방식으로 사용합니다.

```tsx
<Draggable draggableId={application.id} index={index}>
  {(provided, snapshot) => (
    <KanbanCard
      application={application}
      onDelete={onDelete}
      provided={provided}
      isDragging={snapshot.isDragging}
    />
  )}
</Draggable>
```

`provided`에는 `innerRef`, `draggableProps`, `dragHandleProps`처럼 드래그 가능한 DOM에 연결해야 하는 값이 들어 있습니다. `snapshot.isDragging`은 현재 카드가 드래그 중인지 알려줍니다.

이 패턴이 리렌더링을 자동으로 줄여주는 것은 아닙니다. 자식 함수가 매번 다시 실행될 수 있고, 함수 안에서 큰 UI를 모두 만들면 오히려 비용이 커질 수도 있습니다.

이번에는 `Draggable`에서 받은 값을 카드 전체가 아니라 드래그 연결을 담당하는 바깥 컴포넌트에서만 사용하도록 했습니다. 그러면 `provided`와 `snapshot`을 읽는 부분, 카드 정보만 읽는 부분을 코드상에서 나눌 수 있습니다.

## 해결 과정 3: 카드 콘텐츠를 별도 컴포넌트로 분리했습니다

현재 공개된 JobSecretary 코드의 핵심 구조는 `features/document-kanban/ui/kanban-card.tsx`에서 확인할 수 있습니다. 아래 코드는 해당 파일에서 경계를 보여주는 부분만 발췌하고, 카드 내부의 스타일·아이콘·헬퍼 함수는 생략한 것입니다.

```tsx
// 실제 프로젝트 코드의 핵심 구조를 발췌한 예시
const KanbanCardContent = memo(function KanbanCardContent({
  application,
  onDelete,
}: {
  application: Document;
  onDelete: (id: string) => void;
}) {
  // 회사명·직무·마감일·상태 배지 등 카드 정보만 그립니다.
  return (
    <div>
      <h3>{application.company}</h3>
      <span>{application.role}</span>
      <span>{formatDeadline(application.deadline)}</span>
    </div>
  );
});

export function KanbanCard({
  application,
  onDelete,
  provided,
  isDragging,
}: KanbanCardProps) {
  const card = (
    <div
      ref={provided.innerRef}
      {...provided.draggableProps}
      {...provided.dragHandleProps}
    >
      <KanbanCardContent
        application={application}
        onDelete={onDelete}
      />
    </div>
  );

  return isDragging && typeof document !== "undefined"
    ? createPortal(card, document.body)
    : card;
}
```

전체 코드는 [JobSecretary의 `kanban-card.tsx`](https://github.com/kimjunha1231/JobSecretary/blob/main/features/document-kanban/ui/kanban-card.tsx)에서 확인할 수 있습니다. `KanbanCard`는 `provided`와 `isDragging`을 사용해 DOM 연결과 드래그 스타일을 처리하고, `KanbanCardContent`는 `application`과 `onDelete`만 받습니다.

이렇게 나누면 부모인 `KanbanCard`가 드래그 상태 때문에 다시 실행되어도, 카드 정보와 삭제 함수의 참조가 같을 때 `React.memo`가 `KanbanCardContent`의 실행을 건너뛸 수 있습니다.

다만 `memo`를 붙였다는 사실만으로 결과가 보장되지는 않습니다. `application`을 렌더링할 때마다 새 객체로 만들거나 `onDelete`를 새 함수로 만들면 Props가 달라졌다고 판단합니다. 따라서 콘텐츠 컴포넌트에는 필요한 최소 Props만 전달하고, 상위에서 객체와 함수의 참조도 불필요하게 바뀌지 않도록 해야 합니다.

이번 구조를 역할별로 정리하면 다음과 같습니다.

| 컴포넌트 | 맡은 일 | 드래그 중 바뀌는 값 |
| --- | --- | --- |
| `KanbanCard` | `provided` 연결, 위치 스타일, 드래그 상태별 DOM 처리 | `provided`, `isDragging`, style |
| `KanbanCardContent` | 회사명, 직무, 마감일, 상태 배지, 삭제 버튼 표시 | 카드 데이터가 바뀔 때만 |

렌더링 경계를 분리한다는 말은 새로운 React API를 적용했다는 뜻이 아닙니다. 자주 바뀌는 값을 읽는 컴포넌트와 비교적 안정적인 화면을 그리는 컴포넌트를 서로 다른 함수로 나누었다는 뜻입니다.

## 해결 과정 4: Portal로 DOM 위치를 분리했습니다

카드 콘텐츠를 분리한 뒤에도 드래그 중인 카드가 스크롤 영역 안에서 잘리거나 다른 요소 뒤에 가려지는 문제가 남을 수 있습니다. 칸반 보드의 부모에 `overflow`가 있고, 여러 부모가 stacking context를 만들고 있다면 드래그 카드의 `z-index`만 높여서는 해결되지 않습니다.

그래서 현재 구현에서는 드래그 중인 카드의 DOM을 `document.body` 아래로 옮겼습니다.

```tsx
const card = (
  <div
    ref={provided.innerRef}
    {...provided.draggableProps}
    {...provided.dragHandleProps}
  >
    <KanbanCardContent
      application={application}
      onDelete={onDelete}
    />
  </div>
);

if (isDragging && typeof document !== "undefined") {
  return createPortal(card, document.body);
}

return card;
```

Portal은 React 트리에서 컴포넌트를 떼어내는 기능이 아닙니다. 논리적인 React 부모와 Context 관계는 유지한 채, 실제 DOM만 다른 컨테이너에 배치합니다. 따라서 Portal만 적용한다고 `useSortable`이나 드래그 상태 Context의 업데이트가 사라지는 것은 아닙니다.

이번에 Portal을 사용한 목적은 다음 세 가지였습니다.

- 스크롤 컨테이너의 `overflow`에 카드가 잘리지 않게 하기
- 부모의 stacking context와 `z-index` 때문에 카드가 뒤로 가려지지 않게 하기
- 윈도우 스크롤 환경에서 드래그 카드가 화면 위에 안정적으로 보이게 하기

즉 `React.memo`는 콘텐츠가 다시 실행되는 범위를 줄이기 위한 선택이고, Portal은 드래그 중인 DOM의 위치를 안정적으로 만들기 위한 선택이었습니다. 두 문제를 같은 최적화로 설명하면 실제 변경 이유가 흐려집니다.

## 결과: 같은 시나리오로 다시 측정했습니다

같은 카드 목록과 같은 드래그 시나리오로 다시 Profiler를 기록했습니다.

| 항목 | 변경 전 | 변경 후 | 변화 |
| --- | ---: | ---: | ---: |
| 전체 커밋 횟수 | 271회 | 98회 | **63.8% 감소** |
| 비활성 카드 렌더링 | 268회 | 0회 | **100% 감소** |

이 수치는 라이브러리 하나의 효과로 해석하지 않았습니다. 드래그 상태를 처리하는 컴포넌트와 카드 콘텐츠를 나누고, 콘텐츠에 `React.memo`를 적용하고, 드래그 중인 DOM을 Portal로 옮기는 변경이 함께 들어갔기 때문입니다. 또한 측정은 특정 카드 수와 특정 브라우저에서 하나의 드래그 시나리오를 기록한 결과이므로, 모든 환경에서 같은 비율로 개선된다고 말할 수는 없습니다.

제가 이 경험에서 확인한 기준은 “컴포넌트 함수가 다시 실행되지 않는가”에서 끝나지 않습니다. 실제로는 다음을 함께 봐야 합니다.

1. 어떤 Context를 어떤 컴포넌트가 직접 읽고 있는가
2. 드래그 중 변하는 Props와 카드 정보 Props가 섞여 있는가
3. `memo`로 감싼 컴포넌트에 객체·함수 참조가 매번 새로 전달되는가
4. DOM이 부모의 `overflow`나 stacking context에 영향을 받고 있는가
5. Profiler의 실행 횟수 변화가 실제 입력 지연이나 프레임 드롭 감소로 이어지는가

## 정리

문제는 `dnd-kit`이 느리다는 한 문장으로 설명되지 않았습니다. 카드 컴포넌트가 `useSortable`을 통해 `Context`를 직접 읽고 있었고, 그 컴포넌트 안에서 드래그 위치 계산과 회사명·직무·마감일 렌더링을 함께 처리하고 있었던 것이 출발점이었습니다.

처음에는 `React.memo`만 적용했지만 Context 업데이트는 Props 비교 바깥에서 전달되기 때문에 충분하지 않았습니다. `dnd-kit`의 공식 소스를 확인한 뒤, 빠르게 변하는 드래그 상태와 안정적인 카드 콘텐츠를 다른 컴포넌트 경계에 두는 방향으로 접근을 바꿨습니다.

현재 구조에서 각 선택의 역할은 다음과 같습니다.

- `useSortable` 또는 `Draggable` 연결 정보는 바깥 컴포넌트가 담당합니다.
- `KanbanCardContent`는 카드 데이터만 받고 `React.memo`로 감쌉니다.
- `Render Props`는 드래그 라이브러리의 값을 셸에서 받도록 경계를 드러내는 데 사용합니다.
- `React Portal`은 드래그 중 카드가 잘리거나 가려지지 않도록 DOM 위치를 바꾸는 데 사용합니다.

결국 중요한 것은 어떤 라이브러리를 선택했는가보다, 자주 바뀌는 상태를 읽는 컴포넌트와 안정적으로 화면을 그리는 컴포넌트를 어디에서 나눴는가였습니다.
