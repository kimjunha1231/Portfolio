JobSecretary 프로젝트 중 칸반보드에서 카드 하나를 드래그할 때마다 모든 카드들이 리렌더링되던 문제를 해결한 과정이다.

## 문제를 발견한 순간

칸반보드에서 카드를 드래그할 때 움직이는 픽셀 단위마다 리렌더링이 발생하는 것을 확인했다. 하지만 이것이 단순히 해당 카드나 인근 카드가 아닌, 칸반 보드 내 모든 카드에 대해 리렌더링이 발생하고 있다는 사실을 React Developer Tools Profiler로 측정하면서 알게 되었다.

## 첫 번째 가설: `React.memo`로 메모이제이션하면 해결될까?

적어도 드래그 중인 카드와 인근 카드 이외에는 리렌더링이 발생하지 않는 것이 당연하다고 생각했다.
드래그 중인 카드 이외의 다른 카드 컴포넌트들은 데이터가 바뀌지 않기 때문에 상위 컴포넌트 리렌더링이 영향을 주고 있는 것이라고 판단했다.
데이터가 바뀌지 않는다면 카드 컴포넌트를 `React.memo`로 감싸는 방법 즉 메모이제이션을 적용하면 해결될 것이라고 생각하였다.

하지만 기대와 달리 `React.memo`를 적용한 뒤에도 렌더링 횟수에 변화는 없었다.


## 원인 검색

메모이제이션으로도 리렌더링이 해결되지 않자, 동일한 문제를 겪은 사례가 있는지 검색해보았다.

## 문제 접근

초기 구현 당시의 카드 컴포넌트 코드는 다음과 같았다. `useSortable`을 사용하면서 `React.memo`로 감싸고 있는 구조였다.

```tsx
const SortableCard = memo(function SortableCard({application}: Props) {
  const {
    attributes,
    listeners,
    setNodeRef,
    transform,
    transition,
  } = useSortable({id: application.id});

  return (
    <article
      ref={setNodeRef}
      style={{transform: CSS.Transform.toString(transform), transition}}
      {...attributes}
      {...listeners}
    >
      <h3>{application.company}</h3>
      <p>{application.role}</p>
      <span>{application.deadline}</span>
    </article>
  );
});
```

여기서 `application`은 카드가 가지고 있는 채용 공고 정보이다. `application` Props가 바뀌지 않으면 `React.memo`로 리렌더링이 방어될 것 같았지만, 기대와 달리 렌더링을 막지 못했다.

칸반보드 드래그 시 카드 리스트의 순서를 재정렬해주는 `useSortable` 훅을 모든 카드 컴포넌트가 사용하고 있음과 동시에 메모이제이션이 작동하지 않았기 때문에, 해당 훅과 라이브러리의 내부 상태 전파 방식에 원인이 있을 것이라 생각하여 라이브러리 코드를 직접 분석하게 되었다.

공식 문서([dnd-kit use-sortable 가이드](https://dndkit.com/react/hooks/use-sortable/))에서도 기본적으로 각 아이템 컴포넌트 내부에서 `useSortable`을 호출해 순서를 재정렬하는 패턴을 안내하고 있다.

```tsx
import {useSortable} from "@dnd-kit/react/sortable";

function Sortable({id, index}) {
  const {ref} = useSortable({id, index});

  return (
    <li ref={ref} className="item">Item {id}</li>
  );
}

export default function App() {
  const items = [1, 2, 3, 4];

  return (
    <ul className="list">
      {items.map((id, index) =>
        <Sortable key={id} id={id} index={index} />
      )}
    </ul>
  );
}
```
## 라이브러리 내부 코드 분석

이 정렬 기능의 데이터 전파 구조를 단순화하면 다음과 같다.
```text
DndContext - 최상위로 드래그앤드롭 이벤트를 관리한다.
  └─ SortableContext - 정렬만을 담당한다.
       ├─ 카드 A ─ useSortable() ─ 회사명·직무·마감일
       ├─ 카드 B ─ useSortable() ─ 회사명·직무·마감일
       └─ 카드 C ─ useSortable() ─ 회사명·직무·마감일
```

### 1. `SortableContext.tsx` 분석

`SortableContext`는 상위 드래그 상태를 정렬에 필요한 형태로 바꿔 Provider 값으로 하위 모든 카드에 제공한다.

```tsx
const {active, droppableRects, over} = useDndContext();

const activeIndex = active ? items.indexOf(active.id) : -1;
const overIndex = over ? items.indexOf(over.id) : -1;

export function SortableContext({
  // ....
  const contextValue = useMemo(
    (): ContextDescriptor => ({
      activeIndex,
      containerId,
      disabled,
      disableTransforms,
      items,
      overIndex,
      useDragOverlay,
      sortedRects: getSortedRects(items, droppableRects),
      strategy,
    }),
    [
      activeIndex,
      containerId,
      disabled.draggable,
      disabled.droppable,
      disableTransforms,
      items,
      overIndex,
      droppableRects,
      useDragOverlay,
      strategy,
    ]
  );

  return <Context.Provider value={contextValue}>{children}</Context.Provider>;
}
```

위 코드는 [dnd-kit 공식 `SortableContext.tsx`(packages/sortable/src/components/SortableContext.tsx)](https://github.com/clauderic/dnd-kit/blob/master/packages/sortable/src/components/SortableContext.tsx)의 축약이다.

픽셀 단위로 움직이며 갱신된 좌표로 인해 `SortableContext`를 사용하고 있는 모든 카드 컴포넌트들은 마우스가 움직일 때마다 새로운 Context 정보(`contextValue`)를 공유받게 된다.

---

### 2. `useSortable.ts` 분석

그리고 그 Context들은 `useSortable` 내부의 `useContext`를 사용하여 갱신되고 있었다.

```tsx
export function useSortable({
  animateLayoutChanges = defaultAnimateLayoutChanges,
  attributes: userDefinedAttributes,
  disabled: localDisabled,
  data: customData,
  getNewIndex = defaultNewIndexGetter,
  id,
  strategy: localStrategy,
  resizeObserverConfig,
  transition = defaultTransition,
}: Arguments) {
  const {
    items,
    containerId,
    activeIndex,
    disabled: globalDisabled,
    disableTransforms,
    sortedRects,
    overIndex,
    useDragOverlay,
    strategy: globalStrategy,
  } = useContext(Context);
  // ......
}
```

이 코드는 [dnd-kit 공식 `useSortable.ts`(packages/sortable/src/hooks/useSortable.ts)](https://github.com/clauderic/dnd-kit/blob/master/packages/sortable/src/hooks/useSortable.ts)의 Context 구독 부분만 발췌한 것이다.

결국 `SortableCard` 구조에서는 `application` Props가 바뀌지 않더라도, 내부에서 `useContext`로 정렬 Context를 직접 구독하고 있었기 때문에 `React.memo`가 우회되어 카드 컴포넌트가 강제로 다시 실행되었다.

정렬에 참여하는 카드가 자신의 위치를 다시 계산하는 것은 필요한 작업이다. 하지만 같은 카드 함수 안에서 위치 계산과 바뀌지 않는 회사명·직무·마감일 UI 표현까지 함께 처리하고 있었기 때문에, 드래그 위치가 바뀌는 순간 실제 바뀌지 않은 카드 콘텐츠 전체가 같은 컴포넌트 함수의 실행 범위에 포함되어 보드 안의 모든 카드가 리렌더링되는 결과로 이어졌다.

## 해결 기준을 먼저 세우기

원인을 확인한 뒤 해결 기준을 세 가지로 정했습니다.

1. 드래그 위치와 DOM 연결에 필요한 값은 드래그 전용 컴포넌트에서 읽습니다.
2. 회사명·직무·마감일처럼 드래그와 관계없는 UI는 별도의 렌더링 경계로 분리합니다.
3. 라이브러리 변경 자체를 성능 개선의 원인으로 해석하지 않습니다.

검토한 선택지는 다음과 같았습니다.

| 선택지 | 장점 | 고려할 점 |
| --- | --- | --- |
| `dnd-kit` 유지 + 외곽 컴포넌트 분리 | 기존 라이브러리를 유지할 수 있음 | 드래그 상태·DOM 연결·콘텐츠 책임을 직접 재배치해야 함 |
| `dnd-kit`의 `DragOverlay` 활용 | 드래그 중인 표시와 원래 목록을 분리할 수 있음 | 렌더링 경계 설계를 별도로 해야 함 |
| `@hello-pangea/dnd`의 `Draggable` 활용 | 호출부에서 드래그 정보와 카드 데이터를 구분하기 쉬움 | 라이브러리 변경만으로는 렌더링이 줄지 않음 |

이번 구현에서는 `@hello-pangea/dnd`의 `Draggable`을 사용했습니다. 선택의 핵심은 어느 라이브러리가 더 빠른가가 아니라, 빠르게 변하는 값과 안정적인 UI를 코드에서 명확하게 나눌 수 있는가였습니다.

## Render Props로 상태의 경계를 드러내기

Render Props는 컴포넌트가 계산한 값을 자식 함수의 인자로 전달하는 패턴입니다.

```tsx
function Draggable({children}: Props) {
  const provided = getDraggableBindings();
  const snapshot = getDragSnapshot();

  return children(provided, snapshot);
}
```

이 패턴이 리렌더링을 자동으로 줄여주는 것은 아닙니다. 이번 구조에서 Render Props를 선택한 이유는 드래그 상태를 사용하는 지점과 카드 데이터를 전달하는 지점을 호출부에서 확인하기 쉬웠기 때문입니다.

실제 사용부는 다음과 같은 형태입니다.

```tsx
{applications.map((application, index) => (
  <Draggable
    key={application.id}
    draggableId={application.id}
    index={index}
  >
    {(provided, snapshot) => (
      <KanbanCard
        application={application}
        onDelete={onDelete}
        provided={provided}
        isDragging={snapshot.isDragging}
      />
    )}
  </Draggable>
))}
```

`useSortable`과 같은 Hook은 컴포넌트가 내부에서 Context와 상태를 직접 읽는 방식입니다. 반면 Render Props는 부모가 계산한 값을 자식 함수의 인자로 전달합니다. 두 방식의 우열을 말하기보다, 이번에는 Render Props가 드래그 연결 정보의 경계를 코드상에서 드러내는 데 도움이 되었다고 보는 편이 정확합니다.

## 드래그 연결과 카드 콘텐츠를 나누기

Render Props에서 받은 `provided`와 `snapshot`은 드래그 가능한 DOM에 연결하고 현재 드래그 상태를 표현하는 데 필요합니다. 회사명·직무·마감일·상태 배지는 카드 데이터만 있으면 그릴 수 있습니다.

그래서 컴포넌트 책임을 다음처럼 나눴습니다.

| 컴포넌트 | 읽는 값 | 역할 |
| --- | --- | --- |
| `KanbanCard` | `provided`, `isDragging`, 카드 데이터 | DOM ref·드래그 속성·드래그 중 스타일 연결 |
| `KanbanCardContent` | `application`, `onDelete` | 카드 정보와 액션 UI 렌더링 |

구조의 핵심만 줄이면 다음과 같습니다.

```tsx
const KanbanCardContent = memo(function KanbanCardContent({
  application,
  onDelete,
}: {
  application: Document;
  onDelete: (id: string) => void;
}) {
  const router = useRouter();
  const dDay = getDDay(application.deadline);

  const handleClick = () => {
    router.push(`/document/${application.id}?from=dashboard`);
  };

  // 회사명·직무·마감일·상태 배지·삭제 버튼을 렌더링합니다.
  return (
    <div onClick={handleClick} className="cursor-pointer">
      {/* 카드 정보 JSX */}
    </div>
  );
});

export function KanbanCard({
  application,
  onDelete,
  provided,
  isDragging,
}: KanbanCardProps) {
  const card = (
    <div
      ref={provided.innerRef}
      {...provided.draggableProps}
      {...provided.dragHandleProps}
      style={getStyle(provided.draggableProps.style, isDragging)}
    >
      <KanbanCardContent
        application={application}
        onDelete={onDelete}
      />
    </div>
  );

  return isDragging && typeof document !== "undefined"
    ? createPortal(card, document.body)
    : card;
}
```

`KanbanCard`는 드래그 연결 정보를 사용하지만, `KanbanCardContent`에는 `application`과 `onDelete`만 전달합니다. 부모가 `provided`나 `isDragging` 변경으로 다시 실행되어도 콘텐츠 Props의 참조가 같다면 `React.memo`가 콘텐츠 함수 실행을 건너뛸 수 있습니다.

반대로 다음처럼 매번 새 객체나 함수를 만들면 콘텐츠 경계를 나눈 의미가 줄어듭니다.

```tsx
<KanbanCardContent
  application={{...application}}
  onDelete={(id) => handleDelete(id)}
/>
```

따라서 렌더링 경계를 나눌 때는 컴포넌트 이름만 분리하는 것으로 끝나지 않습니다. 경계 안으로 전달하는 Props도 실제로 필요한 최소 단위인지, 참조가 불필요하게 바뀌고 있지 않은지 함께 확인해야 합니다.

## Portal은 렌더링이 아니라 DOM 위치를 위한 선택

드래그 중인 카드는 React Portal을 사용해 document.body 아래로 따로 분리했습니다. 칸반보드 내에서 그대로 움직이면 카드 일부가 잘려 보이거나 z-index에 의해 가려지는 등의 문제가 발생할 수 있어 DOM 위치를 칸반보드 외부로 옮겨 드래그 중인 카드가 안정적으로 보이도록 했습니다.

그래서 드래그 중인 카드만 `document.body` 아래로 옮겼습니다.

```tsx
if (isDragging && typeof document !== "undefined") {
  return createPortal(card, document.body);
}

return card;
```

`createPortal`은 React 트리에서 컴포넌트를 분리하는 기능이 아닙니다. React의 논리적인 부모와 Context 관계는 유지하면서, 실제 DOM 노드만 다른 DOM 컨테이너에 배치합니다.

이번 Portal은 렌더링 횟수를 줄이기 위해 적용한 것이 아닙니다.

- 스크롤 컨테이너의 `overflow`에 드래그 카드가 잘리지 않게 합니다.
- 부모의 stacking context와 `z-index`에 카드가 가려지지 않게 합니다.
- 드래그 중인 카드를 화면 위에 안정적으로 표시합니다.

`React.memo`는 콘텐츠 함수가 다시 실행되는 범위를 줄이고, Portal은 드래그 중인 DOM의 배치 위치를 바꿉니다. 렌더링 문제와 DOM 배치 문제를 각각 다른 도구로 다룬 것입니다.

## 같은 조건에서 다시 측정하기

같은 카드 목록과 같은 드래그 시나리오를 다시 Profiler로 기록했습니다.

| 항목 | 변경 전 | 변경 후 | 변화 |
| --- | ---: | ---: | ---: |
| 전체 커밋 횟수 | 271회 | 98회 | **63.8% 감소** |
| 비활성 카드 렌더링 | 268회 | 0회 | **100% 감소** |

이 결과를 `@hello-pangea/dnd`로 바꾼 하나의 효과로 해석하면 안 됩니다. 라이브러리 변경과 함께 드래그 연결 정보와 카드 콘텐츠를 분리했고, 안정적인 콘텐츠 컴포넌트에 `React.memo`를 적용했습니다. Portal은 별도로 드래그 중인 DOM의 배치 문제를 해결했습니다.

또한 이 수치는 특정 카드 목록·브라우저·드래그 시나리오에서 얻은 결과입니다. 모든 환경에서 같은 비율을 보장하는 절대적인 성능 지표라기보다, 변경 전후의 렌더링 범위를 비교하기 위한 측정값으로 보아야 합니다.

## 비슷한 문제를 만났을 때 확인할 기준

이번 작업 이후에는 `memo`를 먼저 붙이기보다 다음 순서로 확인하려고 합니다.

1. **구독 경로**: 컴포넌트가 Props만 읽는지, `useContext`를 직접 또는 훅 내부에서 읽는지 확인합니다.
2. **변경 빈도**: 드래그 좌표·활성 아이템처럼 자주 바뀌는 값과 카드 정보처럼 안정적인 값을 구분합니다.
3. **컴포넌트 경계**: 빠르게 바뀌는 값을 읽는 바깥 컴포넌트와 콘텐츠를 그리는 안쪽 컴포넌트를 나눕니다.
4. **Props 참조**: `memo` 대상에 새 객체·배열·함수를 매번 전달하고 있지 않은지 확인합니다.
5. **DOM 배치**: 렌더링 횟수와 별개로 `overflow`·stacking context·`z-index` 때문에 드래그 UI가 잘리는지 확인합니다.
6. **측정 범위**: Profiler의 render·commit 수와 실제 프레임 드롭·입력 지연을 같은 것으로 취급하지 않습니다.

## 정리

이번 문제는 “특정 드래그 라이브러리가 느리다”는 한 문장으로 설명되지 않았습니다. 초기 카드 컴포넌트가 정렬 Context를 읽고 있었고, 같은 함수에서 드래그 위치 계산과 회사명·직무·마감일 UI까지 함께 렌더링하고 있었습니다.

`React.memo`는 Props가 같은 일반적인 부모 업데이트를 건너뛰지만, Context를 읽는 컴포넌트의 Context 업데이트까지 차단하지 않습니다. 이 차이를 이해하면 메모이제이션이 기대대로 작동하지 않은 이유를 Props 값이 아니라 구독 경로에서 찾을 수 있습니다.

이번 구조에서 각 개념의 역할은 다음과 같습니다.

- **Context**: 드래그 중 바뀌는 상태를 구독 컴포넌트에 전달합니다.
- **`React.memo`**: Props가 안정적인 카드 콘텐츠의 불필요한 실행을 건너뜁니다.
- **컴포넌트 경계**: 드래그 연결과 안정적인 카드 UI의 책임을 나눕니다.
- **Render Props**: 부모가 계산한 드래그 정보를 호출부에서 명시적으로 전달합니다.
- **React Portal**: 드래그 중인 DOM을 `document.body` 아래에 배치해 표시 문제를 줄입니다.

결국 성능 개선의 핵심은 특정 API를 추가하는 일이 아니라, 상태가 바뀌는 범위와 화면을 다시 계산하는 범위를 일치시키는 일이었습니다.
