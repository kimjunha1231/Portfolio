> StockFit 통합재고 개발 기록 2편 · **조회 범위를 줄이고 수량의 의미를 맞춘 과정**

[1편](/blog/integrated-inventory-sync-flow)에서 동기화 버튼을 누른 뒤 원천 데이터가 canonical과 화면으로 이어지는 실행 순서를 정리했습니다. 이번 글은 그 다음 단계인 **통합재고 목록을 실제로 조회하는 순간**을 다룹니다.

처음에는 “20개 행을 반환하는 API가 왜 18초 이상 걸릴까?”가 문제였습니다. 원인을 따라가 보니 단순히 SQL 한 줄이 느린 것이 아니었습니다. 페이지에 나오지 않을 SKU까지 판매처 JSON·정책·가격·위험도를 계산하고 있었고, 여러 필터를 `EXISTS`로 반복 평가했으며, 프론트엔드는 이전 요청과 새 요청을 구분하지 못한 채 화면을 비우고 있었습니다.

이번 개선은 네 층을 함께 바꾼 작업입니다.

1. 백엔드가 먼저 **필터에 맞는 후보 SKU를 좁히고**, 그 결과로 정렬과 페이지를 확정했습니다.
2. 페이지가 확정된 뒤에만 판매처·LOT·정책·가격 같은 상세 집계를 붙였습니다.
3. SKU×판매처 탐색과 최신 이력 조회에 맞춘 **함수 기반 복합 인덱스**를 추가했습니다.
4. 현재 가용수량과 30일 예상 폐기수량을 같은 SKU 조회 흐름에 넣고, 프론트엔드는 서버가 계산한 값을 표시하도록 했습니다. 일반 상세 집계는 페이지 뒤로 미뤘지만, 예상 폐기 집계는 정렬 계약을 지원하기 위해 후보 단계에서 계산하는 예외가 남아 있습니다.

아래 시간은 프로젝트에서 남긴 단일 Network 관찰값입니다. 실행 모드, 데이터 양, 캐시와 Oracle 부하를 통제한 반복 벤치마크나 p95 보장값은 아닙니다.

| 조건 | 개선 전 | 개선 후 |
| --- | ---: | ---: |
| 4개 채널 `AND` 필터 목록 | 17.99초 | 726ms |
| 같은 조건의 요약 API | 30초에 취소 | 459ms |
| 정렬 조건을 포함한 목록 | 18.19초 | 821ms |

이 글에서 말하는 “페이지를 먼저 계산한다”는 데이터베이스가 모든 행을 물리적으로 즉시 버린다는 뜻은 아닙니다. `candidate_keys`로 후보 범위를 만들고, 후보에서 SKU 단위 집계를 만든 뒤, `paged_candidates`가 정렬·페이지를 결정합니다. 그 이후 판매처·LOT·정책·가격 상세 CTE와 조인은 `paged_candidates`에 연결된 SKU만 참여합니다. 다만 현재 develop의 30일 예상 폐기 집계는 `expected_disposal_qty` 정렬 가능성 때문에 후보 단계에서 먼저 계산됩니다. 이 차이까지 포함해 아래에서 설명합니다.

## 1. 문제 상황: 화면에는 20개인데 DB는 훨씬 더 많이 계산했다

### 1.1 목록 행과 계산 단위를 혼동했다

통합재고 화면의 한 행은 SKU 하나입니다. 하지만 SKU에는 판매처가 여러 개일 수 있고, 판매처에는 LOT·정책·가격·위험 이력이 여러 개씩 붙습니다. 이 관계를 한 번에 조인하면 다음처럼 1:N 행이 늘어납니다.

```text
SKU 1개
 ├─ 판매처 3개
 │   ├─ LOT 여러 개
 │   ├─ 정책 여러 개
 │   └─ 가격·위험 이력 여러 개
 └─ 물류센터별 미할당 재고
```

기존 조회는 이 상세 관계를 먼저 펼친 뒤 `JSON_ARRAYAGG`, `ROW_NUMBER()`와 여러 집계를 수행하고 마지막에 `OFFSET … FETCH`로 페이지를 잘랐습니다. 응답은 20개여도, 20개가 아닌 SKU의 상세 데이터까지 중간 계산에 들어갈 수 있는 형태였습니다.

### 1.2 실제로 문제가 된 코드의 모양

이전 매퍼의 구조를 핵심만 남겨 표현하면 다음과 같습니다. 테이블명과 컬럼은 이해를 위한 축약이고, 실제 변경은 `BackEnd`의 `InventoryMapper.xml`에서 이루어졌습니다.

```sql
WITH row_agg AS (
    SELECT sku_id, sales_point_id,
           SUM(on_hand_qty + reserved_qty) AS current_qty
    FROM inventory_balance
    GROUP BY sku_id, sales_point_id
),
seller_agg AS (
    SELECT sku_id,
           JSON_ARRAYAGG(JSON_OBJECT(
               'salesPointCode' VALUE sales_point_code,
               'quantity' VALUE current_qty
               RETURNING CLOB
           )) AS sales_points_json
    FROM seller_facts
    GROUP BY sku_id
),
sku_agg AS (
    SELECT sku_id, SUM(current_qty) AS current_qty
    FROM seller_facts
    GROUP BY sku_id
)
SELECT ...
FROM sku_agg
JOIN seller_agg USING (sku_id)
ORDER BY updated_at DESC
OFFSET :offset ROWS FETCH NEXT :size ROWS ONLY;
```

`JSON_ARRAYAGG`는 판매처 목록을 JSON으로 묶고, `ROW_NUMBER()`는 최신 위험·가격 행을 고르는 데 필요합니다. 둘 다 필요한 기능이지만 **페이지에 들어오지 않을 데이터까지 먼저 계산하면** 페이지 크기와 계산량이 서로 무관해집니다.

### 1.3 다중 필터는 같은 상관 서브쿼리를 반복했다

채널 네 개를 `AND`로 선택한 경우 이전 필터 SQL은 선택한 값마다 `EXISTS`를 하나씩 만들었습니다.

```xml
<foreach collection="channelTypes" item="channelType">
  EXISTS (
    SELECT 1
    FROM inventory_balance filter_ib
    JOIN sales_point filter_sp ON ...
    WHERE filter_ib.sku_id = ib.sku_id
      AND normalized_channel = #{channelType}
  )
</foreach>
```

`EXISTS`는 “이 SKU에 조건을 만족하는 행이 하나라도 있는가?”를 묻는 좋은 도구입니다. 다만 선택 개수가 늘면 같은 `inventory_balance`와 `sales_point` 범위를 다시 평가하는 SQL이 반복됩니다. 더 큰 문제는 `AND`의 의미가 “선택한 채널이 모두 존재한다”인데, 단순히 `EXISTS`를 늘어놓으면 필터 종류와 조합이 많아질수록 목록·건수·요약의 의미가 어긋나기 쉽다는 점이었습니다.

## 2. 개선 방법 1: 후보 SKU를 먼저 만들고 페이지를 기준으로 상세를 붙였다

### 2.1 `candidate_keys`가 조회의 출발점이 됐다

현재 `InventoryMapper.xml`은 먼저 필터를 통과한 `SKU × 판매처 범위`를 `candidate_keys`로 만듭니다. 범위 키는 소유 판매처(`stock_sales_point_id`)를 우선 사용하고, 없으면 할당 판매처(`allocated_sales_point_id`), 둘 다 없으면 `-1`을 사용합니다.

```sql
candidate_keys AS (
    SELECT DISTINCT
           ib.sku_id,
           NVL(
               ib.stock_sales_point_id,
               NVL(ib.allocated_sales_point_id, -1)
           ) AS sales_point_id
    FROM inventory_balance ib
    JOIN sku s ON s.sku_id = ib.sku_id
    JOIN product p ON p.product_id = s.product_id
    LEFT JOIN sales_point sp ON ...
    LEFT JOIN sales_channel sc ON ...
    WHERE ib.is_deleted = 0
      AND s.active_yn = 'Y'
      /* candidateFilterWhere: 검색·채널·판매처·권역·센터·카테고리 ... */
)
```

여기서 `DISTINCT`는 조인 결과가 늘어나더라도 같은 SKU와 판매처 범위를 후보에 한 번만 남기는 역할을 합니다. `candidate_keys`의 grain을 고정했기 때문에 이후 집계가 판매처·LOT 조인 수만큼 목록 행을 복제하는 문제를 줄일 수 있습니다.

### 2.2 SKU 단위 집계와 페이지 확정 순서를 분리했다

후보 범위에서 가용수량·예약수량·LOT 수·위험도를 SKU 하나의 행으로 줄인 뒤, `paged_candidates`에서 정렬과 페이징을 실행합니다.

```sql
candidate_sku_agg AS (
    SELECT cbb.sku_id,
           SUM(cbb.on_hand_qty + cbb.reserved_qty) AS current_qty,
           SUM(/* 판매 가능한 on_hand_qty */) AS available_qty,
           SUM(/* 판매 가능한 reserved_qty */) AS reserved_qty,
           COUNT(DISTINCT cbb.lot_id) AS lot_count,
           MAX(cbb.updated_at) AS updated_at
    FROM candidate_balance_base cbb
    GROUP BY cbb.sku_id
),
paged_candidates AS (
    SELECT q.*, COUNT(*) OVER () AS total_count
    FROM (
        SELECT ...
        FROM candidate_sku_agg csa
        JOIN sku s ON s.sku_id = csa.sku_id
        JOIN product p ON p.product_id = s.product_id
    ) q
    ORDER BY q.updated_at DESC, q.sku_code ASC
    OFFSET #{offset} ROWS FETCH NEXT #{size} ROWS ONLY
)
```

`COUNT(*) OVER()`는 페이지를 자르기 전 후보 개수를 함께 계산합니다. 그래서 목록 API는 현재 페이지 행과 `totalCount`를 한 결과 흐름에서 받을 수 있습니다. `sku_code ASC`는 `updated_at`이 같은 행의 순서를 고정하는 보조 정렬 키입니다. 이 tie-breaker가 없으면 같은 시각의 행이 페이지 이동 때 서로 다른 위치에 나타날 수 있습니다.

### 2.3 상세 집계는 페이지 SKU를 조인 조건으로 사용한다

페이지가 정해진 뒤에는 판매처 JSON, 물류센터 위치, 최신 정책과 가격, LOT 상세를 `paged_candidates`에 연결합니다.

```sql
seller_agg AS (
    SELECT ...
    FROM balance_base bb
    JOIN paged_candidates pc ON pc.sku_id = bb.sku_id
    GROUP BY bb.sku_id
),
latest_policy AS (...),
latest_price AS (...)
SELECT pc.sku_id,
       pc.available_qty,
       sellers.sales_points_json,
       policy.safety_qty,
       price.selling_price
FROM paged_candidates pc
LEFT JOIN seller_agg sellers ON sellers.sku_id = pc.sku_id
LEFT JOIN latest_policy policy ON ...
LEFT JOIN latest_price price ON ...;
```

이 패턴을 흔히 “페이지 우선 상세 확장”이라고 부를 수 있습니다. 중요한 점은 이름이 아니라 **상세 CTE가 페이지 SKU에 종속되어 있는지**입니다. 페이지 크기가 20인데 후보 SKU가 20만 개라면, 상세 집계가 20만 개 전체를 대상으로 실행되지 않도록 경계를 뒤로 미룬 것입니다.

## 3. 개선 방법 2: `AND`와 `OR`의 의미를 SKU 단위로 다시 정의했다

필터의 `AND`와 `OR`는 SQL 연산자 한 글자를 바꾸는 문제가 아니었습니다. 여러 판매처·채널·권역·물류센터를 가진 SKU를 어떤 단위로 판정할지 먼저 정해야 했습니다.

| 선택 방식 | 의미 | 예시 |
| --- | --- | --- |
| `AND` | 선택한 값이 모두 존재해야 통과 | 채널 `ECOMMERCE`와 `GREETING`을 모두 가진 SKU |
| `OR` | 선택한 값 중 하나라도 존재하면 통과 | 두 채널 중 하나라도 가진 SKU |

### 3.1 `AND`는 선택 개수와 실제 존재 개수를 비교한다

현재 매퍼는 채널·판매처·권역·물류센터의 복수 선택 `AND`에 `COUNT(DISTINCT ...)`를 사용합니다.

```sql
(
    SELECT COUNT(DISTINCT normalized_channel)
    FROM inventory_balance channel_ib
    JOIN sales_point channel_sp ON ...
    WHERE channel_ib.sku_id = ib.sku_id
      AND normalized_channel IN (#{channelA}, #{channelB})
) = #{channelTypeCount}
```

선택한 채널이 두 개이고 SKU가 하나만 가지고 있으면 `1 = 2`가 되어 탈락합니다. 두 채널을 모두 가지고 있으면 `2 = 2`가 되어 통과합니다. `DISTINCT`를 넣은 이유는 한 채널에 LOT가 여러 개 있어도 채널 존재 개수를 한 번만 세기 위해서입니다.

### 3.2 `OR`는 하나의 `EXISTS`와 `IN`으로 평가한다

`OR` 또는 단일 선택은 같은 범위에서 한 번의 존재 여부를 확인합니다.

```sql
EXISTS (
    SELECT 1
    FROM inventory_balance filter_ib
    JOIN sales_point filter_sp ON ...
    WHERE filter_ib.sku_id = ib.sku_id
      AND normalized_channel IN ('ECOMMERCE', 'GREETING')
)
```

채널 코드가 `GREETING`, `MODU_MATJIP`, `DEPT_%`, `HMART_%`처럼 원천 표현에 따라 달라질 수 있어, 현재 SQL은 화면에서 사용하는 채널 코드로 먼저 정규화한 뒤 비교합니다. 이 정규화 규칙이 목록 SQL과 요약 SQL에서 다르면 같은 필터인데 카드의 숫자와 목록 건수가 달라지므로, `candidateFilterWhere`를 목록·건수·요약 조회에 공통으로 포함했습니다.

### 3.3 `EXISTS`를 무조건 없애지는 않았다

가능한 선택지는 세 가지였습니다.

| 선택지 | 장점 | 비용·주의점 |
| --- | --- | --- |
| 값마다 `EXISTS` 반복 | SQL이 직관적이고 작은 선택에 단순함 | 선택 수가 늘면 같은 상관 범위를 반복 평가할 수 있음 |
| 현재 방식: `COUNT(DISTINCT)` + `IN` | `AND`의 “모두 존재”를 직접 표현하고 OR 분기를 단순화 | 상관 집계 자체의 실행계획을 확인해야 함 |
| 선택값을 먼저 전역 집계한 CTE로 만들기 | 후보 집합을 한 번 만든 뒤 조인할 수 있음 | 필터 조합이 늘어나면 CTE 설계와 메모리 사용을 다시 검증해야 함 |

현재 구현은 두 번째 선택지입니다. Oracle 옵티마이저가 상관 서브쿼리를 내부적으로 조인으로 바꿀 수도 있으므로 SQL 텍스트만 보고 “항상 한 번만 읽는다”고 말할 수는 없습니다. 실제 운영 DB에서 `DBMS_XPLAN.DISPLAY_CURSOR`의 `Starts`, buffer gets, 반환 행 수를 확인해야 전역 CTE로 바꿀지 판단할 수 있습니다.

## 4. 개선 방법 3: 수량의 의미를 조회 시점에 맞췄다

조회가 빨라져도 숫자의 의미가 틀리면 개선이 아닙니다. 이번 작업에서 목록에 함께 내려가야 했던 값은 `currentQuantity`, `availableQuantity`, `reservedQuantity`, `expectedDisposalQuantity`였습니다.

### 4.1 가용수량은 `on_hand_qty`에서 판매 불가 LOT를 제외한 값이다

현재 구현은 `on_hand_qty`와 `reserved_qty`를 다시 빼지 않습니다. 판매 가능한 LOT의 `on_hand_qty`를 가용수량으로 사용하고, 예약수량은 별도 값으로 표시합니다.

```sql
SUM(
    CASE
        WHEN lot_status IN ('EXPIRED', 'SALE_STOPPED', 'DEPLETED')
          OR expiry_date <= as_of_date
          OR sale_stop_date <= as_of_date
        THEN 0
        ELSE on_hand_qty
    END
) AS available_qty
```

따라서 물리 재고가 100개이고 예약수량이 10개라고 해서 `100 - 10 = 90`을 다시 계산하지 않습니다. `on_hand_qty`와 `reserved_qty`가 이미 분리된 컬럼이고, 예약을 다시 빼면 이중 차감이 되기 때문입니다.

현재고는 기존 계약처럼 `on_hand_qty + reserved_qty`로 유지하고, 판매 불가 LOT도 LOT 상세와 상태 확인에는 남깁니다. 화면에서 “현재고”와 “가용수량”을 서로 다른 질문으로 읽을 수 있게 한 것입니다.

### 4.2 날짜 경계는 하나의 `asOfDate`로 비교한다

소비기한 또는 판매중지일이 기준일과 같으면 현재 판매 불가로 봅니다.

```text
기준일 D0       → 판매 불가
D+1             → 현재 가용수량에 포함 가능
D+30            → 30일 예상 폐기 후보에 포함
D+31            → 30일 예상 폐기 후보에서 제외
```

`TRUNC(CAST(#{asOfDate} AS DATE))`를 사용해 시간 부분을 제거하고, 날짜 비교를 목록·상세·요약에서 같은 기준으로 수행합니다. 날짜가 `NULL`이라는 이유만으로 자동 제외하지 않고, LOT 상태가 `EXPIRED`, `SALE_STOPPED`, `DEPLETED`인 경우에만 상태 자체로 제외합니다.

### 4.3 30일 예상 폐기수량은 판매처 범위별로 계산한 뒤 SKU에 합산한다

예상 폐기는 모든 재고를 SKU 하나로 뭉쳐 계산하지 않습니다. 수요예측이 판매처별로 존재하므로 매퍼에서 만든 동일한 `SKU × sales_point_id` 범위를 유지합니다. 이 값은 소유 판매처, 할당 판매처, 미할당(`-1`)을 한 가지 키로 표현한 것입니다.

여기서 조회 최적화의 중요한 예외가 하나 있습니다. `seller_agg` 같은 상세 JSON 집계는 `paged_candidates` 뒤에서 현재 페이지 SKU만 읽지만, 현재 develop의 `disposal_by_sku`는 `candidate_balance_base`에서 후보 SKU 전체를 읽은 뒤 `paged_candidates`에 조인합니다. `InventoryQueryRequest`의 정렬 허용 목록에 `expected_disposal_qty`가 있기 때문입니다. 이 값을 전체 후보에서 먼저 계산해야 해당 컬럼으로 정렬할 수 있습니다. 따라서 “모든 계산을 페이지 뒤로 미뤘다”고 쓰면 실제 코드와 다릅니다. 이번 변경에서 페이지 우선으로 줄인 범위와, 아직 후보 전체를 계산하는 범위를 나눠 읽어야 합니다.

현재 매퍼의 최신 forecast 선택은 다음 조건을 포함합니다.

- 기준일보다 미래인 `base_date`는 제외합니다.
- 활성 모델만 사용합니다.
- `DUMMY_BASELINE`은 제외합니다.
- 같은 `SKU × sales_point_id`에서 `base_date`, `updated_at`, `forecast_id` 순으로 최신 행 하나를 고릅니다.
- `D+7 ≤ D+14 ≤ D+30` 누적 관계가 깨지거나 음수·NULL이면 유효 forecast로 사용하지 않습니다.

유효 forecast가 있으면 판매 종료일까지의 예측수요를 D+7, D+14, D+30 구간으로 보간하고, 종료일까지 쌓인 수량에서 예측수요를 뺀 잔여량 중 가장 큰 값을 해당 `sales_point_id` 범위의 예상 폐기로 계산합니다. forecast가 없거나 범위 키가 `-1`이면 그 범위에서 D+30 안에 판매가 끝나는 현재 판매 가능 수량 전체를 fallback으로 사용합니다.

간단한 예시는 다음과 같습니다.

```text
판매 종료 후보 누적 수량: D+7 30개, D+14 50개, D+30 80개
누적 예측수요:           D+7 20개, D+14 45개, D+30 70개

예상 폐기 = max(30-20, 50-45, 80-70, 0)
          = max(10, 5, 10, 0)
          = 10개
```

판매처 A의 forecast로 판매처 B나 미할당 재고를 줄이지 않는 것이 중요합니다. 그래서 LOT 집계와 forecast를 각각 scope 단위 한 행으로 만든 후 결합합니다. forecast를 LOT 행에 바로 조인하면 LOT 개수만큼 예측값이 반복되어 예상 폐기수량이 틀어질 수 있습니다. 이 scope 집계는 현재 후보 SKU 전체에서 실행되므로, 데이터가 더 커졌을 때는 예상 폐기 정렬을 계속 지원할지와 페이지 표시만 남길지를 별도로 결정해야 합니다.

### 4.4 왜 이 계산을 DB가 아니라 백엔드 조회 경계에 넣었나

이번 값은 화면에서 임의로 계산할 값이 아니라 여러 테이블의 업무 규칙을 합친 도메인 결과입니다. `inventory_balance`, `lot`, `demand_forecast`, `ml_model_version`을 함께 읽고, 기준일·판매처 scope·forecast 유효성·fallback을 같은 시점에 적용해야 합니다.

여기서 “백엔드에서 계산한다”는 표현은 Java 서비스가 모든 행을 하나씩 가져와 계산한다는 뜻이 아닙니다. 실제 구현은 **백엔드 API가 계약과 기준일을 정하고, MyBatis가 실행하는 Oracle 집합 SQL이 DB 안에서 한 번에 집계하는 방식**입니다. 백엔드가 이 경계를 소유하므로 목록·상세·요약이 같은 응답 모델과 예외 처리를 공유하고, DB는 대량 행 집계와 조인을 잘하는 역할에 집중합니다. 반대로 DB에 최종 숫자를 저장해 두는 구조는 조회는 단순해지지만 forecast 갱신·동기화 실패·기준일 변경 때 재계산과 무효화 책임이 추가됩니다.

프론트에서 계산하면 다음 문제가 생깁니다.

- 목록 API와 상세 API가 서로 다른 날짜 경계나 상태 규칙을 사용할 수 있습니다.
- 페이지에 없는 LOT와 판매처 데이터가 브라우저에 없으므로 전체 합계를 만들 수 없습니다.
- 동일한 계산식을 대시보드·모바일 카드·상세 드로어에 복사해야 합니다.
- API 응답을 재사용하는 다른 클라이언트가 같은 규칙을 다시 구현해야 합니다.

반대로 DB에 새 컬럼을 저장하거나 배치로 미리 계산하는 선택은 읽기를 빠르게 할 수 있지만, 기준일 변경·forecast 갱신·동기화 실패 시 저장값을 다시 맞추는 운영 비용이 생깁니다. 이번 develop 변경은 기존 테이블과 set-based SQL을 사용해 서버가 계산하고, 저장형 read model은 실제 성능 gate가 넘을 때 검토하는 범위로 남겼습니다.

## 5. 개선 방법 4: 조회 경로에 맞는 복합 인덱스를 추가했다

CTE 순서만 바꿔도 읽는 행이 줄지만, 후보 탐색과 최신 이력 선택이 테이블 전체 스캔으로 남아 있으면 효과가 제한됩니다. `V29__add_inventory_query_indexes.sql`에는 통합재고 조회 패턴을 기준으로 네 개의 복합 인덱스가 추가됐습니다.

### 5.1 SKU×판매처 범위 탐색 인덱스

```sql
CREATE INDEX ix_inv_balance_sku_scope
    ON inventory_balance (
        sku_id,
        NVL(stock_sales_point_id, NVL(allocated_sales_point_id, -1)),
        is_deleted,
        warehouse_id,
        lot_id
    );
```

`inventory_balance`에서 `sku_id`와 판매처 범위를 먼저 찾고, 삭제 여부·센터·LOT 조건을 이어서 확인하는 조회를 지원합니다. `NVL`을 인덱스 식에 넣은 이유는 소유 판매처가 없을 때 할당 판매처, 그것도 없을 때 `-1`이라는 동일한 scope 표현을 쿼리와 인덱스에서 맞추기 위해서입니다. 컬럼을 단순히 나열한 인덱스가 아니라 **조회에서 실제로 사용하는 표현식까지 포함한 함수 기반 복합 인덱스**입니다.

### 5.2 최신 위험 이력 인덱스

```sql
CREATE INDEX ix_risk_balance_latest
    ON risk_assessment (
        inventory_balance_id,
        is_deleted,
        updated_at DESC,
        risk_assessment_id DESC
    );
```

위험 이력은 `inventory_balance_id`별 최신 행을 골라야 합니다. `updated_at DESC`로 최신 이력부터 읽고, 시간이 같은 경우 `risk_assessment_id DESC`로 순서를 고정합니다. 매퍼의 `ROW_NUMBER()` 정렬 기준과 인덱스의 정렬 기준을 맞춘 것입니다.

### 5.3 정책·가격 최신 행 인덱스

```sql
CREATE INDEX ix_inv_policy_scope_latest
    ON inventory_policy (
        sku_id,
        COALESCE(stock_sales_point_id, allocated_sales_point_id, -1),
        is_deleted,
        effective_from DESC,
        inventory_policy_id DESC
    );

CREATE INDEX ix_sku_price_scope_latest
    ON sku_channel_price (
        sku_id,
        sales_point_id,
        is_deleted,
        effective_from DESC,
        sku_channel_price_id DESC
    );
```

정책과 가격도 SKU·판매처 범위에서 기준일에 유효한 최신 행을 찾아야 합니다. scope를 먼저 좁히고 `effective_from` 최신순으로 읽도록 했습니다. 같은 적용일의 행이 여러 개일 때 ID를 보조 키로 둬 결과를 결정적으로 만든 점도 위험 이력 인덱스와 같습니다.

### 5.4 인덱스가 만능은 아니다

복합 인덱스는 읽기 경로를 빠르게 만들 수 있지만 다음 비용이 있습니다.

- `INSERT`, `UPDATE`, `DELETE` 때 인덱스도 함께 갱신해야 합니다.
- 인덱스 저장 공간과 통계 관리 비용이 추가됩니다.
- 컬럼 순서가 다른 조회나 함수 표현식이 다른 조회에는 기대만큼 사용되지 않을 수 있습니다.
- Oracle 옵티마이저가 더 저렴한 실행계획을 선택하면 특정 쿼리에서 인덱스를 사용하지 않을 수 있습니다.

그래서 이번 글에서 “이 인덱스를 추가했으니 모든 조회가 빨라졌다”고 말하지 않습니다. `InventoryQueryIndexMigrationContractTest`가 인덱스 정의가 배포 스크립트에 남아 있는지 확인하고, 실제 사용 여부와 비용은 운영과 가까운 데이터에서 실행계획으로 검증해야 합니다.

## 6. 개선 코드가 실제 API 응답으로 이어지는 방식

### 6.1 백엔드 API가 숫자의 의미를 책임지고 프론트엔드는 표시한다

develop 기준으로 Oracle SQL이 계산한 결과를 백엔드 `InventoryItemVO`와 `InventoryItemResponse`에 담고, `InventoryResponseMapper`가 응답 필드로 옮깁니다. 프론트의 `inventoryMapper.js`는 `expectedDisposalQuantity`를 숫자로 변환해 목록 모델에 보관합니다.

```text
InventoryMapper.xml
  → expected_disposal_qty
    → InventoryItemVO
      → InventoryItemResponse
        → inventoryMapper.js
          → 데스크톱 표·모바일 카드
```

프론트가 `availableQuantity - reservedQuantity`나 forecast를 다시 계산하지 않는 이유도 여기에 있습니다. UI는 서버가 정한 기준일과 scope 계산 결과를 그대로 보여 주고, 0은 `0개`로 표시하며 값이 없는 경우만 `-`로 구분합니다.

### 6.2 목록과 요약 API는 같은 필터를 쓰되 목적은 다르다

목록은 페이지·정렬 파라미터가 필요하지만, 상단 요약은 현재 페이지가 아니라 필터 전체의 가용수량을 보여 줘야 합니다. 그래서 프론트 `inventoryApi.js`는 목록과 요약의 파라미터를 분리합니다.

```js
export async function getInventories(params = {}, signal) {
  return requestJson({
    path: 'v1/inventories',
    method: 'get',
    params: extractInventoryQueryParams(params),
    signal,
  });
}

export async function getInventorySummary(params, signal) {
  return requestJson({
    path: 'v1/inventories/summary',
    method: 'get',
    // page, size, sort는 요약에 전달하지 않음
    params: extractInventoryQueryParams(params, { includePagination: false }),
    signal,
  });
}
```

백엔드의 `countInventory`와 `selectInventorySummary`도 `candidate_keys`와 공통 필터를 사용합니다. 목록은 페이지로 자르지만 요약은 필터 전체의 `available_qty`를 합산합니다. 이 차이를 명시하지 않으면 페이지를 넘길 때 상단 총 가용수량이 바뀌는 버그가 생깁니다.

Query key도 목록과 요약을 다르게 만들었습니다. 목록 key에는 `page`, `size`, `sort`가 포함되지만, 요약 key는 `pickSummaryParams`로 필터만 남깁니다. 같은 필터에서 페이지나 정렬만 바꿀 때 요약 캐시를 새 데이터처럼 여러 개 만들지 않기 위한 구분입니다. `filterOperator`는 필터 의미를 바꾸므로 요약 key에 포함합니다.

```js
summary: (params = {}) => [
  ...inventoryKeys.summaries(),
  pickSummaryParams(params), // page·size·sort 제외, 필터만 유지
],
```

목록·요약 query의 `staleTime`은 `0`이고, 재시도는 서버 오류에 한해 최대 한 번입니다. 재고를 오래된 값으로 고정하지 않으면서도 잘못된 필터나 인증 오류를 무의미하게 반복 요청하지 않도록 한 현재 정책입니다.

## 7. 프론트엔드 개선: 빠른 재조회는 유지하고 이전 요청은 취소한다

서버 응답이 빨라져도 사용자가 필터와 정렬을 연속으로 바꾸면 요청이 겹칠 수 있습니다. 현재 `inventoryQueries.js`는 TanStack Query의 `keepPreviousData`와 `AbortSignal`을 사용합니다.

```js
export function inventoryListQueryOptions(params = {}) {
  return queryOptions({
    queryKey: inventoryKeys.list(params),
    queryFn: ({ signal }) => getInventories(params, signal),
    placeholderData: keepPreviousData,
    staleTime: 0,
    retry: retryServerErrorOnly,
  });
}
```

`keepPreviousData`는 새 요청이 끝날 때까지 이전 목록 행과 테이블 높이를 유지합니다. 기존 데이터를 먼저 비우고 큰 스켈레톤을 그리는 방식보다 필터를 바꿀 때 화면이 덜 흔들립니다.

`queryFn`이 받은 `signal`은 `inventoryApi.js`를 거쳐 HTTP 클라이언트로 전달됩니다. 정렬을 빠르게 두 번 바꿨다면 먼저 시작한 요청을 취소해 늦은 이전 응답이 최신 조건의 화면을 덮어쓰는 가능성을 줄입니다.

화면의 로딩 표현도 한 단계가 아닙니다.

```text
0 ~ 400ms   기존 행 유지
400ms 이후  작은 “조회 중” 안내
1초 이후    본문 스켈레톤 표시
```

이 400ms·1초 지연은 `InventoryTable.jsx`의 `useProgressiveFetching`과 테스트에 고정된 값입니다. 빠른 응답에 매번 스켈레톤을 보여 주지 않고, 정말 오래 걸릴 때만 사용자가 상태를 알아차리게 하려는 UI 선택입니다. 이 부분은 DB 실행시간을 줄이는 작업은 아니지만, 같은 조회 비용을 사용자가 체감하는 방식에 영향을 줍니다.

### 8.2 테스트로 고정한 계약

성능 변경은 결과가 빨라지는 것만큼 결과가 틀리지 않는 것도 중요합니다. develop에는 다음 계약 테스트가 함께 들어갔습니다.

- `InventoryFilterSqlRenderingTest`: 단일·복수 선택, `AND`·`OR`, 필터 SQL 렌더링
- `InventoryQuantitySqlContractTest`: 가용수량, 예약수량 이중 차감 방지, 예상 폐기수량 SQL 계약
- `InventoryQueryIndexMigrationContractTest`: V29 복합 인덱스 정의
- `InventoryOracleMapperTest`: 실제 Oracle 매퍼 기준 목록·페이지·미할당 범위 검증
- `InventoryQueryServiceImplTest`: 목록·요약 서비스가 같은 조회 조건을 전달하는지 검증
- Frontend `inventoryQueries`·`inventoryMapper`·`InventoryTable` 테스트: Query key, 응답 필드 매핑, 400ms/1초 로딩 상태

테스트가 실행계획 자체를 대신하지는 않습니다. SQL 문자열과 경계 조건이 바뀌었을 때 기존 계약을 놓치지 않게 하는 안전망이고, 실제 성능은 실행계획과 대표 데이터로 별도 측정해야 합니다.

## 9. 트레이드오프와 남겨 둔 선택지

### 9.1 `OFFSET` 페이지네이션은 현재 계약을 지키는 선택이었다

현재 API는 `page`, `size`, `sort`를 사용하고, SQL도 `OFFSET … FETCH NEXT`를 사용합니다. 페이지 번호를 URL에 그대로 표현할 수 있고 구현 변경 범위가 작다는 장점이 있습니다.

반면 매우 깊은 페이지에서는 앞의 행을 건너뛰는 비용이 커질 수 있습니다. 데이터가 더 늘고 깊은 페이지의 p95가 문제가 되면, 마지막 `updated_at`·`sku_code`를 커서로 넘기는 키셋 페이지네이션을 검토할 수 있습니다. 다만 이는 API 계약과 프론트 페이지 UI를 함께 바꾸는 일이라 이번 개선에 섞지 않았습니다.

### 9.2 예상 폐기수량 정렬은 계산 범위와 함께 봐야 한다

현재 develop은 예상 폐기수량을 후보 SKU 전체에서 계산한 뒤 `paged_candidates`에 붙입니다. 이 값을 전체 후보에서 계산해야 `expected_disposal_qty`로 정렬할 수 있기 때문입니다. 따라서 일반 상세 집계는 페이지 SKU로 줄었지만, 예상 폐기 branch는 아직 후보 수에 비례하는 비용이 남아 있습니다. develop의 요청 DTO에는 `expected_disposal_qty` 정렬 컬럼 허용 목록도 있으므로, 이 동작을 “이미 페이지 이후 계산”이라고 설명하면 안 됩니다.

가능한 선택지는 다음과 같습니다.

1. 예상 폐기수량을 페이지 SKU에 대해서만 계산하고, 해당 컬럼 정렬을 제거하거나 제한한다.
2. 현재처럼 전체 후보의 예상 폐기수량을 먼저 계산해 정확한 정렬을 보장한다.
3. 동기화 시점에 별도 read model을 만들고 정렬용 값을 저장한다.

1번은 페이지 응답 비용을 줄일 수 있지만 정렬 의미가 달라집니다. 2번은 DB 비용이 후보 수에 따라 커질 수 있고, 3번은 최신 forecast와 동기화 실패를 다시 관리해야 합니다. 따라서 기능 요구와 성능 측정을 함께 보고 결정해야 합니다.

### 9.3 현재 방식과 저장형 read model의 경계

이번 변경은 기존 테이블과 조회 SQL만 수정했습니다. materialized view, Redis 캐시, 새 수량 컬럼, 사전 집계 배치를 추가하지 않았습니다. 이 선택은 구조를 단순하게 유지하고 기준일·forecast 변경을 즉시 조회에 반영한다는 장점이 있습니다.

반대로 데이터가 크게 늘어 다음 조건이 생기면 저장형 구조가 합리적일 수 있습니다.

- 목록·요약의 p95/p99가 합의한 SLO를 지속해서 넘습니다.
- 같은 필터 결과를 여러 화면과 다운로드가 반복해서 읽습니다.
- Oracle CPU와 buffer gets가 조회 트래픽의 병목이 됩니다.
- `OFFSET` 깊은 페이지와 예상 폐기 정렬을 동시에 지원해야 합니다.

그때도 먼저 실행계획, 인덱스 사용률, 캐시 적중률, 필터 조합별 응답 분포를 측정한 뒤 read model·캐시·키셋 페이지네이션 중 하나를 선택해야 합니다. “데이터가 많아질 것 같다”는 이유만으로 저장 구조를 먼저 추가하지 않는 것이 이번 작업에서 배운 또 하나의 기준입니다.

## 10. 이번 2편의 결론

통합재고 조회 최적화는 복합 인덱스 하나를 추가하는 작업으로 끝나지 않았습니다.

```text
필터 의미 고정
  → 후보 SKU·판매처 범위 축소
    → SKU 단위 가용수량·위험도 집계
      → 예상 폐기 branch와 정렬 대상 계산
        → 정렬·페이지 확정
          → 현재 페이지 상세 집계
            → 프론트는 이전 화면을 유지하고 최신 응답만 표시
```

여기에 수량의 의미를 함께 맞췄습니다. 현재 가용수량은 판매 불가 LOT를 제외한 `on_hand_qty`이고, 예약수량을 다시 빼지 않습니다. 30일 예상 폐기수량은 판매처 scope별 forecast와 LOT 종료일을 비교한 뒤 SKU로 합산합니다. 다만 현재 예상 폐기 집계는 정렬을 지원하기 위해 후보 단계에서 먼저 계산하므로, 이 branch까지 페이지 뒤로 미룬 것은 아닙니다. 목록·상세·요약이 같은 `asOfDate`와 필터 계약을 사용하도록 했기 때문에, 빠른 조회와 일관된 숫자를 같은 작업으로 설명할 수 있고, 남은 후보 전체 계산 비용도 다음 측정 대상으로 명확히 남겼습니다.
