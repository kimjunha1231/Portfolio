통합재고 화면에서 필터를 바꾸거나 정렬을 누르면 한동안 목록이 비어 보이거나, 네트워크 탭에 같은 요청이 여러 번 쌓이는 일이 있었습니다. 화면은 20개 행만 필요했지만 데이터베이스는 그보다 훨씬 넓은 범위를 읽고 있었습니다.

이번 변경의 핵심은 **먼저 후보 SKU를 줄이고, 현재 페이지에 필요한 데이터만 계산하는 것**입니다. 다중 필터의 `AND`와 `OR` 의미도 목록·건수·요약이 같은 기준을 사용하도록 맞췄습니다. 다만 `COUNT`와 `SUMMARY`는 전체 집계이므로 별도 실행계획과 p95 측정이 필요한 영역으로 남겨 두었습니다.

## 먼저 결론

- 목록의 기준(grain)을 `SKU 1행`으로 고정했습니다.
- 검색·필터 후보를 만든 뒤 정렬과 페이징을 적용하고, 페이지에 들어온 SKU만 판매처·센터·정책·가격·JSON으로 확장합니다.
- 채널·판매처·권역·물류센터의 다중 선택 `AND`는 `COUNT(DISTINCT ...) = 선택 개수`, `OR`는 `EXISTS ... IN (...)`으로 표현했습니다.
- 프론트는 `keepPreviousData`로 기존 행을 유지하고, 400ms 이후에만 “조회 중”, 1초 이후에만 본문 스켈레톤을 보여 줍니다. 정렬을 빠르게 연속으로 누르면 이전 요청은 `AbortSignal`로 취소됩니다.
- 현재 변경은 **목록 조회의 데이터 범위와 호출을 줄인 개선**입니다. 상단 요약과 전체 건수의 실행계획까지 최적화됐다고 단정하지 않고, 다음 측정 대상으로 분리했습니다.

## 1. 변경 전: 20개를 가져오기 전에 전체를 계산했다

기존 목록 SQL은 마지막에 `OFFSET … FETCH NEXT`를 적용했습니다. 그 앞에서 판매처별 JSON, 물류센터별 JSON, 최신 정책·가격, 위험도 집계를 넓은 범위에 대해 만들었습니다.

```sql
WITH risk_rows AS (... 전체 위험 이력에서 ROW_NUMBER ...),
     latest_policy AS (... 전체 정책에서 최신 행 ...),
     latest_price AS (... 전체 가격에서 최신 행 ...),
     seller_agg AS (... 판매처 전체를 JSON_ARRAYAGG ...)
SELECT ...
FROM ...
ORDER BY ...
OFFSET :offset ROWS FETCH NEXT :size ROWS ONLY;
```

이 방식은 “결과는 20개”와 “계산도 20개”를 혼동한 구조였습니다. `ROW_NUMBER()`는 파티션별 정렬을 필요로 하고, `JSON_ARRAYAGG(... RETURNING CLOB)`는 결과를 직렬화합니다. 페이지에 나오지 않을 SKU까지 이 작업을 거치면 데이터가 늘수록 비용이 선형으로 커집니다.

### 다중 `AND` 필터도 상관 서브쿼리를 반복했다

채널을 네 개 선택했을 때 이전 SQL은 채널마다 `EXISTS`를 만들었습니다.

```sql
AND EXISTS (... 채널 A ...)
AND EXISTS (... 채널 B ...)
AND EXISTS (... 채널 C ...)
AND EXISTS (... 채널 D ...)
```

`EXISTS` 안에서 다시 `inventory_balance`와 `sales_point`를 조인하고 채널 코드를 정규화했습니다. 바깥 후보 행마다 이 서브쿼리가 평가될 수 있어 선택 개수가 늘수록 같은 테이블과 조인을 반복해서 읽게 됩니다. 이 때문에 **상관 서브쿼리(correlated subquery)** 비용이 발생합니다.

![개선 전 통합재고 조회 네트워크 캡처](/images/blog/integrated-inventory-query-before.png)

*개선 전 측정 캡처. 화면에는 일부 행만 필요하지만 목록 XHR이 긴 시간 동안 실행되는 상황을 기록했습니다. 실제 시간은 데이터량·Oracle 부하·네트워크에 따라 달라집니다.*

## 2. 백엔드 개선: 후보 SKU를 먼저 만들고 페이지를 드라이브한다

매퍼의 CTE 순서를 다음처럼 바꿨습니다.

```text
valid_scope_keys
  → sku_risk_agg
  → candidate_keys       -- 검색·필터가 맞는 SKU × 판매처 범위
  → candidate_balance_base
  → candidate_sku_agg    -- SKU 단위 수량·LOT·위험 요약
  → paged_candidates     -- 정렬 + OFFSET/FETCH
  → 페이지 SKU의 상세 집계
```

핵심은 `paged_candidates` 아래에 있던 무거운 집계를 페이지 아래로 내린 점입니다.

```sql
WITH candidate_keys AS (
    SELECT DISTINCT ib.sku_id,
           NVL(ib.stock_sales_point_id,
               NVL(ib.allocated_sales_point_id, -1)) AS sales_point_id
    FROM inventory_balance ib
    JOIN sku s ON s.sku_id = ib.sku_id
    JOIN product p ON p.product_id = s.product_id
    LEFT JOIN sales_point sp ON sp.sales_point_id =
        NVL(ib.stock_sales_point_id, ib.allocated_sales_point_id)
    LEFT JOIN sku_risk_agg sr ON sr.sku_id = ib.sku_id
    WHERE ib.is_deleted = 0
      /* candidateFilterWhere: 검색·채널·판매처·센터·카테고리 ... */
),
candidate_sku_agg AS (
    SELECT cbb.sku_id,
           SUM(cbb.on_hand_qty + cbb.reserved_qty) AS current_qty,
           SUM(cbb.on_hand_qty) AS available_qty,
           SUM(cbb.reserved_qty) AS reserved_qty,
           COUNT(DISTINCT cbb.lot_id) AS lot_count,
           MAX(cbb.updated_at) AS updated_at
    FROM candidate_balance_base cbb
    GROUP BY cbb.sku_id
),
paged_candidates AS (
    SELECT q.*, COUNT(*) OVER () AS total_count
    FROM (
        SELECT ...
        FROM candidate_sku_agg csa
        JOIN sku s ON s.sku_id = csa.sku_id
        JOIN product p ON p.product_id = s.product_id
    ) q
    ORDER BY q.updated_at DESC, q.sku_code ASC
    OFFSET :offset ROWS FETCH NEXT :size ROWS ONLY
)
SELECT ...
FROM paged_candidates pc
LEFT JOIN latest_policy lp ON lp.sku_id = pc.sku_id
LEFT JOIN latest_price price ON price.sku_id = pc.sku_id
LEFT JOIN seller_agg sellers ON sellers.sku_id = pc.sku_id;
```

이 구조를 **pagination pushdown** 또는 **page-driven detail expansion**이라고 부를 수 있습니다. 후보를 SKU로 먼저 고정하므로 판매처와 LOT의 1:N 관계가 목록 행을 복제하지 않고, 페이지에 들어온 SKU에 대해서만 상세 CTE가 동작합니다. `COUNT(*) OVER()`는 같은 후보 집합에서 전체 건수를 함께 가져오기 위한 윈도 함수이고, 정렬 키에 `sku_code ASC`를 붙여 값이 같은 행의 순서도 안정적으로 만들었습니다.

### 정렬 컬럼은 허용 목록을 거친다

정렬 SQL은 컬럼명을 바인딩 변수로 넣을 수 없어 MyBatis의 `${sortColumn}`을 사용합니다. 대신 요청 DTO에서 외부 입력을 그대로 통과시키지 않고 허용된 컬럼으로 변환합니다.

```java
private static String sortColumn(String sort) {
    String field = sortPart(sort, 0, "updatedAt");
    return switch (field) {
        case "updatedAt" -> "updated_at";
        case "productName" -> "product_name";
        case "skuCode" -> "sku_code";
        case "currentQuantity", "currentQty" -> "current_qty";
        case "availableQuantity", "availableQty" -> "available_qty";
        case "riskGrade" -> "risk_grade";
        default -> throw new AppException(ErrorCode.INVALID_PARAMETER);
    };
}
```

동적 SQL은 남아 있지만 **whitelist validation을 통과한 식별자만 렌더링**됩니다. 방향도 `ASC`·`DESC`만 허용합니다. 동적 컬럼을 무조건 문자열 연결로 처리하는 것과는 다른 안전장치입니다.

## 3. `AND`와 `OR`: 같은 필터 계약을 목록·건수·요약에 공유한다

필터 연산자는 “선택한 값들 사이를 어떻게 묶을지”를 뜻합니다.

- `AND`: 선택한 값이 모두 존재해야 통과
- `OR`: 선택한 값 중 하나라도 존재하면 통과

채널·판매처·권역·물류센터처럼 하나의 SKU에 여러 행이 존재할 수 있는 필터는 다음처럼 바꿨습니다.

```xml
<when test="filterOperator == 'AND' and channelTypes.size() > 1">
  (
    SELECT COUNT(DISTINCT CASE
      WHEN channel_sp.sales_point_code = 'GREETING' THEN 'GREETING'
      WHEN channel_sp.sales_point_code = 'MODU_MATJIP' THEN 'ECOMMERCE'
      WHEN channel_sp.sales_point_code LIKE 'DEPT_%' THEN 'HYUNDAI_DEPT'
      WHEN channel_sp.sales_point_code LIKE 'HMART_%' THEN 'HMART'
      ELSE channel_sc.channel_code
    END)
    FROM inventory_balance channel_ib
    JOIN sales_point channel_sp ON channel_sp.sales_point_id =
      NVL(channel_ib.stock_sales_point_id, channel_ib.allocated_sales_point_id)
    LEFT JOIN sales_channel channel_sc ON channel_sc.sales_channel_id =
      channel_sp.sales_channel_id
    WHERE channel_ib.is_deleted = 0
      AND channel_ib.sku_id = ib.sku_id
      AND (
        CASE
          WHEN channel_sp.sales_point_code = 'GREETING' THEN 'GREETING'
          WHEN channel_sp.sales_point_code = 'MODU_MATJIP' THEN 'ECOMMERCE'
          WHEN channel_sp.sales_point_code LIKE 'DEPT_%' THEN 'HYUNDAI_DEPT'
          WHEN channel_sp.sales_point_code LIKE 'HMART_%' THEN 'HMART'
          ELSE channel_sc.channel_code
        END
      ) IN
        <foreach collection="channelTypes" item="channelType" open="(" separator="," close=")">
          #{channelType}
        </foreach>
  ) = #{channelTypeCount}
</when>
```

네 개 중 세 개만 가진 SKU는 `COUNT(DISTINCT ...) = 3`이므로 제외되고, 네 개를 모두 가진 SKU만 통과합니다. `OR`는 같은 정규화 규칙을 한 번의 `EXISTS`와 `IN (...)`으로 평가합니다.

```sql
EXISTS (
    SELECT 1
    FROM inventory_balance filter_ib
    ...
    WHERE filter_ib.sku_id = ib.sku_id
      AND normalized_channel IN ('ECOMMERCE', 'GREETING', 'HMART')
)
```

`filterOperator`는 `InventoryQuery`에서 `AND`·`OR`만 허용하고, MyBatis의 `<choose>`도 두 고정 토큰만 출력합니다. 이 공통 `candidateFilterWhere`를 `selectInventoryList`, `countInventory`, `selectInventorySummary`가 함께 사용하므로, 같은 요청 조건을 세 API가 서로 다르게 해석할 가능성을 줄였습니다.

현재 구현은 **여러 `EXISTS` → 하나의 상관 집계**로 줄인 것입니다. 선택 채널을 전역에서 한 번 집계한 뒤 조인하는 `selected_channel_skus` CTE와는 다릅니다.

```sql
selected_channel_skus AS (
    SELECT channel_ib.sku_id
    FROM inventory_balance channel_ib
    ...
    WHERE normalized_channel IN (...)
    GROUP BY channel_ib.sku_id
    HAVING COUNT(DISTINCT normalized_channel) = :selectedCount
)
```

Oracle 옵티마이저가 상관 서브쿼리를 조인으로 변환할 수도 있으므로, “항상 한 번만 스캔한다”고 SQL 문자열만 보고 단정할 수는 없습니다. 실제 `DBMS_XPLAN.DISPLAY_CURSOR`의 `Starts`, buffer gets, 반환 행 수로 다음 단계의 필요성을 판단해야 합니다.

## 4. 프론트엔드 개선: 빠른 요청은 조용히, 늦은 요청만 보여 준다

백엔드가 빨라져도 필터를 누를 때마다 기존 테이블을 제거하고 스켈레톤 전체를 다시 만들면 화면은 깜빡입니다. 그래서 초기 진입과 재조회를 분리했습니다.

```js
export function inventoryListQueryOptions(params = {}) {
  return queryOptions({
    queryKey: inventoryKeys.list(params),
    queryFn: ({ signal }) => getInventories(params, signal),
    placeholderData: keepPreviousData,
    staleTime: 0,
    retry: retryServerErrorOnly,
  });
}
```

목록 요청이 진행 중이어도 `keepPreviousData`가 기존 행과 테이블 높이를 유지합니다. `isFetching`은 다음 세 단계로 화면에 반영합니다.

```text
0 ~ 400ms   기존 행 유지, 별도 표시 없음
400ms 이후  목록 상단에 작은 “조회 중” 상태 표시
1초 이후    본문 영역만 중립적인 스켈레톤으로 교체
```

필터나 정렬을 빠르게 연속해서 바꾸면 TanStack Query가 전달한 `AbortSignal`을 Axios 요청까지 전달합니다. 새 요청이 시작되면 이전 요청을 취소하므로, 늦게 도착한 이전 응답이 최신 조건의 결과를 덮어쓰지 않습니다. 네트워크 탭에 `(취소됨)`이 보이는 것은 이 경로가 동작한다는 신호이지, 서버 오류를 뜻하지 않습니다.

![개선 후 통합재고 조회 네트워크 캡처](/images/blog/integrated-inventory-query-after.png)

*개선 후 측정 캡처. 필터가 적용된 목록과 요약 요청이 같은 조건으로 완료되는 화면을 남겼습니다. 캡처의 시간은 실행 환경에 따른 관찰값이며 모든 운영 트래픽의 보장값은 아닙니다.*

![정렬 변경 중 이전 요청이 취소되는 네트워크 캡처](/images/blog/integrated-inventory-query-sort-after.png)

*정렬을 연속으로 변경한 상황. 앞선 요청은 취소되고 마지막 정렬 조건의 응답만 남도록 요청 생명주기를 정리했습니다.*

`refetchOnWindowFocus`는 전역 정책으로 무조건 최신화하지 않고, 동기화 완료 이벤트에서 목록·요약을 명시적으로 무효화하는 흐름과 함께 결정해야 합니다. 현재 화면은 동기화가 성공했을 때 필요한 쿼리만 `invalidateQueries`해, 탭으로 돌아왔다는 이유만으로 무거운 재고 조회를 반복하지 않습니다.

## 5. 이번 변경으로 해결한 것과 남긴 것

### 해결한 문제

- 목록 페이지에 없는 SKU까지 판매처 JSON·정책·가격을 계산하던 범위를 줄였습니다.
- 판매처·LOT 1:N 조인으로 목록 행이 복제되는 위험을 SKU 단위 후보 집합으로 분리했습니다.
- 채널·판매처·권역·물류센터 다중 선택의 `AND`를 선택 개수 집계로 표현하고, `OR`를 `IN`으로 단순화했습니다.
- 목록·건수·요약이 같은 후보 필터와 `filterOperator` 계약을 사용하도록 맞췄습니다.
- 정렬 컬럼과 방향을 허용 목록으로 제한하고, `NULL` 정렬과 SKU 코드 tie-breaker를 추가했습니다.
- 프론트에서 빠른 재조회를 조용히 처리하고, 오래 걸릴 때만 상태와 스켈레톤을 노출했습니다.

### 다음 측정이 필요한 것

- `countInventory`와 `selectInventorySummary`의 전체 범위 집계 실행계획
- `selected_channel_skus` 전역 사전 집계와 현재 상관 집계의 실제 buffer gets 비교
- 대표 필터 조합별 p50·p95·p99, Oracle CPU와 대기 시간
- 깊은 `OFFSET` 페이지에서 키셋 페이지네이션으로 전환할 기준
- 프론트 요약 파라미터의 허용 목록과 백엔드 필터 목록이 계속 일치하는지에 대한 계약 테스트

이번 작업을 통해 “20건 응답이 빠른가?”라는 질문을 “20건을 만들기 전에 몇 건을 계산하고 있었는가?”로 바꿔 볼 수 있게 됐습니다. 다음 최적화도 같은 원칙을 따릅니다. **후보를 먼저 좁히고, 무거운 계산은 마지막에, 그리고 목록·건수·요약의 의미는 하나의 필터 계약으로 묶는 것**입니다.
