## 프로젝트 개요

Smart Messaging System은 마케터가 고객을 선택하고, 메시지를 작성·검토한 뒤 여러 채널로 발송하고 결과를 분석할 수 있도록 구성한 통합 메시징 시스템입니다.

- **기간**: 2026.07
- **구분**: 팀 프로젝트
- **담당 범위**: 고객 조회 성능 개선, Redis 기반 수신자 관리, 메시지 링크 추적·수신거부·구매 전환, 발송·통계 UI와 테스트 보강
- **기술 스택**: Java, Spring Boot, Thymeleaf, Oracle, MyBatis, Redis, RabbitMQ
- **주요 성과**:
  - 고객 목록 API 요청 시간 1.99초 → 265ms (**86.7% 감소**), 전체 로드 시간 2.64초 → 564ms (**78.6% 감소**)
  - 고객 정보 요청 8.46초 → 350ms (**95.9% 감소**), 응답 크기 268KB → 0.6KB (**99.8% 감소**)
  - 메시지 이력 요청 5.03초 → 315ms (**93.7% 감소**), 상세 화면 전체 네트워크 완료 시간 11.02초 → 2.54초 (**77.0% 감소**)
  - Redis Draft에 선택 상태를 30분 동안 보관하고, 1,000개 단위 청크와 pipeline으로 대량 선택 요청 처리

## 담당 기능

- **고객 조회**: 고객 목록·상세 조회를 분리하고, 페이지네이션·태그 일괄 조회·메시지 이력 조회를 구현했습니다.
- **수신자 관리**: 여러 검색 결과에서 누적 선택한 수신자를 Redis Draft에 저장하고, TTL과 Selected 탭 페이징을 관리했습니다.
- **메시지 링크와 이벤트 추적**: 발송 대상별 단축 URL을 만들고 클릭·구매 전환·수신거부를 서로 다른 목적의 이벤트로 기록했습니다.
- **멀티채널 발송 보강**: Kakao·SMS/LMS·Email 채널별 입력과 결과를 연결하고, 수신 동의와 발송 실패 결과를 확인할 수 있도록 보강했습니다.
- **검토와 검증**: 발송 전 대상 수·비용 확인 UI와 통계 화면을 보완하고, Mapper·서비스·발송 흐름의 핵심 시나리오를 테스트했습니다.

- **해결 과정**: 조회 목적에 따라 목록과 상세를 분리했습니다. 목록은 현재 페이지에 필요한 고객 정보만 조회하도록 바꾸고, 목록 쿼리에서 상세 전용 `lastSend` 서브쿼리를 제거했습니다. count 쿼리에서도 건수 계산에 필요하지 않은 채널 동의 집계 조인을 제외했습니다.

기존에는 MyBatis `ResultMap`의 중첩 `collection select`로 고객별 태그를 조회해, 목록의 고객 수만큼 추가 쿼리가 발생하는 N+1 조회 문제가 생겼습니다. 현재 페이지의 고객 ID를 모아 `IN` 조건으로 한 번에 조회한 뒤 서비스 계층에서 고객별로 그룹화하는 방식으로 변경했습니다.

상세 모달에는 `GET /api/customers/{customerId}` 단일 고객 API를 추가했습니다. 프론트엔드는 고객 정보와 메시지 이력을 `Promise.all`로 병렬 요청하고, 이력 조회는 최근 90일·최대 40건으로 제한했습니다. 이력에 포함되던 실패 사유 서브쿼리도 제거해 상세 화면에 필요한 범위만 조회하도록 했습니다.

```javascript
Promise.all([
  fetch(`/api/customers/${customerId}`).then((res) => res.json()),
  fetch(`/api/customers/${customerId}/history`).then((res) => res.json()),
]);
```

- **문제 상황**: 수신자는 여러 검색 조건과 페이지를 오가며 누적 선택할 수 있어야 했습니다. <br/>초기에는 선택한 회원 ID 전체를 localStorage에 저장했지만, 대량 데이터를 직렬화·저장·조회하는 동안 브라우저 메인 스레드를 점유하면서 속도 저하를 느꼈습니다. 또한 고객 식별자 목록을 클라이언트 저장소에 보관하는 보안 부담도 있었습니다. 그렇다고 발송 여부가 확정되지 않은 임시 목록을 DB에 저장하면 불필요한 Insert·Delete와 데이터 정리 문제가 발생할 수 있었습니다.

- **해결 과정**: 브라우저에는 전체 고객 ID 대신 Redis Draft를 식별하는 `draftId`만 두고, 사용자 선택 상태를 Redis에 임시 저장했습니다. Redis 자료구조로 Sorted Set을 선택한 이유는 선택 순서를 `score`로 저장하면서 고객 ID를 중복 없이 관리하고, 정렬된 목록을 범위 단위로 조회할 수 있기 때문입니다. 신규 선택 고객에는 순차적인 score를 부여하고, 데이터 적재 상태는 별도의 Hash 키로 관리했으며 두 키에 30분 TTL을 적용했습니다.


Selected 탭은 Sorted Set의 `ZRANGE`로 현재 페이지에 필요한 고객 ID만 조회한 뒤, 해당 ID의 상세 정보만 Oracle에서 가져오도록 구성했습니다. 이를 통해 검색 조건이 바뀌어도 누적 선택 순서를 유지하면서 페이지 단위로 목록을 조회해 성능을 확보했고, 전체 선택 수는 Redis `ZCARD`로 계산해 페이지 수가 어긋나지 않도록 했습니다.

대량 선택 요청은 전체 목록을 한 번에 Redis에 전달하지 않도록 1,000개 단위의 청크로 나누고, Spring Data Redis의 `executePipelined`를 활용해 Sorted Set에 적재했습니다. 이를 통해 Redis 명령의 네트워크 왕복을 줄였습니다.

선택 수를 계산하는 코드는 Redis의 `ZCARD`를 사용해 전체 고객 ID를 다시 가져오지 않도록 했습니다. 화면에는 전체 ID 목록 대신 `draftId`만 전달하고, 실제 목록이 필요할 때만 페이지 범위의 ID를 조회합니다.

```java
String key = KEY_PREFIX + userId + ":" + draftId;
Long count = redisTemplate.opsForZSet().size(key);
return count != null ? count : 0;
```

`size`는 Sorted Set 안에 저장된 고객 수만 반환합니다. 그래서 발송 준비 화면에서 수천 명의 ID를 애플리케이션 메모리로 읽지 않고도 전체 대상 수를 표시할 수 있습니다.

- **결과**: 선택 상태·순서·중복 제거·페이지 조회·만료를 Redis에서 처리하면서 브라우저와 DB의 부담을 줄이고 빠르게 데이터를 주고 받을 수 있었습니다. 대량 선택 데이터를 청크 단위로 처리해 Redis 요청 크기와 임시 데이터 관리 부담을 제한할 수 있었습니다.


### 3. 메시지 링크를 클릭·구매·수신거부 이벤트로 확장

#### 문제 상황

메시지에 원본 URL만 넣으면 링크가 눌렸는지, 어떤 발송 대상이 반응했는지 확인하기 어려웠습니다. 구매 안내나 광고 메시지처럼 발송 이후 행동을 확인해야 하는 경우에는 단순 링크만으로는 캠페인 결과를 설명할 수 없었습니다.

#### 해결 과정

발송 대상(`sendTargetId`)과 링크 목적을 함께 저장하는 추적 URL을 만들었습니다. 링크 목적은 `CLICK`, `PURCHASE`, `UNSUBSCRIBE`로 구분해 같은 단축 URL 기능을 클릭·구매·수신거부 흐름에 재사용할 수 있도록 했습니다.

```java
String actionUrl = shortUrlService.createTrackedUrl(
        target.getId(),
        command.getLinkUrl(),
        ShortUrlPurpose.from(command.getLinkPurpose())
);
```

이 코드는 원본 URL을 그대로 메시지에 넣는 대신, 발송 대상과 링크 목적을 연결한 URL을 생성합니다. 사용자가 링크를 열면 서버가 대상을 확인한 뒤 클릭 횟수와 시간대별 통계를 기록하고 원래 페이지로 이동시킵니다.

구매 링크는 생성 시 전환 전 상태를 저장해 두고, 구매 완료 요청이 들어왔을 때 전환 여부를 갱신하도록 구성했습니다. 따라서 이 기능은 결제를 처리하는 기능이 아니라, 메시지에서 구매 페이지로 이동한 뒤 완료되었는지를 기록하는 기능입니다.

#### 결과

메시지 발송 결과를 성공·실패로만 판단하지 않고, 발송 대상별 클릭과 구매 전환까지 확인할 수 있게 되었습니다. 링크 목적을 분리했기 때문에 일반 링크와 구매 링크, 수신거부 링크가 서로 다른 통계로 섞이지 않습니다.


### 4. 광고성 메시지의 수신거부 흐름 연결

#### 문제 상황

광고성 문자에는 사용자가 쉽게 수신거부할 수 있는 경로가 필요합니다. 수신거부를 화면에서만 처리하면 다음 발송 대상 선정에 반영되지 않을 수 있고, 고객 동의 상태와 거부 이력을 따로 관리해야 하는 문제가 생깁니다.

#### 해결 과정

광고성 SMS를 만들 때 수신거부 URL이 없으면 발송하지 않도록 검증하고, 링크를 누르면 고객의 광고 수신 차단·SMS 동의 철회·거부 이력 저장을 한 흐름으로 처리했습니다.

```java
shortUrlMapper.markClicked(code);
unsubscribeMapper.blockCustomerAds(target.getCustomerId(), SYSTEM_ACTOR_ID);
unsubscribeMapper.revokeSmsConsent(target.getCustomerId(), SYSTEM_ACTOR_ID);
unsubscribeMapper.insertRejectHistoryIfAbsent(target.getCustomerId(), SYSTEM_ACTOR_ID);
```

각 작업을 한 번의 메서드 안에서 순서대로 처리해 “링크는 눌렸지만 동의 상태는 그대로인” 불일치를 줄였습니다. 이후 고객 조회와 발송 대상 필터에서 수신거부 상태를 사용할 수 있도록 DB 이력도 함께 남겼습니다.

#### 결과

수신거부를 단순한 안내 페이지가 아니라 실제 발송 대상 관리와 연결했습니다. 사용자의 거부 요청이 다음 광고성 메시지 발송에서 제외될 수 있는 데이터 흐름을 만들었습니다.


### 5. 멀티채널 발송과 채널별 결과 통일

#### 문제 상황

Kakao, SMS/LMS, Email은 필요한 입력과 실패 조건이 서로 달랐습니다. 채널마다 컨트롤러에서 직접 발송하도록 만들면 수신 동의 검증과 실패 처리 방식이 달라지고, 새로운 채널을 추가할 때 수정 범위가 커질 수 있습니다.

#### 해결 과정

Kakao OAuth·친구 목록 조회, SOLAPI SMS/LMS 발송, AWS SES 이메일 발송을 채널별 서비스로 나누고, 라우터가 현재 채널에 맞는 서비스를 선택하도록 구성했습니다.

```java
switch (currentChannel) {
    case "KAKAO":
        return kakaoMessageService.sendMemoMessage(token, title, content);
    case "SMS":
        return smsMessageService.sendTextMessage(phone, title, content, "SMS");
    case "EMAIL":
        return emailMessageService.sendEmail(email, title, content);
    default:
        return SendResult.fail(currentChannel, "UNSUPPORTED_CHANNEL", "지원하지 않는 채널입니다.");
}
```

각 채널 서비스는 성공·실패를 `SendResult`로 반환합니다. 라우터는 채널별 SDK 응답을 화면과 발송 이력에서 사용할 수 있는 동일한 결과 형태로 바꾸고, 수신 동의가 없거나 연락처 형식이 잘못된 경우도 발송 실패 사유로 구분합니다.

RabbitMQ 초기 구성 자체는 팀원의 담당 영역으로 두고, 저는 이 비동기 발송 흐름에 연결되는 발송 준비·대상 데이터·링크 생성·결과 처리 코드를 중심으로 보강했습니다.

#### 결과

채널별 구현은 분리하면서도 발송 요청과 결과 확인 방식은 통일했습니다. 이후 채널을 추가할 때 기존 화면과 결과 모델을 크게 바꾸지 않고 채널 서비스와 라우팅 규칙을 확장할 수 있는 구조가 되었습니다.


### 6. 발송 전 검토와 통계 화면 개선

#### 문제 상황

발송 버튼을 누르는 순간 바로 요청이 전송되면 대상 수나 예상 비용을 다시 확인하기 어렵습니다. 발송이 실패했을 때도 브라우저 알림만으로는 현재 상태와 다음 행동을 알기 어려웠습니다.

#### 해결 과정

발송 검토 화면에서 대상 수와 예상 비용을 먼저 표시하고, 확인 모달에서 한 번 더 요청을 확인하도록 했습니다.

```javascript
const confirmMsg = `총 ${this.state.totalCount.toLocaleString()}명에게 메시지 발송을 요청하시겠습니까?`;
this.openConfirmModal(confirmMsg);
```

요청이 성공하면 접수 결과 모달을 보여주고, 실패하면 실패 사유와 함께 현재 작성 단계로 돌아갈 수 있도록 흐름을 나누었습니다. 통계 화면에는 채널별 발송 추이·성공률·fallback 차트와 데이터 업데이트 시각을 표시했습니다.

#### 결과

발송 전 확인해야 하는 정보와 발송 후 확인할 수 있는 결과를 분리해, 실수로 대량 발송하는 위험과 실패 원인을 찾기 어려운 문제를 줄였습니다. 통계 화면에서는 발송량만 보는 것이 아니라 채널별 성공률과 fallback 단계까지 비교할 수 있게 되었습니다.


### 7. 테스트로 핵심 발송 흐름 검증

기능이 여러 서비스와 Mapper, 외부 채널에 걸쳐 있어 화면만 확인하는 방식으로는 회귀를 찾기 어려웠습니다. 그래서 PR에 포함된 테스트에서는 기능 목록보다 사용자의 행동과 데이터 흐름을 기준으로 시나리오를 나눴습니다.

- Mapper XML이 정상적으로 파싱되고 검색·태그·라우팅 쿼리가 등록되는지 확인
- 과거 예약 시간이 들어오면 발송 이력을 저장하지 않고 예외를 반환하는지 확인
- 발송 이력과 채널 우선순위가 저장되고 공통 작업 메시지가 발행되는지 확인
- 실제 고객과 가상 고객 발송 결과를 구분하고, 성공 채널의 비용을 계산하는지 확인
- 통계 카드와 fallback 성공률 차트가 낮은 성공률과 시도 단계를 올바르게 표시하는지 확인
- 발송 대상이 없거나 삭제된 이력을 요청했을 때 적절한 오류를 반환하는지 확인

예를 들어 과거 예약 발송은 저장 동작이 발생하지 않아야 한다는 조건까지 함께 검증했습니다.

```java
assertThatThrownBy(() -> sendPreparationService.prepare(10L, request, null))
        .isInstanceOf(BusinessException.class);

verify(sendPreparationMapper, never())
        .insertSendHistory(any(SendHistoryVO.class));
```

이처럼 예외가 발생했다는 사실뿐 아니라 DB에 잘못된 발송 이력이 남지 않았는지도 확인해, 서비스의 외부 동작과 내부 부작용을 함께 검증했습니다.


## 협업 범위

팀 프로젝트에서 RabbitMQ 기반 비동기 발송 인프라의 초기 구성은 팀원이 담당했고, 저는 고객 조회와 상세 조회 성능 개선, Redis Draft 기반 수신자 관리, 메시지 링크 추적과 수신거부·구매 전환, 발송·통계 UI와 관련 테스트를 중심으로 작업했습니다. 기존 발송 구조를 이해한 뒤 제 기능이 연결되는 지점을 수정하고, 데이터 상태와 화면 결과가 일치하는지 테스트로 확인했습니다.
